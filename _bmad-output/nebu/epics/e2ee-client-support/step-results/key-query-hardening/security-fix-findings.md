# Fix brief — Kassandra findings of key-query-hardening (cycle 3, user decided: fix the small things)

Report: `docs/stories/e2ee-client-support/security-reports/key-query-hardening-security-review-2026-11-03.md` (read all three LOW details first). Scope: ONLY the three items. Verdict was CLEAN; these are hardening.

## L1 — cross-user signature rows are bound to the master key ID, not to the key (D7 hole)
If a user replaces its master key with one that keeps the same key id but another public key (nothing enforces id == public key), `put_keys/2` keeps the old cross-user rows (the D7 `DELETE ... NOT (target_key_id = ANY(...))` guard compares ids only) and `/keys/query` still shows the stale signature. Fix: bind the row to the key itself, with the smallest change that closes it — e.g. also store the target key's public key value (`target_key` text, in migration **000061 edited in place: it is untracked/unshipped, check `git status`/`git ls-files` to be sure; if it is tracked, add 000062 instead**) and make BOTH the D7 drop in `put_keys/2` and the visibility join of `KeyQueryStore` compare the key value, not only the id; or drop all of a target's rows whenever its master `keys` map changed at all. Test: replace the master key keeping the SAME id with a different public key: the signature is gone from the query and the row is deleted; an unchanged re-upload (same id AND key) keeps it (the existing D7 negative-half test must stay green). GDPR erasure and RLS of the table stay as they are.

## L2 — up to 4000 Ed25519 verifications per request
Only the signature made BY THE CALLER can ever be stored or matter; verifying other users' signatures in an uploaded object is wasted work. Verify only `signatures[caller]` entries, cap them at 4 key entries per object (`400`-free: an object with more than 4 caller signatures fails per entry with `M_INVALID_PARAM`, before any verification), and ignore (neither verify nor reject, but do not store) signatures of other users as the spec allows; keep the 200-object cap. Worst case per request becomes 800 verifications; document the number. Test: object with 5 caller signatures -> M_INVALID_PARAM and no verification work is needed for it (assert the answer, not the work); an object carrying a foreign user's garbage signature next to a valid caller signature still verifies and stores; existing tests that rely on the old cap of 20 (grep `20 signatures`, docs and tests) are adapted, not weakened.
