# Cycle 2 — fixes from Kassandra security review (report: docs/stories/bugfix/security-reports/media-download-451-scan-race-security-review-2026-10-13.md). Classification CLEAN (0 CRITICAL/HIGH), fix F-1 + F-4 guard now; F-2/F-3/rest = documented follow-ups.

F-1 MEDIUM (MUST FIX): server/lib/nebu/media/download_stall.ex (~L95-101, L194-209) — stall slot leaks permanently when an HTTP/2 client closes its connection. Bandit runs each HTTP/2 request in a process linked to the connection process; on client disconnect that request process is killed from outside, so the `try/after` in await/4 that decrements the :atomics counter never runs. Reproduced by Kassandra (counter stayed at 1). Plain-text h2 is reachable (stackit tls_mode=none passes TCP through). Impact: 500 leaked slots => every download on the node gets the immediate 451 again until restart; ordinary users closing a tab leak slots too (default stall).
Fix: tie each slot to the requesting process's lifetime instead of relying on try/after — e.g. a small monitor/janitor (a process spawned per slot, or a single GenServer/Registry) that Process.monitor/2's the requesting pid and decrements on :DOWN OR on an explicit normal release (exactly-once decrement! guard against double decrement on normal release + later :DOWN: demonitor(flush) on release). Keep the ceiling semantics (acquire_slot atomically add_get/undo when full). Add tests: (1) kill the request process mid-stall (spawn a process that calls DownloadStall.await/4 or drive an HTTP-level request in a spawned process, then Process.exit(pid, :kill)) => slot count returns to 0 and a subsequent request can still stall with max_concurrent_stalls: 1; (2) normal completion releases exactly once (counter never goes negative; repeated cycles keep it at 0); (3) timeout, raise and no_slot paths still release exactly once. Expose the counter for tests only if the existing tests already read it a certain way — look at how current tests inspect slots.

F-4 (small, in scope): clamp_stall_ms/1 in server/lib/nebu/media.ex does not check that max_stall_ms is an integer: `min(ms, max(0, "5000"))` — a string cap sorts above every integer, so the client value would go unclamped. Add `is_integer` to the guard (non-integer cap => 0 = no stall). Add a unit-ish test (config max_stall_ms: "5000" => no stall / no crash).

NOT in this cycle (document as follow-ups in the story's Dev Agent Record + docs/architecture/10-quality.md M-1 entry if not already): F-2 per-user/per-IP cap on stall slots (recommend implementing together with the F-1 registry — ONLY if it is ~1 line with the chosen design, otherwise leave as follow-up); F-3 thundering herd on release (jitter / single shared fetch per media id); F-4 remainder: default_stall_ms/max_stall_ms are compile-time config only, admin-UI max_stall_ms (bounded 1ms-1h) is never read by the handler — note it, lower the admin bound only if trivial.
