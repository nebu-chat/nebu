The rest is retained with a reason. Column-level residuals on retained tables: INFO-4. All 13 erased tables have a `user_id` column, so the interpolated `DELETE FROM #{table} WHERE user_id = $1` is valid for each.
- Atomicity / D14 (focus 2): `unwrap_transaction({:ok, {:error, r}})` is right for real Ecto (a returned `{:error, _}` commits and is wrapped). The one non-aborting business error (`:conflict` from `mark_in_progress`, zero rows) wrote nothing, so committing it is harmless, and the loser gets `:conflict` with no success audit. A failing statement aborts the PG transaction, the Ecto commit then fails and the result is `{:error, :rollback}`: the in-progress marker is rolled back and the attempted audit is written. The moduledoc correction is right.
- Lock order (focus 3): erasure order is `users` row (step 2), `user_keys` rows, `uia_sessions` rows, `cross_signing_keys` row, advisory `sync_global|`, deleted rows, `profiles`, `users`. Against `replace_with_approval/7` (uia, cs row, advisory) and the first-upload path (cs row, advisory) the order is the same: no cycle. `AccountDataStore.put/3` takes only the advisory lock and its INSERT touches only `account_data`, which the erasure locks only after the advisory lock: no cycle. The D5 persist holds nothing before `FOR SHARE users`, and nothing in the erasure waits for a `sync_tokens` / cursor lock: no cycle. Device-key writers are autocommit single statements. FK checks take `FOR KEY SHARE`, which the non-key `UPDATE users` does not conflict with (neither UPDATE touches a key column). Remaining candidates: MINOR-1, INFO-1.
- D10 forms (focus 4): the `SELECT ... WHERE NOT EXISTS (...)` filter runs before the conflict handling, so zero source rows means no INSERT and no UPDATE branch: an `ON CONFLICT DO UPDATE` cannot slip past the guard. `num_rows` is 1 for insert or update and 0 only when refused. The qual is pseudo-constant (no Vars of the query level, uncorrelated sublink), so it becomes a one-time filter and `nextval` is not evaluated for refused writes. The explicit casts make parameter typing unambiguous.
- D5 (focus 5): `FOR SHARE` inside the `EXISTS` sublink is valid, the locking clause prevents sublink pull-up, and under READ COMMITTED the blocked statement re-checks `deletion_status IS NULL` on the updated tuple (EPQ), so a racing initial sync writes nothing. The unannotated `$1..$5` in `SELECT $1, $2, ...` type correctly in INSERT ... SELECT. The `:skipped` plumbing is complete (clause order of `write_cursor_rows` is right, the persist answers `:ok`).
- Migration 000055 (focus 6): up is policy-only and idempotent (`DROP POLICY IF EXISTS`, then `CREATE`). The second branch is correlated (`u.user_id = oauth_codes.user_id`): an active user's unexpired code stays undeletable, an uncorrelated-EXISTS widening is not present. The marker is visible only inside the erasure transaction (it never commits as `deletion_in_progress`), so no other session can delete codes through the branch. `users` has no RLS, so the policy subquery sees the row. Down restores the 000041 text. `CREATE POLICY` takes ShareUpdateExclusive (blocks DDL, not DML), consistent with the release note. Rollback hazard: MINOR-5.
- D12 (focus 7): `guarded/2` wraps the new step (rescue + exit); the warning carries only the reason atom (`:unavailable`).
- Sweep (focus 8): idempotent, limited to `deletion_status = 'keys_deleted'`, profile anonymisation and `devices` included, identical text in 07 and the runbook. Live-system notes: INFO-3.
- Log law (focus 9): the only new log line is the D12 warning (reason atom). No new log carries ids' content, keys, tokens or account data. The refused-write log is `error_kind(reason)` = `"user_erased"` only.

## MINOR

### MINOR-1: `cross_signing_keys` has a third writer that D10 and the lock protocol do not cover
`server/lib/nebu/matrix/cross_signing_key_store.ex:254-282` `put_keys_no_flag/2` (reached from `merge_signatures/3` -> `persist_single/3`, i.e. `POST /keys/signatures/upload`, `protected.ex:3175-3184`) is a plain `INSERT ... VALUES ... ON CONFLICT (user_id) DO UPDATE`, autocommit, no `sync_global|` lock and no `deletion_status` predicate. The target `user_id` of a signature upload is the SIGNED user (any authenticated user can sign another user's master key), so this writer is not limited to "a request of the erased user".
Failure scenario: B uploads a signature for A's master key while A's erasure runs. `merge_signatures` reads A's keys (row present), the erasure commits (row deleted), `persist_single` re-reads (all nil) and the INSERT branch re-creates A's `cross_signing_keys` row with the one merged key object and NULLs for the rest. A peer's `/keys/query` then serves a cross-signing key of an erased user again, the state D1 removes. The window is milliseconds, but it does not depend on A's token being dead, and the docs claim the stores refuse ("those two writers refuse a user whose deletion_status is set" in 08-concepts; the same in 07).
Fix: give `put_keys_no_flag/2` the same `SELECT ... WHERE NOT EXISTS (users ... deletion_status IS NOT NULL)` form (zero rows treated as `:not_found`; note the current `{:ok, _} =` match would raise MatchError on any error), or take the advisory lock in the same order; at minimum list it in limitation (f).

### MINOR-2: the D10 refusal is a permanent condition answered as `500 M_UNKNOWN` with an error-level log
`protected.ex:1010-1018` (global account data PUT), `:2895-2900` (first upload), `:3026-3032` (reset replacement): `{:error, :user_erased}` falls into the generic `{:error, reason}` branch: `Logger.error("... write failed: user_erased")` and `500 M_UNKNOWN "... please try again."`. The condition is permanent, Matrix clients treat 5xx as retryable (Element retries account-data PUTs) and every retry adds an ERROR line. The dev report documents the mapping (section 2) and the privacy side is fine (kind only), but the status class is wrong for a permanent refusal (the deactivated-account path answers 403 `M_USER_DEACTIVATED`). The window is small (the token dies with the teardown), so MINOR. Fix: map `:user_erased` to 403 `M_USER_DEACTIVATED` (or `M_FORBIDDEN`), no error log for it; add the three handler cases to the late-writes test (pre-dev INFO-4 noted the mapping is untested).

### MINOR-3: the erasure does not make the account unusable, and a normal request path undoes the profile anonymisation
Nothing outside the new stores reads `deletion_status` (grep over `server/lib`); `delete_user_keys` does not set `is_active = false`, and `TokenValidator.validate/4` blocks only `is_active = false`. Consequences, all in existing Elixir paths:
- `OidcPlug.do_provision` (`oidc_plug.ex:268`, once per 60 s ETS window) and `provision_and_respond` (`http_public.ex:488`, every login) call `Profile.DB.upsert_profile(user_id, display_name_from_IdP_claim, nil)`; the SQL is `displayname = COALESCE(EXCLUDED.displayname, profiles.displayname)` (`profile/db.ex:5-10`), which overwrites `'Deleted User'` with the IdP name.
- The post-commit teardown ends sessions with a device and kills JWTs bound to a device. An unbound raw IdP JWT (`cj` (c): "requests without a device id") has nothing to kill and keeps working until its own `exp`.
Failure scenario: an operator runs `DeleteUserKeys` (the only entry; `cn`: no route) for a user who is not deactivated, or the runbook order is not followed. The user's client keeps its raw IdP JWT (or logs in again: the IdP account still exists); within 60 s the profile shows the real name again, device keys / read receipts are written again, and the story's D4 "nothing is served afterwards" and the doc claim in 08-concepts limitation (f) ("The tokens are dead afterwards (the window is one request)") are false. D5 / D10 then leave that account half-broken (every `/sync` an initial sync, 500 on account-data PUT).
This is a documented operator prerequisite today (follow-ups I-1 / I-5: "deactivate before erasing"; runbook step 4), so it is not MAJOR, but the story's own doc text over-claims. Options for the orchestrator (owner decision): (a) set `is_active = false` in the erasure transaction, (b) refuse the erasure while `is_active` is true, or (c) enforce `deletion_status IS NOT NULL` in `TokenValidator` / `provision`; in every case state the prerequisite in 08-concepts and the 07 release note and correct (f).

### MINOR-4: every failing new statement ends as `:rollback` with no log, and the two main target tables have no explicit grant
`user_deletion.ex:253-261` / `:267-275` return the Postgrex error, but a failing statement aborts the PG transaction and Ecto's commit then fails, so the audit row, the `Logger.error(reason: inspect(reason))` of `server.ex:4086` and the `500` message all say only `:rollback` (the dev report notes this as pre-existing, section 8). With 14 new statements that can fail for structural reasons (permission denied, RLS, a trigger), a deployment where one DELETE fails is undiagnosable from the logs. Concrete candidate: migrations 000014 (`cross_signing_keys`) and 000015 (`account_data`) carry no `GRANT` (000001's blanket grant predates them; `migrations_grant_test.exs` documents that managed PostgreSQL has no `ALTER DEFAULT PRIVILEGES`). INSERT / UPDATE evidently work there, so a grant exists in practice, but this story adds the first runtime DELETE on both, and the real-DB tests run in the docker setup where default privileges compensate. Fix: in the `reduce_while` error branch log the table name and the SQLSTATE (`%Postgrex.Error{postgres: %{code: c}}`), never row data; add a DELETE-grant check to the verification list of the 07 release note.

### MINOR-5: new code on the old policy erases "successfully" and leaves `oauth_codes` rows, silently
Under FORCE RLS a row the policy hides is not an error: with the 000041 policy `DELETE FROM oauth_codes WHERE user_id = $1` deletes 0 rows of an unexpired code and returns `{:ok, ...}`. Cases: migration 000055 rolled back while the code stays (the release note warns of it), or the migrate step skipped. Scenario: the erasure commits, writes the success audit, and the user's `idp_rt_enc` ciphertexts (IdP refresh token) stay for up to 24 h + TTL; the operator's verification query would show them, but the audit says success. Fix (cheap): after the DELETE of `oauth_codes`, run `SELECT count(*) FROM oauth_codes WHERE user_id = $1` (the SELECT policy is `true`) and fail the step (transaction aborts, attempted audit) when it is not 0. The same post-check is a one-line guard for any future FORCE-RLS table added to `erased_tables`.

### MINOR-6: `read_receipts` is deleted by an unindexed `user_id` scan inside the lock-holding transaction
`read_receipts` PK is `(room_id, user_id, receipt_type)` and no migration adds a `user_id` index (grep over all migrations). The other erased tables have a user index or a user-leading PK (`auto_join_opt_outs`, `device_*`, `forgotten_rooms`, `account_data`, `cross_signing_keys`, `user_room_account_data`, `oauth_consent_requests`, `oauth_account_sessions`); `uia_sessions` and `oauth_codes` have none but are TTL-bounded. `DELETE FROM read_receipts WHERE user_id = $1` is a full scan of a table that grows with users x rooms, run while the transaction holds the `users` row, the uia / cross-signing rows and the advisory lock (the user's initial syncs and writers queue behind it) and under the default 15 s query timeout (nothing in `server/config/*.exs` overrides it). D6 explicitly asked the dev agent to consider an index for a per-user DELETE on a large table; the dev report is silent. Fix: either a `CREATE INDEX CONCURRENTLY IF NOT EXISTS ... ON read_receipts (user_id)` migration, or a documented "measured / accepted" line in the story and the release note.

### MINOR-7: `ck` closing text deviates from the follow-ups.md convention
Row `ck` uses `... ORIGINAL TEXT: **GDPR erasure leaves ...**`. The file's convention is `Original item:` (43 rows; `Original text:` 3; `ORIGINAL TEXT:` only this row), and D6 asks for "the usual `**CLOSED by story ... (date)**` format". `user_deletion_docs_test.exs:126-127` pins only the opening and the `closed` status, so the drift is not caught. Fix: `Original item:` (no test change needed).

### MINOR-8: docs describe the step / lock order differently from the code
`06-runtime.md` (erasure paragraph): "`deletion_in_progress`, the per-user `sync_global` lock, the private keys set to NULL, ..." but the code does the key UPDATEs first and takes the lock (after the two row pre-locks) later. `08-concepts.md` inventory paragraph: "The transaction first takes the per-user `sync_global` advisory lock ... (it first locks the user's `uia_sessions` and `cross_signing_keys` rows ...)": the two "first" claims contradict each other and neither matches `lock_user_writers/1`, which sits after the key steps. The lock ORDER (rows before the advisory lock) is the load-bearing fact: state it once, correctly, in both places. Limitation (f) wording: see MINOR-3.

## INFO

- **INFO-1: two more theoretical lock cycles, both fail-closed.** (a) The erasure's multi-row `SELECT 1 FROM uia_sessions WHERE user_id = $1 FOR UPDATE` and `Uia.reuse_or_mint/3` (`uia.ex`, multi-row `UPDATE uia_sessions SET consumed = TRUE` in its own row order, serialised only by the `user|device` advisory key, which the erasure does not take) can lock rows in opposite order when a user has two or more pending reset requests: the deadlock detector aborts one; the erasure fails closed (attempted audit, a retry works), the writer gets a 500. The dev's lock analysis names `consume` and `replace_with_approval` only. (b) The operator sweep deletes `cross_signing_keys` before `uia_sessions`, the opposite of `replace_with_approval/7`; reachable only for a user whose token is still alive. Unreachable for authenticated users (the token path provisions the row); acceptable.
