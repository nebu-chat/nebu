## 6. Gaps (ambiguities and findings: the orchestrator decides and adds D-points)

* **G1 (blocks a literal D2): `oauth_codes` cannot be deleted by the runtime role.** Migration 000041 gives `oauth_codes` a FORCE-RLS DELETE policy `expires_at < now() - 24 h` (reuse detection) and a guard trigger that allows only `used_at NULL -> NOT NULL` updates. `DELETE FROM oauth_codes WHERE user_id = $1` therefore deletes 0 rows of a pending code (60 s TTL, carries `idp_rt_enc`) and succeeds silently (verified: with the 000041 policy the reference erasure passes everything except the 4 oauth_codes tests). The story says "DELETE ... preferably NO migration". Options: (a) a migration with a second policy branch `OR EXISTS (SELECT 1 FROM users u WHERE u.user_id = oauth_codes.user_id AND u.deletion_status IS NOT NULL)` (the erasure sets the status in the same transaction BEFORE it deletes): what the reference does (migration `000055_oauth_codes_erasure_delete`, 8 lines, policy only, down restores 000041; the throwaway test DB must be recreated, `docker rm -fv nebu-oauth-pg`); (b) mark the code used (`UPDATE ... SET used_at = now()`, the only legal update): not redeemable, but the `idp_rt_enc` ciphertext stays up to 24 h 1 min, no physical deletion. Pinned: row gone + not redeemable + policy not widened, in tests that are separate from the other tables (`Scenario 2 - oauth_codes`, one rollback test in the loop of S5, `oauth_codes` in `expected_erased/0`). If (b) is chosen, amend those tests (keep "not redeemable"). The release note then says "migration 000055" (the docs test accepts `no migration` or `migration 0000NN`).
* **G2 (story premise wrong for legacy devices): the `devices` rows of LEGACY devices survive the erasure.** `Nebu.Matrix.oauth_end_user_sessions/1` ends only `auth_api = 'oauth'` devices ("Legacy rows and devices are NOT touched here"); the dispatcher teardown deletes legacy `matrix_sessions`, `sessions`, `sync_tokens` but not the `devices` row, which holds `display_name`, `last_seen_ip`, `last_seen_ts` (personal data, an IP address). Pinned: exactly one `{:ok,_}` + one `{:error, :conflict}` + one success audit row under a deterministic race (both erasures queued on a `FOR UPDATE` lock of the `users` row). Fix (reference): unwrap `{:ok, {:error, reason}}` before the case; `repo().rollback/1` is not usable (no fake has it).
