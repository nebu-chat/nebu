Checked and held up:

- **throw / catch around `repo().transaction/1`.** The `step/2` throw leaves the transaction function; DBConnection (under Ecto) rolls the transaction back and re-raises the throw with the original kind, so the `catch :throw, {:erasure_step_failed, ...}` sees it after the rollback (generated real-DB tests per table prove the rollback and the retry). The clause matches only the private tuple, any other throw / raise propagates as before. `mark_in_progress/1` is deliberately not a step for its business answer: `{:ok, %{rows: []}}` returns `{:error, :conflict}` normally, the transaction commits (nothing written), Ecto answers `{:ok, {:error, :conflict}}`, `unwrap_transaction/1` turns it into `{:error, :conflict}`, no success audit, no attempted audit: D14 holds. A DB error in `mark_in_progress` goes through `step(:mark_in_progress, ...)` and is named. Fakes without `rollback/1` work because the catch is outside the fake transaction. The two result shapes after unwrap (`{:error, {:step_failed, s, r}}` and a bare `{:error, :rollback}` from a failed commit) are both handled; the second path audits with a nil step.
- **`safe_reason/1`.** `%{postgres: %{code: atom}}` -> `{:db_error, code}`, atoms pass, everything else is `:unknown_error`: no struct, statement or row value reaches the audit `error` field, the log, the returned error or the dispatcher's raised message (which inspects the reason). ## MINOR

### MINOR-1: `put_keys_no_flag` takes the new lock but still builds its merge base outside it
`server/lib/nebu/matrix/cross_signing_key_store.ex` (`merge_signatures/3` -> `persist_single/3` -> `put_keys_no_flag/2`): `persist_single` calls `get_keys(user_id)` (plain read, no lock), merges the one key object, then `put_keys_no_flag` opens the transaction, locks the row + advisory lock and writes ALL THREE columns from that stale base. The new comment and the docs say the writer "takes the same protocol as put_keys/2", but the protocol's purpose (the merge base is read under the lock, as `get_keys_for_update` does in the upload handlers) is not met.
Failure scenario (pre-existing, not introduced here, but the new lock makes it look closed): B uploads a signature for A's master key; between B's `get_keys(A)` and the locked write, A completes a cross-signing reset (`replace_with_approval` commits new master / self-signing keys). B's write then restores A's OLD keys in the two untouched columns (and the old master with the new signature merged). A's published identity silently reverts. Window is milliseconds, needs two racing requests.
Fix (cheap): inside the new transaction, after `FOR UPDATE` and the advisory lock, read the row (`SELECT master_key_json, ...` of the locked row, i.e. `get_keys_for_update/1`'s query), merge there, write; or at least say in the comment that the base read is unlocked. Also covers `cq (g)`-class cleanups.

### MINOR-2: the id-line construction satisfies the pinning suites with prose, and the line is now partly stale
`docs/stories/oauth-broker/follow-ups.md` (id line, line 41): the dev took `gm` and `gn` (rows 525 / 526 are correct and unique) and rewrote the tail to `unused: \`go\` onward (... so that the id line keeps its \`gm\` onward pins; \`gm\` and \`gn\`, formerly unused, are the two rows after \`cn\` ...)`. Consequences:
- The eleven suites that pin `unused:[^.]*\`gm\` onward` now pass only because the quoted phrase "`gm` onward" survives inside the explanatory parenthetical (and the clause had to be placed before the `cj, ck, cl and cm` clause to dodge a refute pattern). The pins no longer assert what they were written for (that `gm` onward is unused); they are satisfied by sentence structure.
- The sentence "so that the id line keeps its `gm` onward pins" (about `bz`, `be`, `bp`) is now misleading: the line says `go` onward. The used-ids enumeration (`... \`gj\`-\`gl\`: history-visibility-enforcement`) was not extended to `gm`-`gn`; they appear only in the "formerly unused" list.
- Information is correct (nothing is lost or wrong: `go` onward is unused, `gm`/`gn` are used, `cn` retained), so the result is honest but brittle: the next story that needs an id will edit this clause and break the same suites again.
Fix: update the pins in one pass (they are all the same regex family, e.g. `unused:[^.]*\`go\` onward` or "next free id" semantics) and write the line plainly (`gm`-`gn` in the used list, `go` onward unused); if the owner prefers not to touch eleven suites now, record that in the story as a known follow-up and drop the misleading "keeps its `gm` onward pins" wording.
