## 8. Not done / residuals / things the orchestrator should know

* **Admin reactivation is not blocked at the admin API**, only at the gates (as D17 specifies): `Nebu.Admin.DB.set_is_active(erased, true)` still writes `is_active = true`, and the admin UI shows such a user as active while no gate lets it in. A guard in `set_is_active/2` (or a refusal in `reactivate_user`) would be a small follow-up; the row is not recorded because no follow-up id is left beyond `go` (and it is cosmetic given the gates).
* **60 s provisioning cache (OidcPlug, node-local ETS)**: a bearer that a node already confirmed stays accepted until that entry expires, also after the erasure; same bound as the admin deactivation, now stated in 07 / 08. Not evicted on the erasing node (the cache table is private to the plug).
* Not NULLed (not in D16): `users.last_seen_at`, `users.personal_room_id`, `users.deactivation_reason` (listed as column residuals in the 08 `users` line; Kassandra INFO-1 suggested NULLing `last_seen_at` / `deactivation_reason`, say if wanted).
* `invite_db.ex` (the pending-invite rate counter that excludes rows of a deactivated inviter) was deliberately NOT changed: it is an abuse counter, not an authentication gate (I reverted a first edit).
* Behaviour change noted for the release: a persist or profile upsert for a user id WITHOUT a `users` row used to fail with a foreign key error and now writes nothing and answers `:ok` (D5 persist since cycle 0, `upsert_profile` now).
* The reset replacement HTTP path of D18 (c) has no HTTP test (section 5).
* `FOR SHARE` on `users` now also happens on every `upsert_profile` (login, once per 60 s per user per node by the provisioning cache): a row write on the `users` page, stated in the 07 note.
* Staged tests were not run on Elixir 1.20 for the unit job this cycle (1.19 as requested; the quick runs used 1.20 for the integration suite).
