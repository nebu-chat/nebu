## Decisions / how D1-D11 are realised

- **D1/D2:** the key comes only from `conn.assigns[:device_id]` (set by `OidcPlug` from the session / binding). All lookups and upserts of a request use one key (verified by the dispatcher spy tests). Device-bound requests never read/write `''` and never clear a flag.
- **D4:** one token upsert per request, real anchor; nil only for a user without any delivered event (as clarified in D10 of the story).
- **D9 race safety:** writers lock `sync_global|<user>` (namespaced: does NOT serialise with room account data, test-pinned) before drawing `nextval` in both upsert branches, so per user the position order == commit order. Two columns, each advanced only to the max read from its own source; `GREATEST` + `since_token = <this response's core token>`, never an INSERT (no orphan from the advance). Positions are read once before the core call; failure direction is always "deliver again".
- **D10:** fallback to a request with a `since` lists the own user (device-bound and device-less); real initial sync lists nobody; never `left`.
- **D11:** wake after commit, cluster-wide `:pg.get_members/1`; pre-check zeroes `timeout_ms` for device-bound requests with a since. Device-less requests are woken but get no pre-check.
- `put_keys/2` is called inside the callers' transactions (`FOR UPDATE` read first): the nested `Repo.transaction` joins the outer one, so the advisory lock is held until the OUTER commit (position order still == commit order). Lock order there is row lock -> advisory lock; the account data writer only takes the advisory lock, so no lock cycle.

## Deviations from the reference diff (hint only)

1. `AccountDataStore.put/3` and `CrossSigningKeyStore.put_keys/2` return `{:error, reason}` instead of raising (`raise "...#{inspect(reason)}"` in the reference would also have put a Postgrex error, which can quote values, into a crash report). The PUT route maps it to `500 M_UNKNOWN`; the two `put_keys` callers roll back explicitly. The store test accepts both ("refute outcome == :ok").
2. The token write is factored into one `persist_token/4` in the dispatcher (used by initial and incremental path) instead of an inline `case` in `initial_sync/2`.
3. Route: the device key and positions are passed as one `{device_id, positions}` tuple; the device-bound clause pattern-matches it (no `not is_nil(positions)` guard needed). `list_since` guard requires `pos >= 0`.
4. Extra docs consistency in `08-concepts.md` / `05-building-blocks.md`.

## Open concerns for the reviewer

1. **Initial-shaped answer with a failed `list_since` read.** `list_since(user, 0)` failing yields `{0, []}`; the advance target is `max(0, ad_pos)` (GREATEST cannot lower a column), so after a no-since initial sync whose account data read failed, the next delta delivers only rows above the OLD `account_data_pos`: a client that reset its cache would miss older rows until it changes them or does another initial sync. Pre-existing equivalent: `list_all_and_clear/1` failing returned `[]` as well. A full fix would need a "reset to the read value" (no GREATEST) on initial-shaped answers only when the read succeeded; not done (it reopens the race the GREATEST guards). Low.
2. **Wake-up send from the request process** (`notify_sync/1` uses plain `send/2` to remote pids): same exposure as follow-up `bz` (a busy/dead distribution link can suspend the PUT request). Not addressed here.
3. **`put_keys/2` inside the outer transactions** holds the `sync_global|` lock until the outer commit (UIA consume + FOR UPDATE read). A concurrent global account data PUT of the same user waits for it (milliseconds). Intended (commit order), but worth a look.
4. **D11 pre-check costs one extra statement per device-bound `/sync` with a since** (included in the pinned +3); `pending_since?` uses the new index.
5. **Statement counts**: no re-pin was needed (initial 48 / 57, incremental 51 measured as pinned by the ATDD step).
6. **Security**: no token, credential or account data content is logged (the new log line is the error KIND only; `Nebu.Repo.QueryTelemetry` never logs params). The since token is only compared / used as a `WHERE` guard. Positions live in the server-side row (a forged `.<pos>` suffix cannot suppress global account data: test green). Follow-up `ck` (GDPR erasure of `account_data` / `cross_signing_keys`) is untouched and pre-existing.
