# Full Playwright e2e run (2026-10-15), isolated stack, HEAD ce0a27fe (+ the e2e fixes below)

Setup: compose project `nebu-oauth` without host ports (docker-compose.oauth.yml), a gateway container in its network that forwards localhost:8008 / 4000 / 5556 / 7070 to the services, Playwright 1.59 (mcr.microsoft.com/playwright:v1.59.0-jammy) in the gateway's network namespace, psql through NEBU_DB_URL. The dev stack `nebu-oauth-dev` was not touched. Fresh volumes.
Result of the whole suite (admin-ui + element-web, default tags): 133 passed, 76 failed, 7 skipped (1.0 h). Logs: e2e-full-current.log.
New scenarios of this run's stories PASS against the real Dex: role mapping (3: claim path shown, value not in the token refused, own group saved), media policy save through the fresh sign-in (1); the sampled gated forms pass with real Chromium clicks (archive / unarchive, auto-join toggle room + space, room visibility, create room, spaces, SSO schemes / origins, claim mapping, OIDC refresh mode, OAuth switch).
The 76 failures, by cause:
 * 42 need an OAuth-enabled HTTPS stack (`oauth_enabled` is false by default, the issuer must be https: `make dev-tls-oauth-on`): oauth-account-management 17, oauth-consent 9, legacy-sso-redirect-confirmation 8, oauth-authorize 5, oauth-client-approvals / revocation 3 ("OAuth 2.0 is not supported by this server"). Not runnable in the plain-http isolated stack.
 * 34 need the Matrix users alex / marie / kai: Element's login helper fails in this stack with "Unable to set up keys" (the server answers `POST /_matrix/client/v3/room_keys/version` with 405: key backup is not implemented), so the users are never provisioned and every test that invites / lists / manages them fails (element-web 18; admin add-user-autocomplete 5, device-management 3, member_management 2, users 1, create_room 1, war-room placeholder 1, media overview 2).
BASELINE COMPARISON: the same 16 admin-ui failures (add-user-autocomplete 5, admin-media-overview 2, create_room 1, device-management 3, member_management 2, sso_redirect_origins 1, users 1, war-room 1) and the Element key-setup error occur identically on the commit before this run's stories (b91676a8, e2e-baseline-admin-comparison.log, e2e-baseline-element-smoke.log): no regression from dg / dh / de.
Real regressions in step definitions found and fixed: (1) the full `bddgen` failed since the media story (two step definitions `the operator clicks {string}`, a whole-suite blocker, pre-existing) -> the media overview step is named `the operator clicks the {string} button without a page reload`; (2) `sso_redirect_origins` "A wildcard origin is refused" matched two role=alert elements since the UX N10 inline error (strict mode violation, also on the baseline) -> `.first()`; verified green afterwards.
NOT exercised end to end (environment): delete device, rename device, add / remove member, add-user autocomplete with real users (their forms use the same click_gate as the passing ones; unit tests and the route enumeration cover them); the storage target and test connection forms (no e2e); everything behind OAuth.
