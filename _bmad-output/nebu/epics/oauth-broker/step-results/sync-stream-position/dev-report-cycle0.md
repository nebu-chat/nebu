## 2. Design decisions and deviations from the reference

1. **The persist is TWO statements in one transaction, not 3 / 4 (deviation, deliberate).**
   - Delta: ONE guarded `UPDATE sync_tokens ... WHERE user_id = $1 AND device_id = $2 AND (since_token = $base OR prev_since_token = $base) RETURNING generation`. The UPDATE takes the row lock itself; after a concurrent writer committed, READ COMMITTED re-checks the WHERE on the new row version (EvalPlanQual), so it is the D7 guard without a separate `SELECT ... FOR UPDATE` round trip and with a shorter lock hold. `SET` reads the pre-update row, so `prev_account_data_pos` / `prev_cross_signing_pos` := `CASE WHEN since_token = $base THEN account_data_pos ELSE prev_account_data_pos END` (the positions of exactly the base generation). 0 rows (base replaced, or the device row deleted meanwhile) = `:stale`, nothing written, never an INSERT (D20 (4)).
   - Initial / fallback: the unconditional token upsert (generation 1, prev NULL, `stream_version` 1; the two delivery positions untouched, the HTTP layer advances / rewinds them as before).
   - Both modes then run ONE cursor statement: `WITH dropped AS (DELETE ... AND NOT (room_id = ANY(keep))) INSERT ... SELECT FROM unnest(...) ON CONFLICT DO UPDATE`. The two parts touch disjoint rows (every written room is in `keep`), a data-modifying CTE always runs to completion. For an initial sync `keep` = the room ids of the new rows (the device's rows become exactly `rows`, prev NULL, gen 1). D12 "one bulk statement regardless of the room count" holds.
   - The D7 concurrency tests (lock held by `SELECT ... FOR UPDATE` on a second connection) pass unchanged: the UPDATE waits on the same row lock. Their moduledoc says the store's function names are not pinned, only the lock.
2. **`:stale` / failure handling.** `persist_position!/3`: `:ok` and `:stale` send the response (a `:stale` logs one value-free DEBUG line); `{:error, _}` (also a store without the function) is a value-free ERROR line and the handled `503 M_UNAVAILABLE` (D20 (5), D21 (1)): nothing written, the old token stays valid.
3. **Cursor values (D3 / D8 / D13), one rule for every class.** For every partition room with a head the value after this response is: joined and resolved -> `{head, "join"}`; a NEW invite / leave -> `{head, class, marker}`; anything else (a not-new invite / leave, an unresolved joined room) -> its BASE value. A row is written when it is new, its value differs from the stored one, or (only for a request with the PREVIOUS token) its `gen == generation` (D20 (1) re-base). `keep` = the rooms with a value, so a room that left the partition, or whose base is absent (only possible for a previous-token request whose lost generation created the row), loses its row. **Deviation from the reference:** the reference kept the STORED (current) value for unresolved joined rooms and for not-new invites / leaves, also for a previous-token request; for a retry whose lost generation advanced such a room (e.g. an unresolved room on the retry), that writes the lost response's position as the new base and loses that room's events of the lost response. With the base value both requests (current: base == stored, no write) and retries are correct. Not covered by a staged test (the cases need an unresolvable room on a retry); noted for the reviewers.
4. **`moves_cursors?`** (renamed from `moves_anchor?`, a field of the delivery map): the partition re-read of `consistent_delivery/4` runs when the delivery delivers rooms, writes ANY cursor row, or has a new invite / leave (reference: only when a joined room's `pos` changed; mine also re-checks a class change without events). The 503 / rebuild logic is unchanged (D13 comment updated: the security reason stays, the global-anchor reason is moot).
5. **Base selection** (`base_generation/2`): `s2_` prefix pattern in the function head, `stream_version` must be 1 (`Map.get` default 0: a fake / old row without the key is the timestamp era = fallback), then current, then previous (only when `prev_since_token` is a binary). The row is looked up by the AUTHENTICATED key only (unchanged), so B presenting A's tokens or a forged `s2_` never matches.
6. **No `room_heads` statement for an empty partition** (`room_heads!/3` returns `%{}` without a call): C-6, the un-amended fake suites (`sync_wakeups_cluster_test`, session) have no `room_heads/3`; with this they stay green unamended.
7. **Range read through `viewer_read/3`** with a fallback that answers `{:error, :viewer_read_unavailable}`: a db module without `fetch_visible_events_in_range/5` is the 503 (no unfiltered fallback, the AC11 call-graph and "real module never falls back" pins hold). `room_heads/3` and `leave_window_events/5` go through `partition_read!/2` (`rooms_db_module`), the range read through `messages_db_module` (as the reference / the spy expects).
8. **Initial page bound:** `visible_page!/6` passes the head only when the db module exports `fetch_visible_events/6` (the real one always does); a TEST module with only `/5` gets the unbounded read.
9. **`last_event_id`** stays written (informational, D6): the newest delivered event of the response, or the row's previous value when nothing was delivered (so an OLD node in a mixed-version window still finds a sane anchor). Never read by the new code.
10. **`pagination_token/1`** instead of the reference's `@doc false event_token/1`: a documented public helper of `Room.DB` (pure, no DB access, so the fake-DB suites can call it).
11. **Leave window** P position: `Map.get(previous, :room_pos) || 0` (a legacy P without a position is never prepended against a base and bounds nothing; the clock bounds still apply).

The design-independent pins in `sync_stream_position_http_test.exs` (cursor statements independent of the room count, one range read per moved room) pass.

## 6. Notes for Kassandra (D18)

- Token: `s2_` + `Base.url_encode64(:crypto.strong_rand_bytes(16), padding: false)` (128 bit, no user id / event id / position). Compared only with the row of the AUTHENTICATED key (`get_since_token(user, device)` / `(user)` for the device-less key): B presenting A's current or previous token, a forged `s2_`, an old-format token, a `stream_version 0` row are all `:none` -> the initial-shaped fallback, which writes only B's own token row and B's own cursor rows (initial mode: delete + upsert by `(user_id, device_id)` of the caller). Every other row byte-identical (pinned by the HTTP tests).
- Cursors are read (`room_heads/3`: `c.user_id = $2 AND c.device_id = $3`) and written (`persist_sync_position/3`: every statement keyed by `$1`/`$2` = the caller's key) ONLY by the authenticated key; no request input reaches a cursor except the opaque token, which only selects current / previous of the caller's own row.
- A cursor row only selects positions of the caller's own partition rooms; every event read is still the history-visibility fragment (range read: `@sql_hv_visible` per row), the leave window is bounded by positions strictly below L and additionally by the member row clocks (only shrink).
- Fail closed: unreadable token columns / persist failure = 503, nothing written (one transaction; the failure-direction test hides `account_data_pos` / `cross_signing_pos` and gets the 503, token row byte-identical). A db module without the position reads = 503 (`partition_read!` / `viewer_read` without fallback).
- Logs: no token, no cursor value, no room / user id in the new lines (`:stale` DEBUG line and the persist ERROR line carry only the error class; the unresolved WARNING carries a count). The log test of the HTTP suite passes.
- No new process state, no node-local state; wake-ups unchanged (`:pg.get_members/1`). OIDC scopes untouched.
