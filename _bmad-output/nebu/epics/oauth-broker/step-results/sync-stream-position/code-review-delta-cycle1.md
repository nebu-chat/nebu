## Verification of the fixes

### (1) MAJOR-1: generation compare-and-set - CORRECT and COMPLETE
- SQL (`postgres.ex:64-82`): `... AND ($7::bigint IS NULL OR generation = $7::bigint)`; `$1..$7` match the 7-element `params` list in `write_token_row/4` (`:283`, `Map.get(spec, :expected_generation)`); the `$7` is cast once, Postgrex encodes nil as NULL. `RETURNING generation` still returns the NEW generation, so the cursor rows' `gen` stays consistent.
- Sequential previous-token retry (D8): `ctx.generation` is `Map.get(row, :generation, 0)` of the row read at the start of the request (`server.ex` `sync_delta/2`), i.e. the generation CURRENT at that moment, also for a `:previous` base. `cursor_base/2` compares `cursor.gen == ctx.generation` with the same value, and the CAS expects the same value, so a retry (R_a committed g+1 earlier, the retry reads g+1, writes g+1 -> g+2) passes. D20(1) re-base interplay unchanged (`write_cursor?/3` uses `ctx.generation` the same way).
- Long-poll / wake rebuilds: `ctx` is fixed for the request, the token row's generation changes only through `persist_sync_position/3` (initial mode resets to 1, delta increments); `advance_positions` / `rewind_account_data_position` / `touch` do not touch `generation`. Wake-up rebuilds of a single client therefore never become `:stale`. Only a second request of the same key that commits first does (the intended case), including the "client already moved on to T1 while the old T request is still alive" case: the old request is stale, its response is unused anyway.
- Production paths without the key: only `do_incremental_sync/3` builds a `:delta` spec and it always sets `expected_generation: ctx.generation` (`server.ex:6123`); `:initial` mode ignores it (`write_token_row/4` initial clause). A key-less spec (callers of the first contract, the fakes) is token-guarded only; `SyncPositionsFake.Store.persist/4` mirrors this (`moderation_test_support.exs:637-638`). Safe.
- Initial-mode generation reset to 1 cannot produce an ABA for the CAS: the token guard (`since_token = $3 OR prev_since_token = $3`) still fails for any token issued before the reset (prev is NULLed, current replaced).
- Rewritten concurrency test (`sync_stream_position_concurrency_test.exs:~318-366`): the sequence is forced (R2 waiting in `wait_loop`, R1 delivers and commits via a direct insert without a wake-up, then `say!` wakes R2), assertions are exact (`valid == [r1]`, both events across the stored token's response + next sync, R2's token is the one-time fallback). Deterministic as far as I can judge; the mutation check in the dev report (nil generation kills it) is the right evidence.

### (2) `base == nil` clause in `delta_events!/4` - CORRECT
- `limited` = `next_batch != ""` is `page_answer/3`'s `length(all) > limit` (the page reads `limit + 1`), the same threshold as the range read (`> 20`); `prev_batch` is still computed by `fetch_delta_rooms/4` as `pagination_token(hd(events))` of the oldest delivered event, which for this ts-ordered page is exactly the `/messages` order (better than for the range read).
- No loss between head bound and cursor: the page is bounded by `room_pos <= head OR room_pos IS NULL` with the head read in the same `room_heads` statement as the cursor; the cursor value written is that same `head`; an event committed after the read has a higher position and arrives with the next delta (base = head). Rooms with more visible events than 20 are `limited` and the gap is reachable via `prev_batch`.
- `failure: :unavailable` routes a failed read to `history_read_failed!(..., :unavailable)` = the 503 of the delta (nothing persisted); `{:error, :not_found}` is unreachable for the empty `from_token`.
- Legacy NULL-`room_pos` events are now included for rooms without a base. That is what D9 already says ("for an absent row the visible newest 20, as an initial-sync room") and what an initial sync delivers; I consider it intended. See MINOR-2 for the doc contradiction and INFO-2 for the `head <= 0` asymmetry.
- Statement count unchanged (one read per moved room); the segment-driven page read removes the unbounded filtered scan of Kassandra MEDIUM-1 for the repeatable previous-token case, as claimed.

## INFO

1. **CAS trade-off.** When a client retries while its abandoned request is still alive, whichever of the two commits second is `:stale`; if that is the request the client keeps (typically the retry), the client is forced into one initial-shaped fallback (full payload, no `rooms.leave` in it) instead of continuing. Correct and documented (`cj`); the alternative (b) of my cycle-0 report (re-evaluating current vs previous per build) would avoid the fallback at the cost of a join per build. No action needed unless fallbacks of this kind show up in operation.
2. **`head <= 0` asymmetry.** `delta_events!/4` returns `{[], false}` for any room with head 0 (only legacy events), so a no-base room with only legacy history shows nothing, while with head >= 1 the same room shows its newest 20 including legacy events. Matches the old behaviour for head 0; mention in `cq` (c) if it matters.
3. **Test probe.** The `Process.info(pid, :current_function)` probe on the private `Server.wait_loop/2` is deterministic (the receive lives in that function, private functions are not inlined) but couples the test to the name; a rename makes the test time out with the clear message "R2 is long-polling with the token T". Acceptable, it is commented. Naming trap: `ModerationTestSupport.wait_until/2` takes ATTEMPTS (1 ms sleeps), so `5_000` means roughly 5-10 s, not 5_000 ms.
