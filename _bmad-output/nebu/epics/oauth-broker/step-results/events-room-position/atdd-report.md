## Story gaps / ambiguities with proposed amendments
1. **"the first trigger of the schema" (OQ1 answer) is wrong.** `events_search_vector_trigger` (000001 / 000002, `BEFORE INSERT OR UPDATE OF content ON events`, function `events_search_vector_update`) already exists. Both are BEFORE INSERT row triggers on `events`; they fire alphabetically and touch different columns, so no conflict. The tests pin that the new trigger is a separate BEFORE INSERT-only trigger and that the old one is kept. Amend OQ1: "the second trigger of the schema; the first writes `search_vector`". Where "documented as an exception to ADR-018" must live is not stated: the tests pin the migration header (`ADR-018`, `trigger`); add it to the DoD or to `07-deployment.md`/ADR-018 if the owner wants it elsewhere.
2. **Names are not given** (function, trigger). The tests find the trigger by what it does (`pg_trigger` x `pg_get_functiondef ILIKE '%event_pos%'`) and only pin `events_room_pos_idx` (named by D4). The Scenario 4 stimulus trigger is named `a00_atdd_hold_*` and relies on alphabetical firing order: do not name the position trigger `a00...` or lower.
3. **D5 operator note, optional addition:** after a `CREATE UNIQUE INDEX CONCURRENTLY` that failed midway an INVALID index `events_room_pos_idx` is left behind and `IF NOT EXISTS` then skips it silently. Add "check `pg_index.indisvalid`, drop and retry if false" to the manual path (not pinned by any test: not in the story).
4. **D6 wording:** "bounded by those transactions' own `lock_timeout` (1 s) or their short duration" is true of the HOLDER; the standalone insert itself (the message path, the four direct writers) has NO `lock_timeout`, so it waits as long as the holder (the archive path's `FOR UPDATE`, a `set_power_levels`, a room write transaction). Lock-order inventory (done for this report): the only transactions that insert events are `apply_member_change/4`, `apply_power_levels_change/3`, `apply_redaction/2`, `apply_state_change/3`; each takes the rooms row FIRST (`FOR NO KEY UPDATE` after D2) and inserts LAST, the archive path locks `FOR UPDATE` first: no lock-order inversion found. Worth one line in D6.
5. **Gherkin 2 "the reader never observed N+1 without N"** is pinned as: a single-statement (snapshot) read of the committed positions is always the gapless prefix 1..k. Why it holds: T2's UPDATE can only proceed after T1's commit released the room row lock, and PostgreSQL releases it after T1 is visible to new snapshots. A reader that spans several statements or holds a REPEATABLE READ snapshot is story 2's concern, not tested here.
6. **Gherkin 4 "no deadlock is reported"** needs both transactions past their archived check when they reach the INSERT; the real room process serialises member changes, so the test forces the interleaving with a stimulus trigger (300 ms barrier, below the 1 s `lock_timeout`). Either a deadlock (40P01) or the lock timeout (55P03) is a failure there; any D2 implementation that takes the strong row lock first passes (including `FOR UPDATE`).
7. **Gherkin 5 "fresh schema"** is the migrated test database (as in 000052's tests), "populated" is built inside the rolled-back transaction after a down. The manual pre-create path of D5 is tested with a plain `CREATE UNIQUE INDEX IF NOT EXISTS` (CONCURRENTLY is not available inside a transaction); the documented statements are pinned textually in the header and in `07-deployment.md`.
8. **D3 side effect to know:** a pre-existing room has unstamped events and `event_pos = 0`, so its first new event is position 1 although older events exist; story 2 must read `room_pos IS NOT NULL` ranges only (it does, D4 index is partial). A failed createRoom cleanup (`@sql_delete_events_for_room`) leaves the room row's counter advanced, irrelevant because that room row goes too.
9. **follow-ups.md:** the story names no row to add or close (fc is closed by story 2, which records `cq` (c)); the docs test pins "untouched" by facts (fc open, no mention of this story / migration / columns, id line intact), because a byte-exact check needs git.
10. `insert_event/1` returning `:ok` (D8) is pinned by every `assert :ok = DB.insert_event(..)` and mutant M29.
