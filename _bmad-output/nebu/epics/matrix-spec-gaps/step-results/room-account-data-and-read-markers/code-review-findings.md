Code review (cycle 0): 1 MAJOR, 5 MINOR. Kassandra: CLEAN (0 CRIT/HIGH, 3 MEDIUM, 3 LOW, INFO). Report: docs/stories/matrix-spec-gaps/security-reports/room-account-data-and-read-markers-security-review-2026-10-08.md (read it). The reviews agree on the regression below.

## Fix list (every behavior fix needs a test that is RED before the fix and green after; prove red by running it against the staged lib state first)
1. [Review MAJOR M1 + Kassandra MEDIUM 1 + LOW 4] REGRESSION: `RawBodyReader.account_data_path?/1` (raw_body_reader.ex:28) and the JsonBody `RequestTooLargeError` rescue (json_body.ex ~56-65) trigger on ANY path containing the segment `account_data` (also state_key/txnId/room id `account_data`). For the GLOBAL `PUT /user/{u}/account_data/{type}` a body > 1 MB now sets body_params=%{} + assigns[:body_too_large]; the global handler never checks it, so it stores `{}` with 200 and silently overwrites secret-storage/cross-signing data (before: 413). Fix: (a) match EXACT path shapes with method PUT only: `["_matrix","client",version,"user",_,"account_data",_]` and `[... "user",_,"rooms",_,"account_data",_]` (check the real path_info prefix handling in the router; use a shared helper so RawBodyReader and JsonBody cannot drift); (b) the global PUT handler must evaluate `conn.assigns[:body_too_large]` BEFORE storing → 413 M_TOO_LARGE and leave the old value unchanged; (c) other routes with an `account_data` segment (e.g. PUT /rooms/{r}/send/{type}/account_data, state_key account_data) must keep their previous behavior (413 for >1 MB, never silent empty content). Tests: global PUT >1 MB → 413 + old value unchanged; room PUT >64 KiB → 413; `PUT /rooms/{r}/send/m.room.message/account_data` with >1 MB → 413 (not empty event).
2. [Kassandra MEDIUM 2] No TOTAL size cap per user (1000 rows × 64 KiB ≈ 64 MB; sync with `since=<core>.0` loads+decodes+re-encodes everything; PUT routes unrate-limited). Add a total-bytes cap per user (default 4 MiB, env `NEBU_ROOM_ACCOUNT_DATA_MAX_TOTAL_BYTES`, parsed like the other envs, safe on invalid values) checked under the existing advisory lock (sum of byte_size(content_json) of the user's rows, counting an overwritten row's NEW size minus OLD size); over the cap → 403 M_RESOURCE_LIMIT_EXCEEDED (overwriting that does not increase the total must still work). Also add a per-user rate limit on the account-data PUT routes using the existing RateLimit plug tier mechanism (reasonable default, e.g. 60/min burst 30, documented). Tests for both.
3. [Kassandra MEDIUM 3 + Review m4, Logging-Law] Room/global account-data request AND response bodies are logged verbatim at DEBUG (request_logger.ex ~218-233, 261-270; payload_redactor). Treat the account-data path shapes (global + room) as content: either exclude from payload capture or run with `in_content?: true`; GET response bodies must not be captured. Test with capture_log at :debug that neither the PUT body nor the GET response content appears.
4. [Kassandra LOW 5 + Review m5] `split_since_token/1` (protected.ex ~156-171): bound the position: digits only (reject `+5`, `-1`), at most 19 digits and <= 9_223_372_036_854_775_807 else position 0; if `since_pos > latest` clamp to latest (forged/stale-after-sequence-reset positions must not suppress delivery forever); `"core."`, `"a.b.c"`, empty suffix → define behavior (core = whole token minus a trailing valid numeric suffix only) and document in the code comment. Tests for the edge cases.
5. [Review m3 + Kassandra INFO 8] `read_markers` is not atomic: m.read/m.read.private receipts are written before `store_fully_read` can fail (cap 403 / DB 500), contradicting the "rejected request stores nothing" comment; also server-managed m.fully_read counts against the user's row cap so /read_markers can fail with 403 once the cap is reached. Fix: exempt m.fully_read (server-managed type) from the row cap AND the total-bytes cap (it is tiny and server-written), and run validation/cap checks BEFORE any write; do the m.fully_read store first, receipts after. Test: user at the row cap can still advance read markers; a failing fully_read store writes no receipts.
6. [Review m1] Global PUT with a non-object body (array/scalar → Plug wraps as `%{"_json"=>...}`) is stored with 200: reject with 400 M_BAD_JSON (spec: body must be an object); keep storing objects as before. Test.
7. [Review m2] Percent-decoding inconsistency: global branch calls `URI.decode_www_form` on the type (a `+` → space) while the room routes do not (Plug.Router already decodes path_info). Make both scopes consistent (no extra decoding) and document; test that type `a+b` is stored under the same key in both scopes.
8. [Kassandra LOW 6, advisory] RLS on the new table: matches existing tables, no change required — add one line to the Dev Notes.
9. [Kassandra INFO 7/9/10/11] Document only (Dev Notes): timing difference unknown room (404) vs non-member (403) on /read_markers is inherited from /receipt; wake-up race bounded by long-poll timeout; global account_data not erased on GDPR erasure (own bugfix); MAX_ROWS env beyond 64-bit range → clamp/ignore at parse time (do that, it is trivial).

# Cycle 2 fixes (final) — after code-review cycle 1 (0 MAJOR, 4 MINOR) + Kassandra delta (CLEAN, LOW #12 #13). Tests first (red before green), no runtime behavior outside these items.
1. [Review M1 + Kassandra #13] The account-data path matchers disagree with the router: `RawBodyReader.account_data_shape?/1` and the request logger compare RAW path segments, while Plug.Router matches on `URI.decode`d `path_info` (so `/user/@u/rooms/!r/%61ccount_data/t` is routed to the account-data handler but not recognized by the matcher): room PUT body not cached → 400 M_NOT_JSON; global PUT object check bypassed; body logged at DEBUG. Fix in ONE shared helper used by RawBodyReader, JsonBody and the RequestLogger: derive segments exactly like the router (split on "/", drop EMPTY segments (the logger's `String.split(request_path, "/", trim: true)` keeps middle empties: `/_matrix//client/...`), `URI.decode` each segment, tolerate invalid percent-encoding without raising) and then match the exact shapes. Tests: `%61ccount_data` (room + global), `//` in the path, trailing slash; logger test that content is not logged for these variants.
2. [Review M2 + Kassandra #12] Global `PUT /user/{u}/account_data/{type}` with an EMPTY body, no Content-Type or a non-JSON Content-Type still stores `{}` with 200 (Plug.Parsers skips the body; `global_body_object?/1` falls back to `true`) and skips the 413 check. Make it like the room scope: read the body via `raw_request_body/1` (oversized → 413 M_TOO_LARGE), empty/non-JSON/invalid → 400 M_NOT_JSON, non-object → 400 M_BAD_JSON; objects (also with a `_json` key) are stored as before. Tests: empty body, no content-type, `text/plain`, urlencoded body, oversized non-JSON body (all must leave the old value unchanged). Dev Notes: note the compatibility decision (clients without Content-Type are rejected like Synapse does).
3. [Review M4] `room_account_data_hardening_test.exs` (~270-290): rate-limit test must also neutralize the OS env var `NEBU_RATE_LIMIT_DISABLED` (System.delete_env with restore in on_exit), like matrix_router_test.exs:339-340 does, so it is deterministic under a harness that sets it.
4. [Review INFO I2] Update the `rate_limit.ex` moduledoc ("Per-IP token-bucket"/"IP extraction") to mention the `key: :user` option and the unbounded-but-small ETS bucket growth (one entry per account, ~100 bytes).
