# Session 2026-06-26 — Device-key registration vs E2EE boundary

**Phil's bug:** Element shows "device could not be registered" on login. He wants the full
device/key surface implemented but E2EE must stay OFF (ADR-011 managed model).

## Findings (CS API v1.18)

### Root cause — two stub violations
Current Nebu stubs in `server/lib/nebu/web/router/protected.ex`:
- `POST /keys/upload` → constant `{"one_time_key_counts": {}}`, ignores body.
- `POST /keys/query` → all-empty maps.

Element's post-login crypto sequence: `/keys/upload` (publish device identity keys + OTKs +
fallback) → reconcile OTK count → `/keys/query` for its OWN user to confirm publication.

- **§/keys/query 200 (line 44162-44169):** `device_keys` = `{user_id: {device_id: DeviceInformation}}`,
  and "the information returned will be the same as uploaded via /keys/upload, with the addition
  of an `unsigned` property." Empty `{}` ⇒ Element never sees its own device ⇒ "device could not be
  registered." **Dominant trigger.**
- **§/keys/upload 200 (line 44629-44635):** `one_time_key_counts` is **Required** = "number of
  unclaimed one-time keys of that type currently held on the server for this device." Constant `{}`
  breaks the OlmMachine's OTK reconciliation (it re-uploads forever).
- **§E2E extensions to /sync (line 44681-44688):** `device_one_time_keys_count` (Required if any
  OTKs exist) + `device_unused_fallback_key_types` (**Required**, added v1.2). Missing ⇒ machine
  can't settle.
- **§whoami 200 (line 11981-11988):** `device_id` required when a device is bound to the token
  (only omittable for appservices). Nebu omits it — secondary, should add.

### The E2EE boundary (critical for Phil)
- **§E2E (line 43212-43214):** "In order to enable end-to-end encryption in a room, clients can
  send an `m.room.encryption` state event specifying `m.megolm.v1.aes-sha2`."
- ⇒ **Device-key directory is ORTHOGONAL to encryption.** Storing/echoing device keys + OTK counts
  is just a key directory; it encrypts nothing. E2EE turns on PER ROOM via `m.room.encryption`,
  client-initiated. So the full key surface can be implemented safely as long as no room gets
  `m.room.encryption`.
- Guardrail to enforce ADR-011: optionally **reject** client PUT of `m.room.encryption` (M_FORBIDDEN)
  so a room can never flip to client-side E2EE. Don't auto-add it, don't default createRoom to
  encrypted, don't advertise it in capabilities.
