# Session 2026-10-05 — Oracle Gate: GET /_matrix/client/v1/mutual_rooms (MSC2666, new v1.19)

Reborn from sanctum. Task: Oracle Gate for new bug/feature ticket implementing `mutual_rooms`,
not yet implemented in Nebu at all. Spec anchor `get_matrixclientv1mutual_rooms`, line 61238 of
`matrix-spec/v1.19/client-server-api/index.html`. Section starts at `id="mutual-rooms"` (61233),
"Added in v1.19", server-behaviour note at `id="server-behaviour-30"` (61423).

## Key findings (full detail in the delivered report)
- Response shape confirmed: `count` (Required, integer, TOTAL even when paginated, MAY be
  inaccurate), `joined` (Required, array of room IDs), `next_batch` (optional — "absent if no
  more results", never null/empty string).
- 400 cause list is a SINGLE bucket in the spec's own prose: invalid/expired `from`, missing
  `user_id`, non-compliant `user_id`, or self-referencing `user_id` — all just "400". The ONLY
  example JSON for this endpoint's 400 uses `M_INVALID_PARAM` uniformly. Spec does NOT carve out
  `M_MISSING_PARAM` for the missing-param case specifically for THIS endpoint, even though
  `M_MISSING_PARAM` is a real generic CS errcode elsewhere (line 3607). Flagged as a nuance, not
  a contradiction — AC6/7/8 (M_INVALID_PARAM for missing/malformed/self-id) are CONFIRMED per the
  endpoint's own example, but a project convention of M_MISSING_PARAM-for-missing elsewhere is a
  real tension worth the team knowing about.
- **Important cross-cutting spec fact (not previously in MEMORY.md)**: `retry_after_ms` was
  **deprecated in v1.10** in favor of the `Retry-After` HTTP header (§Rate limiting, line
  3643-3657). It remains MAY-optional in both the generic 429 shape and this endpoint's own 429
  schema (no "Required:" marker on retry_after_ms in either place). AC10's premise that a body
  `retry_after_ms` field might be "spec-mandated" is WRONG — it's optional and deprecated. This is
  a generally-applicable fact worth remembering for any future 429-shape review, not just this
  endpoint — added to Spec Quirks below.
- Pagination: opaque `next_batch` token, SHOULD be valid ≥10 minutes, expired tokens SHOULD be
  treated like invalid tokens → 400. No page-size number given (server's choice). No ordering
  guarantee on `joined` stated anywhere in the section.
- Self-user-id 400 case IS spec-mandated, directly in the endpoint's own 400 cause list ("...or
  was the sender's own user ID").
- Auth (401 M_MISSING_TOKEN/M_UNKNOWN_TOKEN) and rate-limiting (429) are NOT spelled out in this
  endpoint's own prose beyond its basic-info table (`Requires authentication: Yes`,
  `Rate-limited: Yes`) — those behaviors come from the generic §Using access tokens / §Rate
  limiting sections, same as every other v1/v3 endpoint. Confirmed as explicitly-called-out
  requirements (via the basic-info table), not merely inferred from "it's a v1 endpoint."

## Follow-up (same day, post-review): route-alias investigation for the unstable path

Code review flagged that Nebu's `/versions` now advertises
`unstable_features["uk.half-shot.msc2666.query_mutual_rooms"] = true`, which real clients
(matrix-js-sdk) read as "call the UNSTABLE path", not v1. Phil approved a route alias:
`GET /_matrix/client/unstable/uk.half-shot.msc2666/user/mutual_rooms` → same handler as the
stable v1 route. Task: confirm whether the historical unstable wire shape is field-identical to
the stable v1.19 shape before that alias ships as a pure pass-through.

**Local spec/changelog**: no history/migration note in the spec text itself — the `mutual-rooms`
section (anchor `get_matrixclientv1mutual_rooms`, line 61233) says only "[Added in v1.19]", and
the v1.19 changelog lists it as a plain "New Endpoint", not under any migration-note heading. The
bundled spec mirror does not document pre-stabilization history — this had to come from the web.

**Web research (WebSearch + WebFetch of pinned Synapse release-tag source, cross-checked across
multiple independent fetches)** — confirmed `matrix-js-sdk`'s real constant
`UNSTABLE_MSC2666_QUERY_MUTUAL_ROOMS = "uk.half-shot.msc2666.query_mutual_rooms"` (fetched
directly from `unpkg.com/matrix-js-sdk@36.1.0/lib/client.js`), matching Nebu's flag exactly — so
the flag name itself is correct. Synapse's actual unstable servlet evolved over time
(`shared_rooms` 2020 → renamed `mutual_rooms` 2022 via synapse#12036 → still path-param
`/user/mutual_rooms/{user_id}` as late as Synapse v1.60.0, response `{"joined": [...]}` only, no
pagination at all). By Synapse v1.144.0 (recent, pre-stabilization) the unstable servlet had
moved `user_id` to a query param (matching stable) but **still had NO pagination support at
all** — no `from` read, no `count`/`next_batch` ever returned, and it explicitly 400s on an
unrecognized `batch_token` query param. Synapse's `develop` branch today registers ONLY the
stable `v1` pattern — the unstable registration was dropped once v1.19 stabilized.

**The material finding, not a field-naming issue**: the historical/real-world unstable endpoint
was NEVER paginated. It always returned the complete `joined` list in one response. Nebu's
shared handler (`get_mutual_rooms/3` in `event_dispatcher/server.ex`) unconditionally pages at
`mutual_rooms_page_size()` (default 50) and emits `next_batch` once a caller has more than one
page of mutual rooms with the target. A legacy client hitting the aliased unstable path via pure
pass-through will silently receive only the first 50 mutual rooms if there are more than 50 and
will have no idea a `next_batch` continuation exists — a real, if narrow (>50 shared rooms with
one specific other user), silent-truncation regression for legacy callers. `count` and
`next_batch` themselves are purely additive JSON fields (harmless to a parser reading only
`.joined`), so this is NOT a rename/shim problem — it's a pagination-contract mismatch.
**Confidence**: high on "unstable was never paginated" (corroborated by two independently fetched
pinned Synapse release tags, v1.60.0 and v1.144.0, both showing response `{"joined": [...]}`
only); medium-high on exact current upstream query-param shape (some WebFetch summaries of large
dynamic GitHub pages proved unreliable elsewhere in this same investigation — one fabricated a
stable-endpoint shape that contradicted the verified local spec text — so treat any single
uncorroborated web fetch in this space with caution; the pinned-tag raw-file fetches are the more
trustworthy evidence here since they returned specific, internally consistent, and
mutually-corroborating code).

**Recommendation given to the team**: ship the alias, but either (a) cap/guard so the alias path
never emits a `next_batch` a legacy caller can't consume (e.g. don't truncate for the unstable
route — return the full `joined` list unpaginated the way the real historical endpoint always
did, or at least raise the page size enough that truncation is a non-issue in practice), or (b)
accept the narrow edge case explicitly as a known limitation. Do NOT ship it as a naive
3-line pure pass-through without at least naming this risk to the team — request/response field
*names* need no shim, but the *pagination behavior* does.
