# Session 2026-07-02 — ADR-030 Media Lifecycle: three CS-API rulings

Winston (Architect) consulted me for ADR-030 "Media Lifecycle Rules & Two-Eyes Delete"
(media-security-admin-control epic). Context: media_files has NO room_id by design; adding
(a) DSGVO Art. 17 erasure → restriction-of-processing (media invisible via download 404, bytes
retained, physical delete only via two-eyes), and (b) a per-room/space/global lifecycle policy
cascade (priority room > space > global).

## Q1 — Redaction on legal hold
- CS-API §Redactions (`#redactions`): no "media withdrawal" concept in Content Repository. 404 on
  download is spec-NEUTRAL and acceptable; spec neither requires nor forbids a matching event change.
- Client rendering of a 404'd mxc is UNDEFINED by spec (broken/placeholder is client behavior, not contract).
- Redaction IS the tool if you want the reference gone: room v11 (`rooms/v11/#redactions`) strips ALL
  content keys unless the event type is in the allow-list; `m.room.message` is NOT in it → the whole
  content (url/info/thumbnail_url/body) is stripped. Irreversible. PL-gated. Endpoint
  `PUT /_matrix/client/v3/rooms/{roomId}/redact/{eventId}/{txnId}`.
- No spec notion of "hide media but keep event." → Ruling: legal-hold = 404 (reversible restriction);
  redaction only as operator-initiated, PL-gated, irreversible add-on. Do NOT auto-couple to hold.

## Q2 — Every field an mxc can appear in (for the events.content join)
- m.room.message (m.image/m.file/m.audio/m.video): `content.url` + `content.info.thumbnail_url`
- Encrypted variants (§sending-encrypted-attachments): `content.file.url` +
  `content.info.thumbnail_file.url` (EncryptedFile REPLACES url/thumbnail_url)
- m.sticker: `content.url` + `content.info.thumbnail_url`
- m.room.avatar: `content.url` + `content.info.thumbnail_url`
- m.room.member: `content.avatar_url`
- NO media↔room ownership in spec; same mxc referenceable by many rooms.
- ⚠️ CRITICAL: in E2EE rooms `content` is Megolm ciphertext → server CANNOT see content.file.url →
  the room→media JOIN is impossible for encrypted rooms. Per-room policy = Compliance-Mode-only;
  encrypted rooms MUST fall back to global. Spec consequence, ties to ADR-011/ADR-023.

## Q3 — Resolving a room's parent space(s) (§Spaces)
- m.space.child (state in space-room, state_key=child room id, content.via Required) = the TRUST ANCHOR.
- m.space.parent (state in child, state_key=parent space id) is an unverified CLAIM: ignore unless
  (a) matching m.space.child in the parent, OR (b) sender has PL to send m.space.child in the parent.
- Multiple parents allowed; `canonical:true` marks primary; multi-canonical tiebreak = lowest room id
  lexicographically (Unicode code-points).
- Nesting allowed; loops disallowed but may occur → must guard infinite loops + long trees.
  GET /hierarchy walks depth-first.
- Link is DYNAMIC: demotion/leave can invalidate a previously valid m.space.parent; unjoined parent
  needs peeking (can't peek ⇒ assume invalid).

## Design implications I gave Winston
1. Per-room/space policy is Compliance-Mode-ONLY; encrypted rooms → global fallback (bake in, spec limit).
2. Join must cover all 6 fields; recommend a maintained mxc→room index over runtime JSONB @>. This IS
   the reserved interface from the "Compliance-Sichtbarkeit" ADR — wire them together.
3. most-conservative-wins is the only safe multi-room resolution (no ownership to arbitrate on).
4. Space resolution needs trust-validation (child-or-PL), multi-parent canonical tiebreak, loop/depth
   guards; resolve at cron transition-eval time, not per-download.
5. Keep legal-hold (404, reversible) and redaction (irreversible) decoupled.
