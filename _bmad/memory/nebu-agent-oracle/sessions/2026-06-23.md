# Session 2026-06-23 — Room alias grammar ruling (story room-canonical-alias-from-name)

Asked: alias localpart charset, validity of leading-dot / "/" / "+" / "=" localparts, m.room.canonical_alias content.

Spec findings (CS v1.18, appendices #room-aliases, line 884-894; CS #mroomcanonical_alias line 19415):
- Format `#localpart:domain`.
- Localpart MAY contain ANY valid non-surrogate Unicode codepoint EXCEPT `:` and NUL (U+0000). Very permissive — far more than the impl's allowlist [a-z0-9._=\-/+]. So the impl's allowlist is a SUBSET → spec-valid (never produces an invalid localpart), but conservative.
- Full alias incl. `#` sigil + domain MUST NOT exceed 255 BYTES.
- Leading/trailing dots, "/", "+", "=" are all spec-legal in a localpart (only `:` and NUL forbidden). "." and "..." localparts are legal per the grammar.
- BUT: aliases appear path-encoded in /_matrix/client/v3/directory/room/{roomAlias}; "/" in a localpart needs URL-encoding by clients. Element historically restricts the alias localpart it will *create* to a-z0-9._=-/+ (the impl's allowlist is copied from Synapse/Element create-time rules) — so "/" is interop-tolerated but a known rough edge.
- m.room.canonical_alias content: {"alias": "#x:server"} is sufficient. Optional "alt_aliases": [..]. Server SHOULD validate the alias is grammar-valid and points to this room (it does, by construction).

Verdict given to reviewer: impl allowlist is spec-conservative-valid. Real concern is NOT spec-illegality but interop ugliness of `/` and dot-only localparts (`#...:server`, `#a/b:server`), which Synapse/Element create-time rules avoid.
