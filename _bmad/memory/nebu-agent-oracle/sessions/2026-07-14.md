## Oracle Gate for Story 2d (download-stall-mechanism)

Spec-checked `GET /_matrix/client/v1/media/download/{serverName}/{mediaId}` (+ `/{fileName}`,
+ deprecated v3 forms) for the wait/stall query param (v1.18, added v1.7 — no MSC marker
remains in spec text, it's core).

**CRITICAL finding:** the spec's query param is `timeout_ms` (integer, ms), **not** `timeout`.
Story 2d's AC1/AC7 spec `?timeout=N`. Story 1c's own oracle-context.md (line 8) already
recorded `timeout_ms` correctly. If the handler implements `?timeout=`, real clients (Element,
etc.) sending the spec-correct `timeout_ms` will never trigger the stall — AC1's "absent"
fallback fires for every real request, silently defeating the feature. Flagged as blocking in
the Oracle Gate; recommend renaming the param to `timeout_ms` before dev-story implements it.

**Secondary note:** spec's own default when the param is absent is 20000ms (i.e. spec-default
behavior already waits up to 20s even with no client param). Story 2d's AC1 instead defines
"absent" as immediate no-wait (1c behavior) — a deliberate Nebu deviation from the spec
default, analogous to the existing 451-vs-504 deviation from 2026-07-13. Should be recorded
as an accepted deviation once confirmed with the team.

**Reused facts from 1c oracle-context.md:** 504+M_NOT_YET_UPLOADED is the spec pairing but
Nebu uses 451 (ADR-026, accepted deviation) — AC4's "fall back to 1c deny response" for a
timed-out wait must therefore still emit 451, not spec's 504. 429 M_LIMIT_EXCEEDED (rate
limiting) is orthogonal to AC6's concurrency-guard "degrade gracefully, no error" — spec
does not define behavior for stall-slot exhaustion, so returning the no-stall response instead
of 429 is spec-safe (not a rate-limit condition, just capacity-management policy Nebu owns).

### Worth curating into MEMORY.md
- `timeout_ms` (not `timeout`) is the wire-correct query param for all four download endpoint
  variants (v1 auth + deprecated v3, both with/without `{fileName}`) — add to the Media section
  next time MEMORY.md is touched, so this isn't re-discovered per-story.

## Oracle Gate for MediaReservedUploadCleanupWorker (reserved→hard_deleted cron)

Spec-checked `#post_matrixmediav1create` and `#put_matrixmediav3uploadservernamemediaid`
for any MUST on server-side cleanup of expired `:reserved` rows. Finding: cleanup itself is
entirely spec-optional (server "may optionally enforce a maximum age... and delete media IDs");
`unused_expires_at` is a SHOULD-return timestamp with a recommended (not mandated) 24h default;
no min/max TTL, no requirement that expired reservations be listable/enumerable. So this worker
has zero wire-protocol MUST to satisfy — confirms the story's own framing (internal housekeeping,
no CS API surface).

**Reused/reinforced fact from the 2026-07-01 MEMORY.md entry:** the PUT upload endpoint's 404
response explicitly folds "MXC ID has expired" into the *same* `M_NOT_FOUND` as "never created" —
no distinct errcode for expired-vs-unknown. That 404 must be a **live** check in the PUT handler
(`unused_expires_at < NOW()`), independent of whether this cron has already run — otherwise there's
a race window (up to 15 min, this worker's cron cadence) where an expired-but-still-`:reserved` row
would incorrectly accept an upload. This worker's job is state hygiene (freeing the pending-upload
slot, letting the row leave the table), not the source of truth for the 404 — good to confirm the
dev-story doesn't accidentally make PUT rely on `state = 'reserved'` alone.
