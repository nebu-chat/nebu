# Session 2026-05-27

## Topic
Matrix token refresh spec — `POST /_matrix/client/v3/refresh` — für Nebu opake Matrix-Sessions.

## Spec Findings

### `POST /_matrix/client/v3/refresh` (Added in v1.3)

**Endpoint:** `/_matrix/client/v3/refresh`  
**Auth:** Not required (authenticated via refresh_token in body)  
**Rate-limited:** Yes

**Request body:**
- `refresh_token` (string, **Required**)

**Response 200:**
- `access_token` (string, **Required**) — new opaque access token
- `expires_in_ms` (integer, Optional) — lifetime in ms; omitted = client assumes non-expiring
- `refresh_token` (string, Optional) — new refresh token; omitted = old one can be re-used

**Response 401:**
- `{"errcode": "M_UNKNOWN_TOKEN", "error": "...", "soft_logout": true}`

**Response 429:** Rate-limited, `retry_after_ms` field

### Key Behavioral Rules (§refreshing-access-tokens)

1. **Old access token invalidation:** Server MAY invalidate immediately or leave valid until natural expiry. Clients MUST NOT assume the old token is still valid.
2. **Old refresh token grace:** "The old refresh token remains valid until the new access token or refresh token is used, at which point the old refresh token is revoked." — This is a MUST: old RT stays valid until client confirms it received the new tokens by using them.
3. **Token rotation:** When server returns new refresh token, old is invalidated upon first use of new tokens.
4. **soft_logout on M_UNKNOWN_TOKEN:** Server SHOULD include `soft_logout: true` when access token has expired (token still valid session, just expired) vs. hard logout (session destroyed). Client uses `soft_logout: true` to know it can retry login with same device_id.

### `POST /login` — refresh token support (Added in v1.3)

**Request:** Client signals support via `refresh_token: true` (boolean) in request body.
**Response 200 extra fields:**
- `expires_in_ms` (integer, Optional) — access token lifetime
- `refresh_token` (string, Optional) — only issued when client sent `refresh_token: true`

Server handling note from spec: "Handling of clients that do not support refresh tokens is up to the homeserver; clients indicate their support for refresh tokens by including a `refresh_token: true` property in the request body." → Nebu MAY issue non-expiring tokens to clients that don't send `refresh_token: true`, or MAY expire them anyway and rely on soft_logout.

### Token Format Note (§using-access-tokens)
"This specification does not mandate a particular format for the access token. Clients should treat it as an opaque byte sequence. Servers are free to choose an appropriate format." → Nebu can issue 32-byte random hex tokens, just as admin sessions do.

### Device Binding (§relationship-between-access-tokens-and-devices)
"When a refresh token is used to generate a new access token and refresh token, the new access and refresh tokens are now bound to the device associated with the initial refresh token."

## Nebu Implementation Implications

The current implementation returns `rawJWT` (OIDC id_token) as `access_token`. This:
- Uses the OIDC token lifetime directly (typically 5 min in Keycloak)
- Discards the OIDC refresh_token from `oauth2Config.Exchange()`
- Has no `POST /refresh` endpoint
- JWTMiddleware validates directly against OIDC provider

The fix (story: `oidc-session-refresh`) requires:
1. New `matrix_sessions` table: opaque AT + opaque RT + encrypted OIDC refresh token + device_id + user_id + expires_at
2. `offline_access` scope in SSO flow to get OIDC refresh tokens from Keycloak
3. `POST /login` response: return opaque tokens + `expires_in_ms` when `refresh_token: true` in request
4. `JWTMiddleware`: look up opaque token in DB instead of verifying JWT directly
5. `POST /_matrix/client/v3/refresh`: exchange Nebu refresh token → use OIDC refresh token → issue new Nebu tokens
6. `soft_logout: true` when returning 401 M_UNKNOWN_TOKEN for expired (not logged out) sessions
