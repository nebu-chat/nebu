## Key Findings

**F-1 MEDIUM:** `WITH CHECK (true)` on compliance_requests UPDATE policy allows free column writes on pending rows, including `status` field. Two-step attack (pending→rejected→pending) is theoretically possible. Correctly out of scope for AC1, but worth addressing when compliance-feature application logic is built.

**F-2 LOW:** Down migration omits explicit `WITH CHECK (true)` — relies on PostgreSQL default. Maintenance risk if future migrations tighten the post-image check.

**F-3 LOW:** No regression test for DELETE policy remaining blocked after migration 003. DELETE is blocked by `000002` policies but not asserted in `000003` test suite.

**F-4 INFO:** Migration header comment does not state that FORCE RLS is intentionally retained (unlike audit_log Story 13.14 where it was removed). Future maintainers may incorrectly apply the managed-PG compatibility exception here.

## Patterns Noted

The `WITH CHECK (true)` on UPDATE with a USING-only state-machine guard is a recurring pattern now. For compliance/audit tables this creates a "during pending window, any field is writable" gap. See also: `server_config` where both USING and WITH CHECK are allowlist-scoped. Consider recommending a standard pattern for immutable-audit-trail tables: USING (row in mutable state) + WITH CHECK (immutable fields unchanged).
