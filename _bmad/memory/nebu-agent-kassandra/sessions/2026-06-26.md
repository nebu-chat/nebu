## Session — fix-device-key-registration (SEC Gate 1, story-level)

**Scope:** Stateful Matrix device-key directory. `DeviceKeyStore` (inline SQL), `/keys/upload`, `/keys/query`, `GET /devices(+/{id})`, `whoami`, `/sync` E2E extension, `m.room.encryption` state-PUT guardrail, migration 000009.

**Finding summary:** 0 CRITICAL, 1 HIGH, 1 MEDIUM, 1 LOW, 1 INFO → **BLOCKED**

- F-1 HIGH: E2EE guardrail bypass via createRoom `initial_state`. State-PUT path rejects `m.room.encryption` (protected.ex:1164) but `apply_initial_state/3` denylist (`@initial_state_forbidden_types`, server.ex:4403) is only `m.room.create/member/power_levels` — `m.room.encryption` is "honored" and replayed via emit_state_event. Persisted event is event-derived (search/db.ex excludes encrypted rooms) → real E2EE activation → ADR-011 break. Single authenticated request. Untested (AC6 guardrail test only covers state-PUT). Fix: add `"m.room.encryption"` to the denylist + regression test.
- F-2 MEDIUM: /keys/upload has no rate limit (only /sync does) and no per-array cap on one_time_keys; store-once dedup only on identical key_id → unbounded device_one_time_keys growth across repeated uploads. Mirror createRoom's 64-cap + add RateLimit.
- F-3 LOW: 000009 tables have no RLS — but parity-consistent with events/room_members (app-scoped single-role), not a regression.
- F-4 INFO: inner blob user_id spoofable but query_devices keys by trusted DB user_id column → no cross-user surfacing/overwrite. Correct design.

**New patterns discovered:**
- **Event-derived invariant denylist must include `m.room.encryption`.** Pattern #64 (createRoom denylist sound because state is GenServer-authoritative) has a CRITICAL EXCEPTION: `m.room.encryption` is NOT GenServer-authoritative — its mere persistence in `events` activates E2EE (search/db.ex treats a room with the event as encrypted; clients begin Megolm from /sync). Any new event-replay/writer path (createRoom initial_state, room upgrade copy_state_events server.ex:4523, future state-resolution) MUST forbid `m.room.encryption` to hold ADR-011. The state-PUT guard alone is insufficient — guardrails on a forgeable invariant must cover EVERY writer, not just the obvious one.

**Accepted risks this session:** none.

**Follow-up:**
- After F-1 fix lands, note `copy_state_events` (server.ex:4523) lists `m.room.encryption` among types copied on /upgrade — moot once no room can hold the event, but verify when /upgrade is next touched.
- SQL all parameterized, no secret logging, no new crypto — clean on those axes.
