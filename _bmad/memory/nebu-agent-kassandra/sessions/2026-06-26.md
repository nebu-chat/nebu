## device-management S4 — AC3 revoke-confirm CSP fix (SEC re-review, 2026-06-27)

**Diff:** show.html.heex + app.js + device_management_test.exs (3 files, +69/-19). Branch feature/device-management.

**Context:** epic-end SEC Gate 2 (2026-06-26, MEMORY row) had reviewed the OLD S4 confirmation = inline `onsubmit="return confirm('<fixed string>')"`. That inline handler is BLOCKED at runtime by the admin CSP `script-src 'self'` (no 'unsafe-inline') → confirm never fired → AC3 E2E red. This fix moves confirmation to a delegated `submit` listener in the external app.js (CSP-allowed, `script-src 'self'`) reading the form's `data-confirm` and calling `window.confirm`, `preventDefault` on cancel.

**Verdict: APPROVED / CLEAN — 0 CRITICAL, 0 HIGH, 0 MEDIUM, 2 LOW.**

Verified against code (not trusted from prompt):
- **Kill-switch UNTOUCHED (pattern #70 stays closed):** `git diff` shows matrix.ex / users_controller.ex / router.ex unchanged. `delete_user_device/2` still: denylist every bound JWT by token_hash→exp (`revoke_by_hash`), delete binding rows, revoke opaque session, delete keys. `require_admin` plug + `protect_from_forgery` CSRF intact. The confirmation is UX/4-eyes only; server enforcement is the real control. A devtools bypass of confirm() still hits CSRF + admin-auth + the full server-side revoke — no privilege gained.
- **XSS — IMPROVED, not regressed.** Old design used a fixed `onsubmit` string SPECIFICALLY to dodge dual-context (HTML-attr + inline-JS) escaping if device_id were ever interpolated. New design removes the inline-JS context entirely: `data-confirm={... <> device_id <> ...}` is a plain HTML attr (HEEx auto-escapes), read at runtime via getAttribute (browser-decoded) → passed to `window.confirm()` which renders PLAIN TEXT (no HTML/JS parse). device_id with `'`/`"`/`</script>`/`");alert(1)` is inert. Existing XSS test (line 405, `<img src=x onerror=...>`) already covers the device_id attr sink. No CSP `sandbox` dir → confirm() works.
- **No collateral confirm-gating.** Only the revoke form carries `data-confirm`; rename form does not. Listener keys on `form[data-confirm]`, capture phase, so only destructive revoke is gated.

LOW-1: Defense-in-depth — `data-confirm` is the ONLY guard on the client; this is acceptable because the server-side controls are authoritative (this is the correct security posture — confirm() was never a security boundary). LOW-2: the new listener is global to all admin pages but harmless (no-op without `[data-confirm]` forms).

No new MEMORY pattern — this is a CSP-compatibility refactor of an already-sound control. Reinforces existing note (MEMORY line 56/170): admin `script-src 'self'` (no unsafe-inline) is the correct topology — and it MEANS inline `on*=` handlers are dead; future destructive-action confirmations must use the external app.js delegated-listener pattern, never inline onsubmit. Worth curating as a reusable pattern.
