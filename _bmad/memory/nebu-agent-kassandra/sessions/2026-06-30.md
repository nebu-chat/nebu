## Key find (F-1, MEDIUM, NEW pattern)
PCRE `$` anchor accepts a single trailing `\n`. `String.match?("email\n", ~r/^[a-zA-Z0-9_:.\-]+$/)`
=> true. Verified empirically. Split-on-space doesn't split on `\n` → `"profile email\n"` passes
all three write whitelists. NEUTRALISED to MEDIUM because the scope string reaches the IdP only
via `URI.encode_query/1` (→ `%0A`, no CRLF/header/open-redirect). But the test suite gave FALSE
CONFIDENCE: AC3 tests only cover EMBEDDED newline `"profile\nemail"` (correctly fails), never the
TRAILING case. Fix: `$`→`\z` + trailing-`\n` regression test.

## What was CLEAN (and why, so I don't re-litigate)
- 3 write whitelists byte-identical; defaults byte-identical across 4 sites; `groups` only removable

- HEEx `value={...}` auto-escapes attr context + `script-src 'self'` → no XSS.

- Scopes read LIVE (no replay), names not URLs (no SSRF), IdP enforces per-client grants (no elevation).

## Carry-forward
- The `$`-anchor gap is project-wide latent: any future scope/claim/config validator using `^...$`
  on data that reaches a header/URL/downstream call (not URI.encode_query) is a live CRLF primitive.
  Recommend a grep/lint gate for `$/` in Elixir validators. Recorded as the new recurring pattern.
