# Session 2026-07-01 — media-security-clamav epic, pre-implementation design consultation

**Scope:** Ad-hoc consultation (not a diff review — nothing implemented yet). Phil handed me
`tmp/media-epic.md` (draft epic: quarantine→ClamAV-scan→release state machine, async MSC2246-now-
core upload, admin media management UI) and asked for security concerns + a specific architecture
question: clamd as sidecar, worried clamd crashing pulls Nebu down, wants a watchdog in the clamd
container that polls the DB for stale scans as fallback, plus "what restarts open scans on deploy".
Follow-up question: could the scanner be Elixir-native, orchestrated via Horde instead.

**Finding summary:** 0 CRITICAL / 0 HIGH-blocking (nothing to commit) — reported as a design watch-
list: 3 HIGH-if-implemented-carelessly, 4 MEDIUM, 2 LOW/doc-consistency. No report file (design-phase,
consistent with the device-management whole-epic pre-impl precedent).

**Core verdict (the actual ask):** Watchdog-in-clamd-container-polling-DB is UNSAFE — rejected.
Giving the one component deliberately fed attacker-controlled bytes (clamd/libclamav, real CVE
history in its archive parsers) a live Postgres credential/write-path turns an engine RCE into a DB-
writing primitive, and duplicates Story 1's own grep-enforced single-write-path invariant from a
different (unaudited) angle. The two real failure modes decompose cleanly onto EXISTING mechanisms
with zero new attack surface: (a) clamd down/unreachable → must never crash the Elixir caller — hard-
require every `:gen_tcp` call in `Nebu.Media.ClamAV` to return `{:error, reason}`, never raise; (b)
Nebu node dies/redeploys mid-scan → `Oban.Plugins.Lifeline` (rescues jobs stuck `executing` past
`rescue_after`) is built exactly for this, pair with graceful Oban shutdown-drain on deploy. Follow-up
(Elixir-native scanner via Horde): if that means NIF-embedding libclamav into the BEAM — worse than
the sidecar, a NIF crash takes the whole node, not an isolated process; reject. If it means only the
TCP-client GenServer becomes a Horde-managed cluster singleton — redundant, Oban+Lifeline already
gives cross-node job resilience via Postgres, and Horde adds split-brain risk on the state-transition
path for no gain. Recommendation: no Horde, no watchdog-in-sidecar; clamd stays an isolated external
process, `Nebu.Media.ClamAV` is a plain per-node GenServer with hardened error handling.

**New patterns discovered:**
1. Scanner/AV-sidecar trust boundary — a process deliberately fed attacker-controlled bytes must
   never be granted a orthogonal trust upgrade (DB credential, write path) to solve an unrelated ops
   problem (stale-job detection); solve that via the job queue's own crash-recovery primitive.
2. NIF-embedding a native library that parses untrusted input is a REGRESSION vs. an external
   process — trades OS-level crash isolation for none (NIF crash = BEAM node crash).
3. Distributed actor frameworks (Horde) are not a substitute for DB-backed job-queue resilience
   (Oban) — check whether the "node death" problem is already solved by the job queue before adding
   a second distributed-coordination layer.
4. Default-deny state gate — when a download/access gate is implemented as two enumerated allow-
   lists (which states → 451, which → 404) instead of a single allowlist-of-success, every future
   state addition (here: `scan_failed`, introduced two stories after the gate is written) risks
   silently falling through to permissive behavior. Gate must be `case state do :released -> 200; _
   -> deny end`.
