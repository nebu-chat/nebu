**Report:** `_bmad-output/implementation-artifacts/epic-room-naming-and-default-rooms-security-review-2026-05-28.md`

**Findings:**
- **F-1 MEDIUM** — `update_room_settings/2` uses `_stream` (no trusted_identity extraction). Pre-existing from Story 6.8, but this epic widens the proto with `is_auto_join` — a sensitive policy field that auto-subscribes every future new user. Mirrors Epic 14 F-2 pattern. Gateway PSK + sessionGuard + CSRF hold today; flag is defense-in-depth + inconsistency with sibling RPCs.
- **F-2 MEDIUM** — No `audit_log` emit when `is_auto_join` toggles. Gateway-side comment claims "Core audit log records actor_user_id" — false. Sibling admin ops (archive_room, set_user_role, gdpr_delete, etc.) all emit. Pattern match: Epic 14 "Bulk operation with no audit_log entry" — bulk SHAPE, not bulk row count.
- **F-3 LOW** — Personal-room concurrent-login race produces orphan room rows. `set_personal_room_id` has `WHERE personal_room_id IS NULL` guard, but `create_personal_room` already ran twice before the UPDATE — orphan rows for rooms/room_members/events persist. No security boundary crossed (user owns both rooms). UX/data-quality issue.
- **F-4 LOW** — `Nebu.Room.Server.join` does not check `m.room.join_rules` or ban state. Auto-join exploits this absence. Pre-existing weakness; only an issue when ban/join_rule subsystem is added in a future epic. Informational/architectural.
- **F-5 LOW (informational)** — Three new dev dex users share one bcrypt hash. ADR-012 example-only.

**New patterns discovered (curate to MEMORY.md):**

1. **Proto field widening re-audit:** When a proto message gains a new field whose security weight exceeds existing fields, re-audit the handler for `_stream` AND audit_writer.log. Story 6.8's `update_room_settings` was reviewed CLEAN with only `max_members` (soft cap); adding `is_auto_join` (persistent membership policy) makes the same handler weight-shift but the review pattern didn't catch it because the diff "only added one field." → Add to recurring patterns.

2. **Gateway-side comment claims vs. Core-side reality drift:** `rooms.go:401-402` says "Core audit log records actor_user_id" but Core discards the metadata. Comments asserting Core-side behaviour must be either grepped against the actual Core RPC or removed. Future per-story reviews should flag any cross-layer behavioural claim in a comment without a matching Core-side assertion.

3. **Fire-and-forget Task.start from RPC handlers:** Not a finding here (every helper catches and returns :ok), but architectural watch-flag: silent crashes lose work. If self-room creation becomes compliance-mandatory, the unsupervised Task shape silently violates the invariant. Track for future epics that add hard requirements to login-side side-effects.
