## bugfix/device-signing-upload-500-cors-masking (SEC Gate 1 — story-level) — CLEAN / APPROVED

Report: `docs/stories/security-reports/bugfix-device-signing-upload-500-security-review-2026-08-04.md`
(written in worktree `nebu-chat-worktrees/device-signing-upload-500`). 0 CRIT / 0 HIGH / 0 MED / 1 LOW / 2 INFO.

**Change:** unrescued DB write in `CrossSigningKeyStore.put_keys/2` + `put_keys_no_flag/2`
(`{:ok,_} = query(...)` → `MatchError`) crashed the HTTP handler before CORSPlug flushed
`Access-Control-Allow-Origin`, so browser misreported the 500 as a CORS error. Fix: route both
writes through the existing `safe_query/2` rescue; widen `@spec`s to `:ok | {:error, term()}`;
handle `{:error,_}` at both call chains → `device_signing/upload` = 500 `M_UNKNOWN`,
`signatures/upload` = per-(user,key) `M_UNKNOWN` in the `failures` map.

**Verified clean:**
- Reason-leak: `error/4` (`http.ex:91`) serializes only literal args; `put_unknown_failure/3`
  hardcodes; both consumers use `{:error, _}` (unbound). Test `cross_signing_test.exs:304` locks
  exact body `{"errcode":"M_UNKNOWN","error":"Internal server error"}`. NO raw `Postgrex.Error`
  struct reaches client. (`safe_query` returns `{:error, e}` = raw struct, but discarded everywhere.)
- Authz intact: AC6 key-id-collision guard first; validate-then-persist order unchanged; MINOR-1
  own-keys-only (`user_id != caller` → M_FORBIDDEN, touches no storage) unchanged; writer =
  server-derived `current_user`, SQL keyed `ON CONFLICT (user_id)`. Refactor added `{:error,_}` arms
  only INSIDE persist branches.
- SQL still param'd `$1..$5`, no interpolation introduced (only `query`→`safe_query` swap).
- No DoS (single rescue, no retry/loop; cheaper than the crash it replaces).
- CORS `origin:"*"` is pre-existing default + Matrix-spec-standard (bearer auth, no cookies) — not a
  finding, error body non-sensitive.

**F-1 LOW (advisory):** `safe_query/2` swallows the rescued exception with NO `Logger` line anywhere
in the store, and both consumers discard reason → an intermittent write failure on a security-sensitive
key-write leaves no server-side diagnostic beyond the generic 500. Suggest `Logger.error(reason)`
server-side (never in response). Ties to the recurring "decode_key outside safe_query" observability note.

**F-2 INFO (out of scope):** cross-signing writes have NO audit entry — but the SUCCESS path is equally
unaudited (pre-existing; public Ed25519 directory, no private material per ADR-011). Failed-write audit
meaningless without success audit. Forward, don't block.

**Memory tie-in:** same code as `client-crypto-setup` epic (2026-06-28) — all its guardrails preserved.
This fix is a net robustness improvement (write path now inside the same rescue the read paths use).
