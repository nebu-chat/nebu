
## SEC Gate 1 — fix-admin-member-audit-actions / Bug C admin force-add (2026-06-21)

Reviewed staged diff: `admin_add_room_member/3` + new `local_domain?/1` in
`core/lib/nebu/matrix/event_dispatcher/server.ex`.

Verdict: **CLEAN** (no CRITICAL/HIGH).

Verified:
- `actor_id` is server-derived from `session["current_user"]` (rooms_live.ex mount ~70),
  never client-settable. No IDOR/privesc on actor.
- `local_domain?/1` reads `:event_dispatcher, :server_name` — same source as
  `generate_room_id/0`. Default-deny on foreign domains. No hardcoded value.
- Domain-spoof: UserId regex `^@[a-z0-9._=\-/+]+:[^\s:]+$` forbids `:` in BOTH localpart
  and domain → `@x:localhost:evil` fails `valid?` (first cond branch). `split(parts: 2)`
  is sound; `_ -> false` default-denies anything without a `:`. No bypass.
- `insert_invitation` is idempotent (`ON CONFLICT (room_id, invitee_id) DO NOTHING`) →
  duplicate/concurrent force-add cannot raise → no 500/DoS.
- `enforce_restricted_join!` still runs unconditionally in `join_room/2`; the invite is
  created ONLY on the admin-authorized path. Client join path unweakened.
- LiveView catch-all (rooms_live.ex ~311) surfaces `{:error, :foreign_domain}` as flash,
  no crash.

LOW (non-blocking, hygiene): dangling pending invite on join failure.
If `join_room` raises after `insert_invitation`, the invite row stays pending →
room_id shows in target's `rooms.invite` on sync though the add failed. Target is always
a LOCAL user the admin intended to add; info leak is the room_id to that same user.
Low impact. Consider rescuing+rejecting the invite on failure, or inserting after a
successful membership check. Not a Gate-1 blocker.

NOTE: admin force-add invite skips the `invite_user/2` membership + PL `:invite` checks
(by design — operator authority via admin auth/router). Acceptable given admin gating.
