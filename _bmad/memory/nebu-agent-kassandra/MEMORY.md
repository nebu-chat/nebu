## Epic Watch-List — pre-implementation gate items (device-management)
_Recorded 2026-06-26 from a whole-epic design-phase review (S1–S4 all `ready-for-dev`, nothing
implemented yet). Each item is a SEC-Gate-1 MUST-VERIFY when the matching story's diff lands. The
epic threads through exactly the auth/session/token surfaces I have flagged for months (opaque
sessions, denylist, deactivation kill-switch, refresh, UIA). Grounding reads: `oidc_plug.ex`,
`matrix_session_store.ex`, `token_denylist.ex`, `sso_login.ex`, `http_public.ex`, `000001`/`000009`._

**S1 (device registry model) — verify on diff:**
- New `devices` table: add `ENABLE ROW LEVEL SECURITY` + per-user policy OR document the deliberate
  omission in the migration header. NOTE: sibling auth tables `matrix_sessions` (000001) and
  `device_keys` (000009) currently have NO RLS — `devices` lacking it is *consistent* but the whole
  family is a standing defense-in-depth gap. (Recurring pattern: "Missing RLS on new tables", Epic 9.)
- Backfill migration is a NEW forward migration (000009 is shipped/immutable) — confirm idempotent
  (`IF NOT EXISTS` + `ON CONFLICT DO NOTHING`), inline SQL (ADR-018), `release_test.exs` count bumped.
- `device_id` is a client-chosen opaque string landing in a PK + echoed to Admin UI / `GET /devices`:
  bound its length (≤255) and reject control chars at the write boundary.

**S2 (device lifecycle at login + device_id binding) — verify on diff (HIGH-density story):**
- **G1 fail-closed:** when `conn.assigns[:device_id]` is absent (binding-store miss, pre-S2 token, DB
  error), per-device write paths (`/keys/upload`, S3 endpoints) MUST reject — NEVER fall back to a
  body-supplied `device_id` as authority (that re-creates the cross-device-transfer primitive the
  removed `sole_device_id/1` heuristic embodied). Body `device_id` may only be equality-checked and
  rejected on mismatch (AC6).
- **Login now honors client `device_id`** (today it always `generate_device_id()` — http_public.ex:296,
  ignores body device_id + initial_device_display_name). When it starts honoring reuse: re-login on an
  existing (user_id, device_id) MUST invalidate the prior token bound to that device (Matrix spec — a
  security mechanism, not a nicety). Opaque: `delete_for_user_device/2`. JWT: denylist the prior bound
  token. Push AC2 to "honor", not "document".
- **JWT token→device binding store** must record, per (user_id, device_id), each active token's
  denylist key (jti or sha256 hash) + `exp` — see S3 item (device-delete needs to enumerate them).
  device_id must NOT go into the IdP-issued JWT; bind server-side. (Dev Notes already say this.)
- **Refresh non-regression (G2/G3):** `rotate_tokens/1` already carries `user_id`/`device_id` from the
  old row → new row (store:146-163). Confirm the rotated AT/RT stay bound to the SAME device_id; the
  existing oidc-session-refresh tests must stay green.

**S3 (device endpoints + UIA-gated delete) — verify on diff (HIGHEST scrutiny):**
- **UIA fresh-auth must be anchored to a server-verified IdP `auth_time`, NOT "an SSO round-trip
  happened".** `verify_token/2` does NOT inspect `auth_time` today. The existing SSO redirect sends
  `prompt=login` (sso_login.ex:98-101) — but S3 builds a NEW UIA-SSO coordination path that can
  silently drop it. REQUIRE: (a) UIA-SSO authorization request sends `prompt=login` AND
  `max_age=<window>`; (b) callback reads `auth_time` from the freshly-verified id_token and requires
  `now - auth_time ≤ window`; (c) missing/non-integer `auth_time` → treated as STALE (challenge), never
  fresh — same for the "≤15 min proceeds directly" branch on both opaque and JWT sessions. Without
  this the walked-up-to/hijacked-open-session threat the story names is NOT mitigated. (HIGH)
- **UIA SSO completion must bind the freshly-authenticated `sub` to the UIA session's user AND the
  access-token user.** If it only checks "an SSO completed for this session id", an attacker holding
  the victim's session satisfies UIA with THEIR OWN IdP account → fresh-auth granted → victim's devices
  revoked. REQUIRE `UserId.from_claims(claims) == uia_session.user_id == conn.assigns.current_user`. UIA
  `session` = server-issued, single-use, bound to (user, pending-op fingerprint), short TTL, and
  CLUSTER-correct (reuse `SsoStore`, NOT node-local ETS — ADR-020). (HIGH)
- **Device delete must revoke ALL tokens bound to the device — incl. raw-JWT via the denylist.** Opaque
  path: `delete_for_user_device/2` exists. JWT path: the ONLY revocation primitive is
  `TokenDenylist.revoke(jti, token, exp)` — needs S2's binding to enumerate the device's jti/hash+exp.
  If skipped, the JWT keeps authenticating as the user until OIDC `exp` (incomplete kill-switch, pattern
  #69). S3 test #3 currently only covers the opaque session — EXTEND it to assert a JWT-bound device's
  token is `401 M_UNKNOWN_TOKEN` after delete. (HIGH)
- **`auth_time` MUST NOT be reset by refresh.** `matrix_sessions` has NO `auth_time` column → S3 adds
  one (new forward migration). `rotate_tokens/1`'s INSERT sets `created_at = NOW()` (store:154-163) — a
  dev adding `auth_time` there will naively write `NOW()` → refresh defeats the freshness gate. It MUST
  be carried from the old row exactly like user_id/device_id. Regression test: login→/refresh→auth_time
  unchanged. (HIGH-mechanism / MEDIUM-likelihood)
- **`POST /delete_devices` array cap.** Cap list length (≤100) → `400`; dedupe; per-element scope to
  current_user with 404-silent for foreign/unknown (no oracle). Amplification otherwise. (MEDIUM)
- **IDOR (G3):** rename/delete scope strictly to `conn.assigns[:current_user]`; foreign/non-existent
  device → `404` (no existence oracle, no 403). Already specified — confirm in code.

**S4 (Admin UI device management) — verify on diff:**
- Admin device-delete REUSES S3's path (story says so) → inherits the F-3 completeness requirement
  (revoke opaque + denylist JWT). Confirm it doesn't reimplement a weaker revoke.
- New audit actions registered in `AuditWriter.@known_actions` at the same commit (project memory:
  merging audit actions without registering them silently breaks the audit trail). Every rename/delete
  emits audit_log.
- Admin authz gate on view AND act (existing OIDC/role gate); `last_seen_ip` rendered as text only.
