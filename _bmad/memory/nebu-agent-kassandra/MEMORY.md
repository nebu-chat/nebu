## Recurring Patterns
_Finding types that appear across multiple stories — indicators of systemic issues._

## Recurring Patterns

| Pattern | Epics | Description |
|---------|-------|-------------|
| Fix that WAKES UP previously-dead code = review it as NEW attack surface | oidc-bootstrap-only (bugfix-autojoin-first-login-race) | A bugfix whose whole point is that a code path never ran in production (dead fn, no caller) now runs on a publicly-reachable endpoint. The reviewer must NOT wave it through as "already-audited, unchanged behavior" — the *reachability* changed, so the trust model must be re-verified at the NEW call site: (a) is every input the woken code consumes still server-derived at the new entry, or does the new caller pass attacker-controllable data the old (dead) caller never did? (b) is the new endpoint's rate-limit/auth posture equal-or-stronger than the dead path assumed? (c) does newly-running code newly *reach* a pre-existing latent gap (here: `Room.Server.join/2` has no join_rule/ban check, F-4) that was harmless only while the path was dead? Verdict here was CLEAN: `is_new` + `user_id` both server-derived (TokenValidator DB lookup + `UserId.from_claims(verified)`), `/login` already carries per-IP 30/min RateLimit, room set is admin-flagged server-side SQL — but the CHECKLIST is the reusable artifact, not the verdict. |
| Missing RLS on new tables | 9 | New tables (forgotten_rooms) added without RLS policy, breaking defense-in-depth. Check every new table migration for ENABLE ROW LEVEL SECURITY + policy. |
| Device-ID threading gaps | 9 | When per-device columns are added to existing queries, all dependent query helpers must be updated to pass device_id. Check all query helpers when schema adds device_id to PK. |
| Nullable state_key + equality filter | 11 | Any `WHERE state_key = '...'` filter misses NULL rows because in three-valued SQL logic `NULL = ''` is NULL. The events.state_key column (mig 000038) is nullable. Defense-in-depth: prefer event_type-only checks for "is room encrypted/redacted/etc.", or include `OR state_key IS NULL` explicitly. |
| DB-module user_id trust-boundary docstring | 11 | New DB modules taking `user_id` for authorization scoping must document loudly that it MUST come from the validated session, not from request payload. FOR UPDATE USING (true) WITH CHECK (true)` on shared key-value tables (e.g., `server_config`) destroys the per-key immutability invariant. Always scope UPDATE policies by `key IN (...)` allowlist. | "// for MVP" auth shortcut → live vulnerability | 4 → 12 | A `// for MVP, accept any bearer` comment lived in media/upload for 8 epics; Story 12.3 wired the service into compose and exposed port 8009. | Unauthenticated media endpoint + unbounded resource | 12 | Thumbnail (`width`/`height`) and download (`io.ReadAll`) handlers do expensive per-request work without auth and without bounds. | Inline Content-Type echoed back with `inline` disposition | 12 (4) | Stored XSS surface: attacker uploads `Content-Type: text/html`, download serves it back inline. Matrix spec v1.12+ requires `attachment` for unsafe types. Add `X-Content-Type-Options: nosniff` always; allowlist server-controlled types on download. |
| OIDC fail-open at startup | 12 | When an OIDC-required service falls back to "any bearer accepted" if the provider can't be reached at boot, an operator misconfiguration (empty issuer env, Dex offline) silently produces an anonymous-upload surface. Pattern: services that require OIDC must support a `_REQUIRED=true` knob to refuse startup when the verifier is nil. Logged `slog.Warn` is necessary but insufficient. |
| `uploader_user_id` ≠ Matrix user ID | 12 | When media stores identity claims (raw `sub` or `name`) without going through the gateway's `FormatUserIDFromClaims` translation, audit-trail correlation breaks. Story 12.9 partially closed this: added `@localpart:server` format + sanitisation, but still extracts from `claims.Sub` (with `Name` fallback) instead of operator-configured `oidc_user_id_claim`. | XFF rate-limit spoofing on directly-exposed services | 12 | When a service exposes a port directly to the host (`ports: ["8009:8009"]`) and the rate-limiter trusts `X-Forwarded-For` without a `trustedProxy` toggle, attackers rotate the rightmost XFF entry to force fresh sync.Map buckets and bypass per-IP rate limits entirely. | Per-story CLEAN reviews can stack into combined HIGH at epic-end | 12 | 12.8, 12.9, 12.10 each reviewed CLEAN in isolation. | Deprecated CSP directive `plugin-types` misleads auditors | 12 | `plugin-types application/pdf` is ignored by all modern browsers (removed from CSP3 spec; Firefox 84+, Chrome 70+ do not implement it). Including it in a CSP header creates false assurance that PDF plugin embedding is controlled by a directive when it is actually controlled (correctly) by `object-src`. Remove from all CSP headers; rely on `object-src 'self'` or `object-src 'none'` instead. |
| Unvalidated URL path segment in Content-Disposition filename | 12 | When a URL path variable (e.g. `{fileName}`) is used as a `Content-Disposition` filename, apply the same input-character allowlist used elsewhere in the service (e.g. `mediaIDPattern: ^[A-Za-z0-9_\-]+$`). Go's `%q` prevents CRLF injection but does not produce RFC 5987-safe filenames and does not strip semantically dangerous characters from log/audit perspectives. |
| Story-title oversell on partial graceful-shutdown | 12 | Story 12.13 titled "Graceful Shutdown" but only wires signal-awareness into OIDC startup; `http.Server.Shutdown(ctx)` is NOT called, so SIGTERM during serving phase still results in Docker SIGKILL after 10s grace. Not a security finding (no auth bypass, no data exposure), but a pattern to watch: future "graceful shutdown" claims must verify `srv.Shutdown(ctx)` with a `shutdownTimeout` is actually wired, plus a regression test that issues a request → SIGTERM → asserts request completes before exit. **CLOSED 2026-05-13 by Story 12.14**: `srv.Shutdown(shutdownCtx, 30s)` + `pool.Close()` + ctx-aware `cleanupLoop` all wired; pattern remains as a watch-flag for future "graceful X" stories. |
| Shutdown-phase auth bypass via cancelled request ctx | (audit) | In Go HTTP servers, `r.Context()` derives from `srv.BaseContext` (default `context.Background()`), NOT from any outer SIGTERM ctx. This is actually a feature: in-flight requests during `srv.Shutdown` complete their full middleware stack with uncancelled request contexts — auth/rate-limit/OIDC verification still run. BUT: if a future story sets `srv.BaseContext = func(_ net.Listener) context.Context { return shutdownCtx }` to "speed up drain", it would propagate cancellation into request contexts and could cause `oidcVerifier.Verify(r.Context(), ...)` to error with `context.Canceled` → 401 → and depending on error handling, potentially leak a bypass. Rule: never wire the outer SIGTERM ctx as `BaseContext` without also auditing every `ctx.Err()` check in the request path. |

| `/.well-known/matrix/client` reflects unsanitized `Host`/`x-forwarded-proto` into `base_url` | client-crypto-setup (wellknown-e2ee-default) | PRE-EXISTING WATCH-FLAG (noted 2026-06-28, NOT introduced by this story). `server/lib/nebu/web/router.ex` `get "/.well-known/matrix/client"` builds `base_url = scheme <> "://" <> host` where `host = get_req_header(conn, "host")` (or `x-forwarded-proto` for scheme) with NO allowlist/sanitization. ## Epic Watch-List — pre-implementation gate items (device-management)
_Recorded 2026-06-26 from a whole-epic design-phase review (S1–S4 all `ready-for-dev`, nothing
implemented yet). Each item is a SEC-Gate-1 MUST-VERIFY when the matching story's diff lands. The
epic threads through exactly the auth/session/token surfaces I have flagged for months (opaque
sessions, denylist, deactivation kill-switch, refresh, UIA). Grounding reads: `oidc_plug.ex`,
`matrix_session_store.ex`, `token_denylist.ex`, `sso_login.ex`, `http_public.ex`, `000001`/`000009`._

**S1 (device registry model) — verify on diff:**
- New `devices` table: add `ENABLE ROW LEVEL SECURITY` + per-user policy OR document the deliberate
  omission in the migration header. NOTE: sibling auth tables `matrix_sessions` (000001) and
  `device_keys` (000009) currently have NO RLS — `devices` lacking it is *consistent* but the whole
  family is a standing defense-in-depth gap. (Recurring pattern: "Missing RLS on new tables", Epic 9.)
- Backfill migration is a NEW forward migration (000009 is shipped/immutable) — confirm idempotent
  (`IF NOT EXISTS` + `ON CONFLICT DO NOTHING`), inline SQL (ADR-018), `release_test.exs` count bumped.
- `device_id` is a client-chosen opaque string landing in a PK + echoed to Admin UI / `GET /devices`:
  bound its length (≤255) and reject control chars at the write boundary.

**S2 (device lifecycle at login + device_id binding) — verify on diff (HIGH-density story):**
- **G1 fail-closed:** when `conn.assigns[:device_id]` is absent (binding-store miss, pre-S2 token, DB
  error), per-device write paths (`/keys/upload`, S3 endpoints) MUST reject — NEVER fall back to a
  body-supplied `device_id` as authority (that re-creates the cross-device-transfer primitive the
  removed `sole_device_id/1` heuristic embodied). Body `device_id` may only be equality-checked and
  rejected on mismatch (AC6).

  ignores body device_id + initial_device_display_name). When it starts honoring reuse: re-login on an
  existing (user_id, device_id) MUST invalidate the prior token bound to that device (Matrix spec — a
  security mechanism, not a nicety). Opaque: `delete_for_user_device/2`. JWT: denylist the prior bound
  token. Push AC2 to "honor", not "document".
- **JWT token→device binding store** must record, per (user_id, device_id), each active token's
  denylist key (jti or sha256 hash) + `exp` — see S3 item (device-delete needs to enumerate them).
  device_id must NOT go into the IdP-issued JWT; bind server-side. (Dev Notes already say this.)

  old row → new row (store:146-163). Confirm the rotated AT/RT stay bound to the SAME device_id; the
  existing oidc-session-refresh tests must stay green.

- **UIA fresh-auth must be anchored to a server-verified IdP `auth_time`, NOT "an SSO round-trip
  happened".** `verify_token/2` does NOT inspect `auth_time` today. The existing SSO redirect sends
  `prompt=login` (sso_login.ex:98-101) — but S3 builds a NEW UIA-SSO coordination path that can

  `max_age=<window>`; (b) callback reads `auth_time` from the freshly-verified id_token and requires
