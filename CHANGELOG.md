## [Unreleased]

### Added

- **`PUT /_matrix/client/v3/rooms/{roomId}/redact/{eventId}/{txnId}` and applied `m.room.redaction` events, audit action `room_event_redacted`, migration 000051 (story state-writer-redaction; follow-ups `fw`, `fv`, `fz`, `fx` closed)**: Element's "Remove" and "Remove recent messages" work. A redaction is decided and written by the room process (own event: `events["m.room.redaction"]`; another user's event: also the `redact` level), stored with a top-level `redacts` (new column `events.redacts`, migration 000051) and served with `redacts` and `content.redacts`; the redacted event is served pruned (`content: {}`, `unsigned.redacted_because`) on every read path while its content stays in the database (Compliance Mode); a redaction of another user's event writes the audit row `room_event_redacted`. Operator query **Q-rd** (07-deployment) lists legacy unchecked redactions.
- **`PUT /_matrix/client/v3/rooms/{roomId}/state/m.room.power_levels` (story power-levels-enforcement; follow-ups `eq`, `er`, `fr` closed)**: power levels can be changed after the room was created (Element's Roles & Permissions, `/op`, `/deop`) under the room version 10 change rules, decided and written in the room process in one transaction; new audit action `room_power_levels_changed`; the PUT is charged to the `moderation` tier; operator query Q-pl in `docs/architecture/07-deployment.md`.
- **Room moderation routes `POST /_matrix/client/v3/rooms/{roomId}/kick`, `/ban` and `/unban` (story moderation-routes-atomic-ban; follow-ups `ex` and `ew` closed)**: the three routes work as the Matrix spec and room version 10 define them, including the "Disinvite" of a pending invitee (a kick of an invited user) and pre-emptive bans. Every change that a ban can race (kick, ban, unban, the invite event, the decline, the join) is decided and written inside the room process, stamped after the user's latest member event and committed in ONE database transaction. A fourth per-user rate-limit tier `moderation` (30 per minute, burst 60, one unit per request of the three routes; a labelled divergence from the spec's "Rate-limited: No"; env `NEBU_RATE_LIMIT_MODERATION_PER_MIN` / `NEBU_RATE_LIMIT_MODERATION_BURST`, passed through by `docker-compose.yml`). New audit actions `room_member_kicked`, `room_member_banned`, `room_member_unbanned`. Operator query Q-half (banned users that are still in the member set) in `docs/architecture/07-deployment.md`.

### Changed
- **⚠ `/event`, `/relations` and the incremental `/sync`: new answers (story history-visibility-enforcement, follow-up `es`; behaviour change)**: `GET /rooms/{roomId}/event/{eventId}` and `GET /rooms/{roomId}/relations/{eventId}` answer `404` `M_NOT_FOUND` `Event not found` for an unknown event or parent (was `Room not found`) and, byte for byte the same, for one the caller may not see; an unknown room keeps `Room not found`. The incremental `/sync` answers `503` `M_UNAVAILABLE` when the events of a room cannot be read (the since token is not advanced, the client retries) instead of silently dropping that room from the response, which let the next since token pass its events.
- **⚠ History visibility and guest access values are validated (story history-visibility-enforcement, security cycle 1; follow-up `gj` closed; behaviour change)**: a PUT of `m.room.history_visibility` (empty state key) with a value other than `invited`, `joined`, `shared`, `world_readable`, or of `m.room.guest_access` with a value other than `can_join`, `forbidden`, is `400 M_BAD_JSON` (also as a createRoom `initial_state` entry); the 257th history-visibility event of a room is `429 M_LIMIT_EXCEEDED` unless it is strictly more restrictive than the current setting (the cap never blocks tightening); these PUTs and `m.room.join_rules` cost a `moderation` token; `POST /read_markers` refuses an `m.fully_read` event the user may not see like an unknown one (`400`); an event id with a NUL on `/event` / `/relations` (and a `/messages` token naming one) is `404` `Event not found`.
- ⚠ **Membership state (story membership-state-model, follow-ups `fb`, `fl` (c)):** the initial `/sync` state lists the latest member event of every user (join, invite, ban, knock, leave) from the member events, so Element's "Invited" section and "Banned users" list survive a reload; `GET /rooms/{roomId}/members` honours `membership` / `not_membership` (`400 M_INVALID_PARAM` for other values, `at` ignored), serves real event ids and `unsigned`, and answers `403` for non-members and for an unknown room (no `rooms` row any more); `/initialSync` serves real event ids and `unsigned` (unknown room `403`); `POST /upgrade` writes real invite events in the upgrader's name (`is_direct` carried). Member slots other than `join` are capped at 10 000 per room (operator query Q-ms in 07-deployment). Security cycle 1: `/members` and `/initialSync` are charged to a new per-user tier `members_read` (60 per minute, burst 30; `NEBU_RATE_LIMIT_MEMBERS_READ_PER_MIN` / `NEBU_RATE_LIMIT_MEMBERS_READ_BURST`; a divergence from the spec (no rate limit listed); the initial `/sync` is not charged); the slice runs under a 2 s `statement_timeout` (a slower read is `503 M_UNAVAILABLE`, its cost is O(member events of the room), operator query Q-ms2); a never-member no longer starts a stopped room; an upgrade reads the `is_direct` flags before the tombstone. Security cycle 2: at most 3 concurrent member-state reads per node (`NEBU_MEMBER_SLICE_MAX_CONCURRENCY`, node-local); on `/sync` a room whose member state cannot be read in time is served with the joined members only (one warning) instead of failing the response; the `/members` and `/initialSync` predecessor lookup has its own 2 s timeout.

- **⚠ Redaction and state writes: stricter and new answers (story state-writer-redaction; behaviour change)**: a `/send` of `m.room.redaction` is authorised (the `redact` level for another user's event, `403` below it) and applied instead of being stored as sent; redacted events are served pruned and left out of search and relations; state events and redactions cannot be redacted (`403`); PUT state is decided and written in the room process (an archived room is `404`, an unknown room `403` without a `rooms` row); the upgrade needs the tombstone level and at least 100; a createRoom `initial_state` entry whose state key is another user's id is `400 M_INVALID_ROOM_STATE`. A redaction of an already redacted message returns the existing redaction (no second row); the `/send` idempotency key now includes the event type (the same txn id on two event types is two requests); search also leaves out the edits of a removed message (they stay served elsewhere); an upgrade whose old room does not answer the tombstone write is `503` and keeps the started new room (retry the upgrade). Operators: migration 000051 adds a column and builds an index on `events` in one transaction under an ACCESS EXCLUSIVE lock (reads and writes on `events` wait: maintenance window, or add the column by hand and pre-create the index with `CONCURRENTLY`, see 07-deployment); rolling it back, or rolling back only the application image, makes removed messages readable again.
- **⚠ Power levels: `events[type]` is enforced, new rooms get a default `events` map (story power-levels-enforcement; behaviour change)**: the per-type `events` map now decides sends and state PUTs (`events[type]`, else `events_default` / `state_default`); a state key that starts with `@` must be the sender's own id; new rooms carry the default `events` map (non-spec, Synapse-derived: levels event, history visibility, tombstone, server ACL, encryption at 100, name, avatar, canonical alias at 50); an `initial_state` `m.room.power_levels` entry is applied; `POST /rooms/{roomId}/upgrade` carries the levels and needs the upgrader at the highest level of the room.
- **⚠ Room moderation: stricter and new answers (story moderation-routes-atomic-ban; behaviour change)**: an unban needs the `kick` level as well as the `ban` level and is only possible for a banned user (`403` otherwise); a kick of a user who is neither a member nor an invitee is `403 M_FORBIDDEN` (it was an internal `404`); `POST /rooms/{roomId}/upgrade` carries the bans of the old room into the new room as new ban events in the upgrader's name (the power levels are still not carried, follow-up `fr`); `reason` of the three routes is capped at 1024 bytes and refuses NUL; an upgrade of a room with more than 10 000 bans is refused with `403 M_FORBIDDEN` before anything is written, and the old room is archived and stopped right after its tombstone (before the new room is filled); the requester of an upgrade must be a member of the old room and not banned (`403 M_FORBIDDEN`). Element's "Banned users" list stays empty after a fresh initial sync until the membership state model of story 2 (follow-up `fb`): unban with `/unban <user id>` or the member's profile.

- **⚠ Event size limits: `413 M_TOO_LARGE` at write time (follow-up `ep`; behaviour change)**: `PUT /rooms/{roomId}/state`, `PUT /rooms/{roomId}/send` and `POST /createRoom` (`initial_state`, `creation_content`, `power_level_content_override`, decided before the room exists) refuse, before anything is persisted, an event above 65 536 canonical bytes (the stored event plus `event_id` and `signatures`) or with a `type` / `state_key` above 255 bytes with `413 M_TOO_LARGE` and a fixed message (Synapse parity; the spec names no code); a body above the 1 MB parser cap on `/_matrix/*` now gets the `M_TOO_LARGE` envelope "Request body is too large" instead of an empty 413; user ids derived from IdP claims are bounded to 255 bytes (an id of 255 bytes or more is hashed to exactly 255 bytes, natural ids stay at most 254; an account with such an id gets a new id at its next login, query Q-uid in 07-deployment; a server name above 235 bytes now refuses to start); `upgrade_room` skips legacy oversized state and copies `m.room.join_rules` / `m.room.history_visibility` / `m.room.guest_access` of that size in a reduced form that is never more open; existing events are unchanged (read-side budgets stay as defence in depth), see 07-deployment (Q-size).
- **⚠ Per-user rate limits for `POST /createRoom`, `POST /join` and `POST /rooms/{id}/invite` and caps of pending invitations (follow-up `ey`; behaviour change)**: three per-user token buckets, `create_room` (10 / min, burst 20), `invite` (20 / min, burst 50; a `createRoom` is charged one unit per distinct invitee) and `join` (12 / min, burst 30), answer a refused request with `429 M_LIMIT_EXCEEDED` (`Retry-After`, `retry_after_ms`); pending invitations are capped per inviter (500), per invitee (100) and per pair (10), a refused invitation is `403 M_FORBIDDEN` ("You have too many pending invitations ..."). Tunable with `NEBU_RATE_LIMIT_<TIER>_PER_MIN` / `_BURST` and `NEBU_INVITE_MAX_PENDING_PER_INVITER` / `_PER_INVITEE` / `_PER_PAIR`; `NEBU_RATE_LIMIT_DISABLED` disables the tiers, not the caps. `POST /rooms/{id}/upgrade` also spends one `create_room` unit. The caps are enforced under PostgreSQL advisory locks (hard against concurrent client invitations); the per-invitee total ignores rows of deactivated inviters and of inviters on the invitee's `m.ignored_user_list`; the `rooms.invite` section of `/sync` has a per-response byte budget for the stripped state (an optional event above 64 KiB, then the largest optional events above 8 MiB in total, are left out; an invitation never). The limiter now takes tokens with a compare-and-swap. `docker-compose.yml` passes the nine variables through. Migration 000050 adds a partial index on `room_invitations`. The release gate of the createRoom / sync batch is lifted.
- **⚠ Legacy SSO login: confirmation page for unlisted https clients (epic SEC gate 3, G3-3; behaviour change)**: after the IdP login, the legacy `m.login.sso` flow now redirects with the `loginToken` straight to the client only when the `redirectUrl` origin is *listed*: the server's own `https://<server_name>`, the `oauth_issuer_url` origin, the https redirect origins of approved OAuth clients, or an origin in the new Admin setting **"SSO redirect origins"** (`/admin/config`, `server_config.sso_redirect_allowed_origins`). For any other https `redirectUrl` the user must confirm on a page ("Continue sign-in to `<origin>`?") before a `loginToken` is minted. Loopback `http://localhost|127.0.0.1` targets and custom-scheme clients (`element`, `schildichat`, `im.fluffychat.auth`, the configured extra schemes) are unchanged. **Operator impact:** web clients served from another origin than `server_name` (a separately hosted Element Web, `app.element.io`, SchildiChat / Cinny / Hydrogen / FluffyChat web on other hosts) show the page on every login until their origin is listed; the server log line `matrix SSO: redirect confirmation shown host=<host>` names the hosts. `redirectUrl` values with userinfo, backslashes, control characters, numeric host lookalikes or more than 2048 bytes are now rejected with `400`; existing `loginToken` parameters of the `redirectUrl` are removed before the new one is appended. Independent of `oauth_enabled`. Runbook: `docs/architecture/07-deployment.md`, "Legacy SSO confirmation page".
- **Migration 000048**: the `server_config` update policy now allows the keys `sso_extra_redirect_schemes` and `sso_redirect_allowed_origins`. Before it, saving the "SSO redirect schemes" form a second time failed with a row-level-security error.
- **SSO Redirect Schemes — bootstrap-only config**: `NEBU_SSO_REDIRECT_SCHEMES` environment variable has been removed. All SSO redirect scheme configuration is now bootstrap-only: configure additional trusted schemes via the Admin UI at `/admin/config` after bootstrap. The hardcoded default now correctly lists `element`, `schildichat`, and `im.fluffychat.auth` (previously included inaccurate scheme names `io.element.fluffychat` and bare `fluffychat`, which do not match any real Matrix client's registered URI scheme).
- **⚠ BREAKING (dev/local only) — dev Dex's issuer is now a public hostname**: the bundled development Dex instance (`dev/dex/config.yaml`) now advertises `http://dex.localtest.me:5556/dex` as its `issuer`, instead of the Docker-Compose-internal `http://dex:5556/dex`. This fixes the MSC2965 `auth_metadata` endpoint (and every other OIDC discovery field) advertising a hostname only reachable from inside the compose network — browsers and Matrix clients could never actually reach it. `dex.localtest.me` resolves to `127.0.0.1` via public DNS (the `*.localtest.me` wildcard convention), so no `/etc/hosts` edit is needed in the common case; see README.md / `docs/getting-started.md` for the DNS-rebind-protection fallback on networks where it is blocked.
  - **Impact for already-bootstrapped local/dev deployments using Dex:** the stored `server_config.oidc_issuer` still has the old `http://dex:5556/dex` value. After upgrading, Dex mints tokens with `iss = http://dex.localtest.me:5556/dex`, and the server's strict `iss` claim check (`Nebu.Web.Plugs.OidcPlug`) will reject every existing Bearer token and admin login with `bad_issuer`.
  - **Remediation:** per ADR-022 (OIDC is bootstrap-only — no env var to patch), there is no Admin-UI-driven fix for the stored issuer value today. Simplest fix: update the persisted row directly — `docker compose exec postgres psql -U nebu -d nebu -c "UPDATE server_config SET value = 'http://dex.localtest.me:5556/dex', set_at = (EXTRACT(EPOCH FROM NOW())*1000)::bigint WHERE key = 'oidc_issuer';"` — then restart the server (`make redeploy`). Alternatively, discard the local dev database entirely and re-run the Bootstrap Wizard from scratch (`make dev-reset-db`).
  - This only affects local/dev environments using the bundled Dex; it does not affect real IdPs (Keycloak, etc.), which already configure their own public-reachable issuer independently of this change.

### Fixed
- The scope doc claimed `GET /rooms/{roomId}/joined_members` was supported ("Compact map of joined members"): it is not routed (`404 M_UNRECOGNIZED`), corrected by story membership-state-model (follow-up `gh`).

- **State events carry `unsigned.prev_content` / `prev_sender`; Element marks an accepted DM invitation as a direct chat (follow-up `ff`, e2e known failure K10)**: every state event delivered through `/sync` (joined state and timeline, `rooms.leave` timeline), `GET /rooms/{roomId}/messages`, `/event/{eventId}` and `/relations` now carries, together with `unsigned.replaces_state`, the predecessor's content (`unsigned.prev_content`) and sender (`unsigned.prev_sender`) when the slot has a predecessor (one batched lookup, no extra statement per event; `rooms.invite` stripped state is unchanged). Element reads them on the invitee's own join to write the room into `m.direct`, so a direct chat you accepted is a direct chat (People list) instead of an anonymous group room; a declined invitation now reads "rejected the invitation" instead of "left", a withdrawn one "withdrew the invitation". The user's own join, leave and decline are stamped strictly after the latest member event of the room, so an invitee who joins immediately after `createRoom` still answers the invite. `prev_sender` and `replaces_state` are Synapse-compatible extensions outside the Matrix v1.18 text; the keys are delivered whatever the room's `history_visibility` (known deviation, follow-up `es`).

### Security

- **⚠ History visibility is enforced on every event read path (story history-visibility-enforcement; follow-up `es` closed; behaviour change, no migration)**: in a room whose `m.room.history_visibility` is `invited` or `joined`, members who are invited or join later no longer see the events from before their invitation / join: `/messages`, the initial and the incremental `/sync` timeline (incl. thread roots), `/event`, `/relations`, `/search` (each result is checked) and `/initialSync` serve only the events the caller may see, and `unsigned.prev_content` / `prev_sender` / `replaces_state` are omitted when the predecessor is not visible. ONE SQL fragment in `Room.DB` decides it inside the existing statements (the spec's rules at each event's position; no extra statement); a failing read fails closed. `shared` rooms (every preset, every room without the setting) are unchanged; the current state stays visible to joined members; events stay stored. Read cost (security cycle 1): the visibility SQL is O(B log B) in the room's history-visibility events and the reader's member events, a room holds at most 256 history-visibility events (`429 M_LIMIT_EXCEEDED` above; the cap never blocks tightening: a strictly more restrictive change still passes), a PUT of `m.room.history_visibility` / `m.room.guest_access` / `m.room.join_rules` costs a `moderation` token, and the request reads run under a 2 s statement timeout (`500`; not the `/sync`). Operators: the read-only queries Q-hv1 (the rooms whose CURRENT setting is `invited` / `joined`; a room that was restricted earlier and changed back keeps a hidden segment and is not listed) and Q-hv2 (the cost inputs) in `docs/architecture/07-deployment.md`.

## [0.2.1] – 2026-05-20

### Fixed

- **Stackit deployment — Matrix SSO redirect URI**: `ssoCallbackURL` now respects `NEBU_TRUSTED_PROXY=true` and trusts `X-Forwarded-Proto: https` from nginx, building `https://` redirect URIs instead of `http://` when behind a TLS-terminating reverse proxy. Refactored `isRequestSecure` into `internal/middleware` (shared with admin auth handler).
- **Stackit deployment — database migrations**: migration SQL (`000001_init.up.sql`) now grants `SELECT`, `INSERT`, `UPDATE`, `DELETE` on all application tables and sequences to `nebu_app` after creation. Required when running migrations as a dedicated `nebu_migrate` role (dual-role deployment). Function grants are scoped explicitly to avoid errors from extension-owned functions (`set_user`, `pg_stat_*`).
- **Stackit deployment — PostgresFlex ACL**: database ACL now includes the VM's floating IP (`stackit_public_ip.nebu.ip/32`) alongside the VPC CIDR. Docker container traffic reaches PostgresFlex via the public IP, not via internal Stackit routing.
- **Stackit deployment — runtime environment variables**: `NEBU_ENV`, `NEBU_KEY_ENCRYPTION_KEY`, and `NEBU_TRUSTED_PROXY` are now provisioned via `cloud-init` from Terraform variables (`nebu_env`, `key_encryption_key`). Previously required manual post-deploy configuration. `NEBU_TRUSTED_PROXY` is derived automatically from `enable_tls`.
- **Stackit deployment — Dex static users**: additional demo users (`alice@example.com`, `bob@example.com`, `compliance@example.com`) can now be provisioned via optional `dex_user1_password_hash`, `dex_user2_password_hash`, `dex_compliance_password_hash` Terraform variables. Users are gated behind `%{ if ... != null }` to keep existing deployments unchanged.
- **Secret scan**: `terraform.tfstate.*.backup` (numbered OpenTofu state backups) added to `.gitignore`; accidentally committed backup removed from tracking.

## [0.2.0] – 2026-05-20

### Added

- **Element Web integration** (Stackit deployment): optional `enable_element_web` Terraform variable deploys Element Web as a Docker service alongside Nebu. Includes nginx routing, CORS precondition enforcing `enable_tls`, and an `element_url` Terraform output.
- **Certbot-managed TLS** (Stackit): replaced ACME DNS-01 challenge with certbot HTTP-01 on the VM. Removes `vancluever/acme` and `hashicorp/tls` Terraform providers; auto-renewal via systemd timer baked into `cloud-init`.
- **Stackit Logs integration**: optional `enable_logs` / `logs_retention_days` Terraform variables ship `nebu.service` logs to Stackit Observability.
- **Stackit network resources**: dedicated Tofu-managed network, security groups, and ALB configuration extracted into separate `network.tf`, `alb.tf`, `dns.tf`, `database.tf`, and `logs.tf` modules.
- **PII encryption at rest** (`pii_encryption_key` variable): 64-character hex key validated at plan time; injected into the gateway via environment override in `cloud-init`.
- **`m.login.token` advertisement**: login flow now advertises `m.login.token` alongside `m.login.sso`, preventing redundant SSO re-initiation in Element Web 1.12+.

### Fixed

- **SSO URL fragment handling**: login tokens are now inserted before the URL fragment (`#`) in redirect URLs, fixing broken redirects in hash-based SPA routers (Element Web, Cinny).
- **Gateway migration squash** (story 13-14): consolidated 49 schema migrations into a single seed migration `000001_init.up.sql`, resolving role-dependency failures on Stackit PostgresFlex and other managed PostgreSQL services where `nebu_migrate` / `nebu` roles are provisioned outside of migrations.
- **Element Web nginx routing** (security): added `/api/v1/` gateway proxy block and WebSocket upgrade headers to the Element location block; previously, these API calls were silently unreachable from Element Web.
- **E2E bootstrap tests**: fixed `PROJECT_ROOT` path resolution (was 3 levels up — pointed to `e2e/` instead of project root, causing all database resets to silently fail); fixed `DEX_ISSUER_URL` undefined-at-module-load-time `ReferenceError` in step definitions.
- **WCAG AA contrast** (Admin UI): `primary-content` token `#fff7ed → #1c1917` (5.98:1 contrast ratio), `error-content` token `#450a0a → #000000` (5.9:1); removed duplicate `role=region` / `aria-label` landmark on the dashboard live-metrics div (WCAG SC 4.1.2).
- Removed redundant `--quiet` flag from Makefile E2E targets for consistent log output across CI and local runs.

### Changed

- Stackit PostgreSQL default CPU flavor updated to 2 cores in Terraform variable defaults.
- Docker Compose `healthcheck` for Element Web container uses `nginx:alpine`-bundled `wget` (no curl dependency).

## [0.1.0] – 2026-05-17

First official release of Nebu — enterprise Matrix chat server.

### Highlights

**Matrix Client-Server API** — login, logout, sync, send, createRoom, join, profile, presence, receipts, typing, media upload/download/thumbnails, push rules, devices, account_data, tags, public rooms, event context, notifications, moderation, room state, joined members, aliases, MSC2965 OIDC discovery endpoints.

**Core architecture** — stateless Go API Gateway + Elixir/OTP Core (Horde, libcluster, ETS) communicating via gRPC. PostgreSQL 16 as append-only event log. No Redis, no NATS, no Kafka.

**Authentication** — OIDC-only (Authorization Code + PKCE). MSC2965 `auth_issuer` / `auth_metadata` discovery. Dex sidecar mode for dev; Keycloak / Azure AD / Google Workspace compatible.

**Admin UI** — Bootstrap Wizard (first-run setup), dashboard with SSE live metrics, user management, room management, compliance access requests, audit log viewer, server configuration, role mapping, OIDC user directory search.

**OIDC user directory** — OIDC endpoint (Dex/Keycloak) for live user search + SCIM 2.0 RFC 7644 bulk import (Azure AD / Okta).

**Security** — Ed25519 message signatures and X25519 encryption key pairs per user; rate limiting (5 tiers); CSRF double-submit cookie; security headers (CSP, HSTS, X-Frame-Options); body size limits; Slowloris protection.

**Compliance** — Four-eyes approval for compliance access, signed JSON/PDF export, GDPR Article 17 right-to-erasure, audit log retention scheduler.

**Full-text search** — PostgreSQL `tsvector`-based message search.

**Media Gateway** — AES-256-GCM encrypted upload/download, MinIO S3-compatible backend.

**Deployment** — Kubernetes/Helm, AWS ECS Fargate, Stackit VM + Docker Compose. Let's Encrypt TLS via ACME DNS-01 for Stackit deployment.

**CI/CD** — GitHub Actions + GitLab CI dual-host pipeline. Secret scanning (gitleaks). SemVer release stage (Kaniko).
