Structural-position redaction is unsafe for Matrix payloads. Recurring gaps in `payload_redactor.ex` (enhanced-logging/matrix-payload-debug-logging, 2026-07-05):

1. **Wrapper assumption (CRITICAL, F1).** Category-2 (message content) redaction only fired when a key named `content`/`prev_content` was present. But Matrix WRITE endpoints send the event content as the raw top-level request body with NO wrapper: `PUT .../send/{eventType}/{txnId}` and `PUT .../state/{eventType}/{stateKey}` bodies are `{"body":..,"msgtype":..}` / `{"topic":..}` / `{"name":..}` directly (`protected.ex:693,1756`, `content = body_params(conn)`). RequestLogger logs `conn.body_params`, so top-level user text leaked. The READ path (sync/messages) wraps in `content` and passed all tests — masking the write-path hole.

2. **Metadata allowlist over-shadow (HIGH, F2/F3).** An allowlist of "structural metadata keys" that survive redaction hid genuine user text: `m.relates_to` in the list → reaction `key` leaked; `reason` in the list → kick/ban/redaction free-text leaked.

3. **Fixed field-name list is a HALF-FIX for the write path (HIGH, cycle-5 residual of F1).** The dev's cycle-5 fix added `@always_content_keys` (a FIXED list: body/formatted_body/filename/topic/name/displayname/reason) masked at any depth, PLUS the original "any non-metadata key inside content ⇒ content" catch-all. But that catch-all is gated on `in_content? = true`, which NEVER holds for the wrapper-less write body (`redact_payload` is always called with `in_content? = false`). So on the write path, ONLY the fixed list is masked — every other content field still leaks: `m.location.geo_uri` (plaintext GPS PII), custom-event fields (`com.example.*`), poll question/answer text, `m.room.encrypted.ciphertext`. Tell-tale: the read-path test masks `custom_field` (proving intent) but there is NO write-path test for it or `geo_uri`. The only structurally-complete fix is route-aware `redact_payload(body, in_content?: true)` for send/state bodies (treat the top-level write body AS a content object) — a fixed key list can never be exhaustive because event content field names are open-ended.

**Why:** Phil's no-sensitive-data-in-logs LAW is absolute — message content must never appear even at DEBUG (GDPR-equivalent; `geo_uri` is literal user location). Redactors must be verified against BOTH read and write payload shapes, and against OPEN-ENDED custom/event-type-specific field names, not just the wrapped read shape the tests favor.

**How to apply:** For any log/payload redactor review — (a) redact user-text by treating the whole event-content object as content (position + name), not a finite key list; (b) treat every allowlist entry adversarially: is this key EVER user-generated free text (`reason`, `key`, `displayname`, `geo_uri`)? (c) demand WRITE-path (send/state PUT, unwrapped) tests for a CUSTOM/non-standard content field and `geo_uri`, not only wrapped read-path/sync tests; (d) when a dev picks the "field-name list" option over the "treat body as content object" option, re-derive whether the list can ever be complete — for open event schemas it cannot. Related: [[stale-cross-file-comments]].

4. **Cycle-6: send/state fixed the RIGHT way, but the same limitation bites OTHER write endpoints.** Cycle 6 landed the correct structural fix — `redact_payload/2` with `in_content?: true`, wired route-aware in `request_logger.ex` via `write_path_content_body?/1` matching `@send_event_path_regex`/`@state_event_path_regex` against `conn.request_path` (immune to `forward` path_info-stripping; query string is NOT in request_path so it can't break the match; no GET/POST route shares the send/state shape so method-agnostic matching is fail-closed — over-match only over-redacts). geo_uri/custom/ciphertext now masked on send AND state. BUT the field-name-list is still the ONLY defense on every OTHER user-text write endpoint that isn't send/state: `POST /search` `search_categories.room_events.search_term` (user's query, nested) and `PUT /presence/{u}/status` `status_msg` leak verbatim at DEBUG (flagged N1/N2, MEDIUM). Also `PUT /user/{u}/account_data/{type}` = arbitrary user JSON (N3, LOW). Lesson: when you approve a route-aware content fix, immediately enumerate ALL write routes carrying user text (grep `put|post` in the router), not just the two the finding named — the redactor's structural gap is global, the fix was local.

**Refined how-to-apply:** (e) After a route-aware `in_content?`-style fix, grep the ACTUAL router for EVERY `put`/`post` route and ask "does this body carry user text at a key not in @always_content_keys?" — send/state are the loud cases; search_term, status_msg, account_data are the quiet ones. (f) Verify regex fixes against the registered route list (API version, optional trailing path segment like empty state_key, room_id URL-encoding, trailing-slash 404 fallback) — confirm no real write route regresses to the default gapped path.

**Epic-end status (SEC Gate 2, enhanced-logging, 2026-07-08):** N1/N2/N3 (search_term / status_msg / account_data) are STILL UNRESOLVED at epic close — `@always_content_keys` in payload_redactor.ex remains `body formatted_body filename topic name displayname reason`, and RequestLogger only wires `in_content?: true` for send/state. Carried forward as the epic's one open MEDIUM. NOT elevated to HIGH because there is NO admin-UI/unauth path in this epic that raises the effective global `Logger.level` to `:debug` (war-room does NOT raise it; per-route `log_min_level_<route>` keys are written+display-only, never consumed to emit; temporary-capture only gates persistence) — so the payload closure only runs when an operator has set global `:debug` via console `Logger.configure/1`. Leaked data is user text/PII (search queries, presence status, account_data prefs/encrypted-blobs), not credentials (credentials ARE covered). Recommend closing before the field-name list drifts further behind Matrix's schema.
