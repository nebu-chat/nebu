Rule: when a story attaches a GENERIC Erlang `:logger` handler that persists intercepted events to a durable, admin-readable DB table (Nebu.Web.LogStore, enhanced-logging/operational-log-store, 2026-07-05), do NOT accept the module's "we rely on upstream redaction (PayloadRedactor)" docstring at face value. That assumption only covers the ONE caller that runs the redactor (RequestLogger's payload line). The handler intercepts ALL `Logger.*` (~140 call sites) PLUS OTP/SASL crash reports, none of which run any redactor.

**Why:** Phil's no-sensitive-data-in-logs LAW must be re-checked for the DURABLE sink, not just transient console/file. The three holes found (all MEDIUM, none blocking, but foundation-story surfaces for the dependent UI/retention/war-room stories):

1. **[RESOLVED 2026-07-06, admin-logs-retention-settings]** ~~Always-on WARN/ERROR tier has NO retention.~~ Now capped by a hardcoded (non-admin-configurable, no server_config key, no UI) 90-day safety-net TTL in `Retention.prune_operational_logs/0` (`@warn_error_safety_net_days`, `prune_ttl("warning"/"error", 90)`). Disk-exhaustion + GDPR-storage-limitation gap closed. NOTE the GDPR *crypto-shred* mismatch (hole below / point 2) is NOT closed by a TTL — warn/error rows still embed user_id/room IDs for up to 90 days and remain outside `UserDeletion`'s erasure scope. Original text: `Retention.prune_operational_logs/0` only prunes info/debug (TTL) and debug (max-count). `should_persist?/1` persists warn/error unconditionally and forever. So (a) unbounded table growth / disk-exhaustion DoS under an error storm, and (b) GDPR storage-limitation gap — warn/error rows embed `user_id`/room IDs (e.g. server.ex:1666 `Logger.error("validate_token failed", user_id: user_id)`) and outlive the crypto-shredding erasure flow (`Nebu.Compliance.UserDeletion` NULLs keys, never touches operational_logs). The story's claimed compensating control (retention) does NOT cover the tier that is always collected.

2. **Crash reports + arbitrary metadata persisted verbatim.** `render_msg({:report, report})` inspects the whole report; `safe_metadata` keeps every metadata key except a bookkeeping DROP-list (not an allowlist). A GenServer crashing with a token in `:last_message`/`:state`/exit-args leaks it at ERROR level (always, forever). Prefer: drop/truncate `:report` on the persist path; switch metadata to an allowlist; cap message length.

3. **PubSub fan-out is unconditional.** Handler broadcasts EVERY entry (incl. DEBUG payloads) to topic "operational_logs" regardless of persistence policy — the later admin/war-room live view MUST gate subscription behind admin auth and treat DEBUG payload lines as sensitive even when debug persistence is off.

**How to apply:** For any "persist logs to a table / forward logs to a durable sink" story — (a) enumerate EVERY Logger.* call site (`grep -rn "Logger.(info|warning|error|debug)" server/lib`) and grep for credential/content terms; verify the specific noisy callers (Ecto QueryTelemetry — must log source/duration/result only, never :query/:params/exception; token/session stores — hashes/JTIs/reasons only, never raw secrets). (b) Confirm EVERY persisted level has a retention bound — an "always collected, never toggled" tier with no TTL/max-count is both a DoS and a GDPR gap. (c) Treat OTP crash reports as an intercepted, unredacted input. (d) Check the erasure model: Nebu erases by CRYPTO-SHREDDING keys + deactivation, NOT by deleting user_id references across tables — any new plaintext-identifier table is outside erasure scope by default. (e) RLS allowlist for new server_config keys: FOR UPDATE `USING (key IN (...))` with WITH CHECK omitted is correct (Postgres reuses USING as the row-check) — matches the key-scoped pattern, contrast the permissive migration 000045. Related: [[redaction-wrapper-assumption]] (the field-name-list gap that this durable sink now makes permanent for search_term/status_msg/account_data at DEBUG).
