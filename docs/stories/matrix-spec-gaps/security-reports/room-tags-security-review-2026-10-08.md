### Detail

**Finding #1: Tag names in the INFO request log** [MEDIUM]
`RequestLogger` logs `path: route_template` with `route_template = RouteNormalizer.normalize_route(conn.request_path)` (request_logger.ex:69/102). `@anchor_rules` replaces `send`/`state`/`redact`/`devices`/`account_data` segments, but there is no rule for `tags`. `/_matrix/client/v3/user/:user_id/rooms/:room_id/tags/u.client-secret-x` is logged as it is, the user and room get placeholders, the tag name stays. Logging happens at INFO (always on stdout, so container and log shippers). It is persisted in `operational_logs` when `log_collect_info` is on, and it is visible in the admin live stream, which according to the admin-logs-monitoring-view F-1 is not filtered by policy. That means operators and log readers see a user's private room labels (e.g. `u.Bewerbung`, `u.Anwalt`), with the user as `metadata.user_id`. This is no exploit for a privilege gain, but it is a privacy/data exposure to insiders and long-lived logs. It also contradicts AC6 directly, and the Dev Agent Record ("the tag NAME is part of the logged request path") and the test (room_tags_test.exs:1177) defend that decision. The account-data `type` already gets a placeholder, so tag names should be treated the same. Side effect: every tag name creates its own `route_template` (cardinality for endpoint grouping / War Room scope). Fix: see table. With #2 the rule also covers the `%74ags` and `//` variants that the story test already sends.

**Finding #2: Normalizer anchor comparison is not router-identical** [LOW, existed before]
`Enum.find_index(segments, &(&1 == anchor))` on `String.split(path, "/")` without decoding or dropping empty segments. The router (`Plug.Router.Utils.decode_path_info!` = `URI.decode` on adapter `path_info` without empty segments) executes such paths anyway. The leak therefore affects even the account-data type that is already protected. This is the same lesson the previous story learned for the body matchers. This time it applies to the normalizer.

### Verified clean (no finding)

- **IDOR / authorization (CWE-639/285):** all five handlers reject `user_id != current_user` (server-derived MXID, OidcPlug runs before `:match`) with 403 before any DB access. That also holds for admins: there is no admin bypass. The store is always called with `authenticated_user`, every SQL statement filters `user_id = $1`. GET returns only your own `m.tag`.
- **Existence leak:** check order: user → roomId syntax → tag name → body (PUT) → `require_room_member` → store. None of the earlier checks depends on the room. Unknown room and non-member give an identical 403 M_FORBIDDEN body (`require_room_member` maps 404 to 403). DELETE also checks membership, even when nothing is stored.
- **Atomicity (AC3):** `update/4` takes `lock_user` as the first statement in the transaction, then SELECT, `fun`, `upsert!` (caps plus `nextval` under the lock), commit, and only then `notify_sync` (`finish_write` after `Repo.transaction`). Every writer of `user_room_account_data` (`put/4` room account data and `m.fully_read`, `update/4`) takes the same lock, and the only other statement is the GDPR DELETE. No lost updates, and `stream_pos` order equals commit order. `:unchanged` writes nothing and wakes nothing. Direct PUT of `account_data/m.tag` against tag PUT is serialized, last writer wins on the whole event, never corrupted.
- **Caps / accumulation:** the re-encoded event is checked against `max_bytes` (64 KiB) under the lock, so growth from re-encoding (e.g. `1e5` becomes `1.0e5`) is caught. Total and row caps are re-checked in `upsert!` under the lock with the NEW minus OLD delta. A tag in a room that already has an `m.tag` row does not create a new row. Raw body ≤64 KiB before decoding, parser cap 1 MB, `{:more,..}` counts as oversized.
- **Rate limit:** PUT/DELETE (including the nameless variants) go through `@account_data_write_rate_limit` (key `{tier, current_user}`, after auth, not spoofable) BEFORE validation and lock. A lock storm only hits your own per-user lock.
- **Malformed stored `m.tag`:** `decode_tag_event` falls back to `%{}` for non-objects, `tags_of_event` to `%{}` for non-map `tags`, and unknown top-level keys are kept. `Jason.encode!` cannot fail on Jason-decoded data: Jason validates UTF-8, rejects lone surrogates, and an overflowing float (`1e400`) gives a decode error and therefore 400, not 500. `order` is checked with `is_number`. Integers keep full precision (bigint), floats re-encode shortest, `-0.0` stays `-0.0`, and `order` outside [0,1] is accepted by design (spec).
- **Tag-name validation:** the router param is already `URI.decode`d. `""` (also `.../tags`, `.../tags/`) gives 400. The 255-BYTE limit is checked after decoding. `%FF` (invalid UTF-8) and `%00` give 400. `%2F` becomes the name `a/b` (segment count unchanged, matcher consistent). A malformed `%G1` is rejected as 400 by the router. The name is never echoed in an error.
- **Path matcher (router-identical):** `room_tags_shape?/1` drops empty segments and decodes each segment, exactly like `Plug.Router` (`%74ags`, `//`, trailing slash OK). Case variants (`Tags`) are routed by neither the router nor the matcher. `_version` as a wildcard is a fail-safe over-approximation: there are no r0 routes, so the catch-all gives 404 and nothing stores `{}`. No overlap with the account-data shapes (different literal and position). `JsonBody` swallows RequestTooLarge only for PUT on these exact shapes. Every such handler checks `:body_too_large` before any write, or rejects nameless writes with 400 first. The account-data matcher behavior is unchanged (regression check OK).
- **Body/response capture:** `account_data_content?/1` → `opaque_content_shape?(request_path)` (split + reject `""`, i.e. path_info semantics, closes the earlier #13 class) covers all tag shapes and methods. No new `Logger`/`inspect` calls with content in the store or handlers. 500 is a static `M_UNKNOWN`.
- **GDPR / cascade:** `m.tag` rows live in `user_room_account_data` and are covered by `user_deletion.ex:204` (DELETE by user_id) and FK `ON DELETE CASCADE` (migration 000035, unchanged).
- **SQL:** all new statements are parameterized. The only interpolation is the module constant `@exempt_type` (unchanged). No new env vars, no test seams in `lib/` (`put_env` only in tests).
