### Detail

**Finding #1 — Oversized global account-data PUT silently overwrites with `{}`** [MEDIUM]
`JsonBody.call/2` now rescues `Plug.Parsers.RequestTooLargeError` whenever `RawBodyReader.account_data_path?/1` is true. In that case it sets `body_params: %{}` and `:body_too_large`. The new room route checks the flag (protected.ex:675). The pre-existing global route (626-647) does not. It goes straight to `Jason.encode!(body_params(conn))`, which gives `"{}"`, and then to `AccountDataStore.put/3`, which returns 200. Before this diff the error re-raised and Plug answered 413. Matrix clients (Element) store secret-storage keys, cross-signing material and key-backup config in global account data. A client that sends an oversized update (bug, or a future large payload) would lose the existing value without any error. No attacker can trigger this for another user (Bearer auth, user==auth guard), so it is not HIGH. It is a regression introduced by this diff and should be fixed before merge: one extra cond branch plus a test.

**Finding #2 — No aggregate cap: per-user ~64 MB delivered per /sync** [MEDIUM]
`max_rows_per_user × max_bytes = 1000 × 65_536 ≈ 64 MB`. `list_for_sync/3` returns all rows with `stream_pos > since_pos`, and `since_pos` comes from the client's token, so `.0` is always allowed. The text rows, the decoded maps and the final `Jason.encode!` response all sit in the request process at the same time. With a burst of 100 concurrent syncs per user (sync tier) the node can be pushed into OOM by one account after ~1000 unthrottled PUTs. The bound exists, which is why this is MEDIUM rather than HIGH, but it is far too high for the actual payloads (m.marked_unread/m.fully_read/m.tag are a few hundred bytes).

**Finding #3 — Account-data content in DEBUG payload capture** [MEDIUM, carried class]
At DEBUG, RequestLogger logs `redacted_request_body` and `redacted_response_body`. For the new PUT/GET routes the payload is the raw content object, which has no `content` wrapper, so `PayloadRedactor.redact_payload/1` without `in_content?` leaves non-credential keys untouched. Tag names, marker values and any client-defined user text are logged verbatim. This only fires under operator-raised global :debug, consistent with the open enhanced-logging F-1, which this diff extends to two new routes.

### Verified clean (no finding)

- **IDOR / authorization (CWE-639/285):** PUT and GET reject `user_id != current_user` (server-derived MXID from OidcPlug) with 403 before any DB or room lookup. The store is always called with `authenticated_user`, never the path value. Every SQL statement (`get`, `put`, `pending?`, `list_for_sync`, erasure) filters `user_id = $1`. A forged token position can only select the caller's own rows. `list_for_sync` additionally restricts to rooms with active membership (`left_at IS NULL`), so extra_rooms / full_rooms cannot surface rooms the user is not in. No admin bypass path.
- **Check order / existence leak:** user → server-managed type → roomId syntax → type length → body size → JSON object all run before `require_room_member`. Unknown room and non-member give an identical 403 M_FORBIDDEN body (both map to "You are not a member of this room").
- **`ensure_room_member!/2` extraction:** the body is byte-identical to the former inline membership block. `send_receipt/2` still calls it before `upsert_receipt`, so /receipt authorization has no regression. read_markers calls it first for every marker. m.read/m.read.private go through `send_receipt`. m.fully_read is validated with `event_in_room?(room_id, event_id)` (parameterized) before any write.
- **405 server-managed types:** enforced in both scopes. The room scope uses the Plug-decoded type, the global scope the double-decoded type, and in each case the same value is checked and stored, so encoding cannot smuggle `m.fully_read`. The only m.fully_read writer is read_markers, with a server-built `{"event_id": ...}`.
- **SQL injection:** all queries are parameterized ($1..$6, `ANY($3::text[])`). The advisory key is `hashtextextended($1,0)` with a bound parameter.
- **Advisory lock:** per-user transaction-scoped lock, held only for one INSERT…ON CONFLICT. A 64-bit hash collision with another user or with `@bootstrap_lock_id` is negligible and would only serialize briefly. No lock ordering with other locks, so no deadlock. The commit-order guarantee holds: nextval is drawn under the lock (DEFAULT on insert, SET on update), and the reader's MAX(stream_pos) comes from a single-statement snapshot.
- **Body limit:** for JSON content-types the parser cap is 1 MB (`read_body` length, `{:more,..}` → too_large). `raw_body` is cached only for complete bodies ≤1 MB on account-data paths. For non-JSON content-types `raw_request_body` reads with `length: max_bytes+1` and treats `{:more,..}`/error as oversized (413). The 64 KiB check runs after the read but within the 1 MB bound (advisory, same as all routes).
- **Poison row:** PUT requires `Jason.decode` → map (JSON object). m.fully_read is server-encoded. `decode/1` in `/sync` falls back to `%{}`, so no row can corrupt a sync response.
- **Migration:** FKs ON DELETE CASCADE to users/rooms. Room hard-delete (room/db.ex rollback) and user deletion are not blocked, and the cascade touches only this table (audit_log untouched). Down migration drops table and sequence. Grants are least-privilege. Index `(user_id, stream_pos)` serves `pending?` and `list_for_sync`.
- **Logging:** no new Logger/inspect of content in the store or handlers. Error bodies are static, with no DB reason echoed (500 M_UNKNOWN). The pre-existing `inspect(reason)` in the `upsert_receipt` raise message is not sent to the client (`map_error` → static message).
- **Test seams:** none added to production code. Config is read via `Application.get_env` with defaults.

### Still valid (re-verified)

The IDOR guard (`user_id != current_user` → 403 before any DB access) still holds in all four handlers. The global scope now uses the router-decoded parameters for both the check and the store (no double decode), so the check and the stored key are identical. The room scope still stores content verbatim (raw bytes). All SQL is parameterized; the only interpolation is the module constant `@exempt_type`. The advisory lock is held for one statement (two sub-sums over at most about 1000 user rows, index `(user_id, stream_pos)`). The migration is unchanged. The new environment variables are parsed strictly (`{n, ""}`, 1..int8 max, otherwise the default applies) and never crash. The new `key:` plug option defaults to `:ip`, so existing tiers are unaffected. The raw body is cached only for account-data PUTs, at most 1 MB, and those requests are rate-limited.

### New findings

**#12 — Global PUT with a non-JSON Content-Type or an empty body still overwrites with `{}`** [LOW, existed before this diff]
`server/lib/nebu/web/router/protected.ex:691-693` (`global_body_object?/1`: no `raw_body` or `""` → `true`). With `pass: ["*/*"]`, Plug does not read the body for `text/plain` or a missing Content-Type, so `body_params = %{}` and `{}` gets stored. A body of any size skips the 413 check. An empty `application/json` body also gives `{}`. This is not exploitable by anyone else (only the token holder can write their own data), but a buggy client could silently destroy secret-storage or cross-signing material. Recommendation: mirror the room scope by reading the body yourself via `raw_request_body/1`, so oversized → 413. Then reject an empty or non-object body with 400 `M_NOT_JSON` instead of returning `true`.

**#13 — RequestLogger path split differs from Plug `path_info`** [LOW]
`server/lib/nebu/web/plugs/request_logger.ex:225-227` uses `String.split(request_path, "/", trim: true)`, which only removes LEADING and TRAILING empty segments. The adapter's `path_info` drops ALL empty segments. So a request like `PUT /_matrix//client/v3/user/@u:x/account_data/m.secret_storage.key.X` reaches the handler (router and JsonBody see the normal shape), but the logger does not recognize the shape and captures the body at DEBUG (only `PayloadRedactor`, no content redaction). This only matters at DEBUG and needs a malformed client URL. Recommendation: normalize to `path_info` semantics, e.g. `String.split("/") |> Enum.reject(&(&1 == ""))`, and add a test with `//`.
