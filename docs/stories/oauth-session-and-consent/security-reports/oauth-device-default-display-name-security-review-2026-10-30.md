# Security Review: oauth-device-default-display-name (Kassandra, cycle 0)

Date: 2026-10-30. Scope: staged `Nebu.OAuth.DeviceName` (new), `Token.issue_session` (authorization_code grant only, not refresh), `OAuthSessionStore.insert_replacing_device` (conditional UPDATE inside the issuance transaction). **Verdict: APPROVED (CLEAN: 0 CRITICAL, 0 HIGH, 0 MEDIUM).** 2 LOW, 1 INFO.

| # | Severity | Location | Finding | Remediation |
|---|----------|----------|---------|-------------|
| 1 | LOW | device_name.ex:61-65 | Combining marks (\p{M}, "Zalgo") and invisible letters that are not Cf/Zs (U+3164 HANGUL FILLER, U+115F, U+2800 BRAILLE BLANK) pass the sanitiser; a name made only of these renders as an almost blank `"  (ABCD1234)"` in Element, FluffyChat and the admin UI. Length stays capped at 64 code points (~256 bytes). | Drop \p{M} without a base letter (or cap marks per base), denylist U+115F, U+1160, U+3164, U+FFA0, U+2800; fall back to "OAuth client" when no letter/number is visible. |
| 2 | LOW / INFO | device_name.ex:45-50 | Homoglyphs/impersonation not handled (Cyrillic "Еlement", "Nebu Security", a name faking a suffix "Element (ABCD1234)"); names also show in the account page's cross-signing reset request (account_pages.ex:391). Main control: only the client_name of an approved client is used and an admin reviews it (rendered escaped) at approval; the device suffix is always added and not client-controllable. | Accepted residual risk; optionally a confusable/mixed-script warning on approve_confirm. |
| 3 | INFO | token.ex:339 | One extra `ClientStore.fetch_by_client_id` SELECT per code exchange, even when the device already has a name; runs only after code, PKCE and client checks (no amplification). | none |

## Verified clean
Unapproved clients (name only taken when `status == "approved"`; pending/rejected/revoked/unknown, non-binary id, DB error or raise -> "OAuth client"; revoked between read and issuance -> the in-transaction CR5/CR6 check rolls everything back incl. the UPDATE). No overwrite (`WHERE user_id=$1 AND device_id=$2 AND display_name IS NULL`; the upsert passes no name; L-1 `device_in_use` rollback undoes the UPDATE). SQL injection (bound $1-$3). No cross-user leak (own client metadata + own device id only). Markup, bidi, NUL, log injection (`< >` removed; Cc, Cf incl. RLO/LRO/isolates/ZWSP/ZWJ/tags, Zl/Zp, Co, Cs dropped; invalid UTF-8 -> fallback; suffix filtered to `[A-Za-z0-9._-]` with SHA-256 hex fallback). Rendering (admin users/show.html.heex:40/62 HEEx-escaped; account_pages.ex:287/349/391 escaping engine, `raw` only for compile-time literals; GET /devices JSON). Logging (no new lines; debug body capture of GET /devices is a known follow-up outside this story). GDPR (devices.display_name already erased, pinned by device_name_erasure_test.exs).
