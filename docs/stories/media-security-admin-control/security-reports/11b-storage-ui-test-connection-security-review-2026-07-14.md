## Detail

### M-1 — MEDIUM — Scheme-prefix guard is a partial mitigation; private-IP SSRF + transport downgrade remain, now on a live S3 call

11a's M-1 was scored MEDIUM/**forward** because `get_for_connection/0` had zero live callers. 11b wires the first real consumer: `test_connection/1 → default_test_connection/1 → ExAws.S3.head_bucket |> ExAws.request(config_overrides(candidate))`, where `config_overrides/1` sets `host`, `scheme`, `port` directly from the candidate. The dev agent added `validate_candidate_endpoint/1` (module) and `invalid_endpoint_scheme?/1` (controller) — both reject only a `http://`/`https://` **scheme prefix** (after downcase; inputs are `String.trim`ed, so leading-whitespace and case evasions are covered). That closes the "scheme confusion / `USE_SSL=false` temptation via a URL" half of MEMORY #56.

What remains open (explicitly noted by the dev agent as out-of-scope, and correct to re-raise here):

- **Private-range SSRF.** A bare host (`169.254.169.254`, `10.x`, `127.0.0.1`, `metadata.internal`, `127.0.0.1:9000`) passes the scheme check and becomes a server-originated HEAD against internal infra. `test_connection` returns only `:ok` / a fixed generic error, so this is a **blind** SSRF — an internal existence/port-scan oracle, not a data-exfiltration primitive (no response body reflected). No rate floor on the action, so it is a repeatable oracle.
- **Transport downgrade.** `use_ssl:false` + real (or blank→stored) credentials sends S3 creds over plaintext HTTP — MEMORY #56's second half.
- **Inconsistency.** This same controller pins `webhook_url` through `Nebu.Media.SSRF.check/1` (which resolves the host and rejects RFC1918/loopback/link-local/ULA). The storage endpoint — a functionally identical admin-configured-outbound-target (MEMORY #44/#50) — gets only the weaker scheme check. The remediation tooling is already imported into this module.

**Why MEDIUM, not HIGH:** exploitation requires **admin** credentials (not a standard user), the SSRF is blind, transport-downgrade is self-inflicted operator config, and `test_connection` never persists. Consistent with 11a's own severity. **Non-blocking**, but this is the live instance 11a's verdict said to verify — it should be closed (SSRF host-resolution rejection at the `test_connection/1` and `save_storage/2` boundaries) before epic end, ideally reusing the `Nebu.Media.SSRF` path for parity with `webhook_url`.

### L-1 — LOW — Failure-path `inspect(reason)` can embed the access key ID (and, via a config-bearing exception, the plaintext secret) in the server log

The task specifically asked whether `test_connection/2`'s `Logger.warning(inspect(reason))` could leak. Findings:

- **Browser: CLEAN.** All three response branches (`:ok`, `{:error, :invalid_endpoint}`, `{:error, reason}`) render fixed constant strings (`@storage_generic_failure_message` / `@storage_invalid_endpoint_message` / "Connection succeeded.") — a raw ExAws/`:hackney` struct is never interpolated into the HTML, and no signed-URL query string can reach the response. The story guardrail is satisfied.
- **Server log: LOW.** `default_test_connection/1` returns `{:error, reason}` where `reason` is ExAws's error term. For S3 auth failures the response XML embeds `<AWSAccessKeyId>` — the access key **ID** (an identifier of the same class as a username, not the secret). More importantly, the `rescue e -> {:error, e}` branch returns the raw exception; because `config_overrides/1` carries the plaintext `secret_access_key`, an ExAws exception type that embeds its config would put the plaintext secret into the log line. This is speculative (the common ExAws paths return clean tuples), server-log-only, and admin-context — hence LOW — but it is trivially closed by returning `Exception.message(e)` / a tag from the rescue rather than the raw struct.

### L-2 — LOW — Masked secret present in the render assign though unrendered (latent 11a-L-3 exposure)

`render_settings/3` computes `current_storage_cfg = StorageConfig.get()` and assigns it (or the params echo) as `@storage_config`. `get/0` returns `access_key`/`secret_key` in `mask_secret/1` form — last-4 for normal secrets, and per 11a-L-3 the **entire** value for a secret ≤4 chars. The template does the right thing (no `value=` on the password inputs; presence hints use the separate `@access_key_configured`/`@secret_key_configured` booleans), so **there is no leak in shipped code**. But AC2's intent ("`get/0` … returns only a presence indicator … so there is no decrypted value in this controller's process") is not literally met: get/0 returns masked values and the controller both derives the booleans AND forwards the masked map into the template assigns. Strip the two secret fields from the assigned map so no secret-derived value can ever be picked up by a later template change.

## Verified CLEAN (angles independently checked)

- **CSRF — protected, same path as 9b's `save/2`.** Both new `post` routes live inside `scope "/admin", Nebu.Admin do pipe_through :browser`, whose pipeline runs `protect_from_forgery`. The storage `<form>` carries `<input type="hidden" name="_csrf_token" value={Plug.CSRFProtection.get_csrf_token()} />`, and the Test Connection button uses a native HTML `formaction` on a submit button **inside that same form**, so the CSRF token is submitted for both actions. `maybe_skip_csrf` only bypasses when the `:admin_csrf_bypass` app-env is truthy (a test-only seam) and never for these paths in production.
- **Admin-only (AC7) — enforced, not merely visual.** `plug Nebu.Admin.Auth, :require_admin` is a module-level plug on `Nebu.Admin.MediaSettingsController`, so it runs for `save_storage/2` and `test_connection/2` exactly as for `index/2`/`save/2`. An unauthenticated/non-admin request redirects to `/admin/login` before either action body executes; no nav-link-only gating.
- **Secret write-only contract — holds on every path.** Password inputs have no `value=`. `storage_config_from_params/1` (blocked/invalid re-render) hard-nulls `access_key`/`secret_key`. `candidate_from_params/1` sends secrets as `nil` when blank so server-side blank→stored resolution applies. The decrypted plaintext produced by `resolve_candidate_secrets/1` exists only inside `Nebu.Media.StorageConfig.test_connection/1` and is passed solely to the test fun, whose return value is `:ok | {:error, reason}` — the plaintext never round-trips to the controller or browser (subject to L-1's server-log note).
- **`archive_bucket` / `region` are inert w.r.t. SSRF.** `test_connection` uses only `bucket` (in `head_bucket`) and `endpoint` (as `host`). `region` is passed to `config_overrides` as an ExAws signing region string, not a URL/host. `archive_bucket` is not referenced by `test_connection` at all (only persisted via `upsert/2`). Neither is fed into request host/scheme resolution — no SSRF vector beyond `endpoint` (M-1).
- **No SQL injection in `count_media_with_storage_key/0`.** `real_count_media_with_storage_key/0` runs a static, parameter-free literal `"SELECT COUNT(*) FROM media_files WHERE storage_key IS NOT NULL"` with `[]` params via `Ecto.Adapters.SQL.query!/3`. No interpolation, no caller input. The test seam (`:media_files_storage_key_count_fun`) is an `Application.get_env` fun, not attacker-reachable.
- **Orphan-risk gate is a real server-side gate (AC4).** `handle_storage_save/2` compares the raw submitted `changes` against `StorageConfig.persisted_target/0` (persisted-row-only, deliberately NOT `get/0`'s env/default-merged view, so a genuinely fresh config never gates), and on an endpoint/bucket change with `count > 0` and an unchecked box re-renders at 200 with a `role="alert"` warning + native `<input type="checkbox">` — no JS `confirm()`, no dismissible flash. `persisted_target/0` reads only the config row, never `media_files`. The confirm bypass (`confirm_orphan_risk=true`) is the intended acknowledgment, an admin safety gate, not a security boundary.
- **No secret material in any `Logger` call in `storage_config.ex`.** `decrypt_secret/1` logs only `inspect(reason)` (a `:decrypt_failed`-class atom) / `Exception.message(e)` — never ciphertext or plaintext. Loader/env-reader/ETS log only the error term.
- **`refresh_cache/0` robustness.** A missing/normally-stopped singleton no longer crashes an already-successful `upsert/2` request: it re-uses the sanctioned `Supervisor.restart_child`-then-raw-start fallback and `catch`es a NORMAL `:exit`. No security dimension; noted CLEAN.

## Memory Integration

No new recurring pattern beyond what MEMORY already holds. This story is the predicted **live materialisation** of three curated lessons: MEMORY #44/#50 (admin-configured outbound target = SSRF + credential surface; validate at the persistence boundary, not only the consumer) and #56 (S3-compatible endpoint needs scheme assertion AND `USE_SSL` fencing) — the scheme half is now closed, the private-range/transport half (M-1) is still open and should be closed by reusing the `Nebu.Media.SSRF` path already applied to `webhook_url` in the same controller. #84 (crash-report plaintext leak) is architecturally avoided for the supervised holder but re-touched by L-1's request-process exception-logging path. Recommend curating one durable note: **"when a story wires a second admin-configured outbound target into an existing controller that already SSRF-pins another URL field, the new field must reuse the same pin — parity, not a weaker scheme-only check."**
