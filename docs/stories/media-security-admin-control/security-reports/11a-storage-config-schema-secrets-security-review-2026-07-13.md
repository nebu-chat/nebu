# Security Review — 11a-storage-config-schema-secrets

**Reviewer:** Kassandra (nebu-agent-kassandra) · **Date:** 2026-07-13 · **Epic:** media-security-admin-control
**Story flag:** `security_review: required` — new `media_storage_config` singleton table + `Nebu.Media.StorageConfig` (GenServer + ETS + `:pg` cache) holding admin-configurable S3/MinIO target config with `access_key`/`secret_key` encrypted at rest via `Nebu.Web.SecretBox`.

## Verdict: APPROVED — CLEAN (0 CRITICAL, 0 HIGH, 1 MEDIUM, 3 LOW, 3 INFO)

Nothing blocks the commit. The 9a-class HIGH (missing `GRANT`) is **not** repeated — `000024_media_storage_config.up.sql` ships the correct `GRANT SELECT, INSERT, UPDATE, DELETE ON media_storage_config TO nebu_app;` and `MigrationsGrantTest` was genuinely extended to guard it. Secret handling is sound: `Nebu.Web.SecretBox` is the sole crypto path (no second AES call site), the `:protected` ETS table holds only ciphertext/env-raw values (decryption is on-demand in the caller process, never memoized as plaintext), `get/0` masks on every path, and the audit trail is field-names-only. The single MEDIUM and the LOWs are all **forward-looking / defense-in-depth** on an entirely **unwired** module — `get_for_connection/0` (the only plaintext-returning path) and `upsert/1` have **zero production callers** (grep-confirmed), so live attack surface today is nil. The findings are carry-forward obligations onto whichever later story wires this config into an actual S3 client / write-UI.

The plaintext-return path is therefore not reachable from any UI/JSON surface today — consistent with the story's claim. The security question is almost entirely about the *latent decisions* this module encodes and how they behave once a later story wires a consumer.

## Detail

### M-1 — MEDIUM — Non-secret storage-target fields are unvalidated → forward SSRF + transport-downgrade surface

`build_columns/1`/`column_for/2` store `endpoint`, `bucket`, `region`, `archive_bucket`, `use_ssl` verbatim (any binary / any bool), and `build_resolved/2` returns them unmodified. There is no scheme assertion, no hostname-shape check, no private-range guard, and no transport fence. Prior review passes concentrated on the two *secret* fields (encryption, masking, ETS-at-rest, decrypt-failure handling) and did not score the non-secret fields for their forward sink behavior.

`get_for_connection/0`'s stated purpose is "actual `ExAws`/S3-client construction." When a later story wires it:

- **SSRF-adjacent:** `endpoint` (and `archive_bucket`) become the target of server-originated S3 requests. An admin-set (or, if a future write path is under-scoped, attacker-influenced) endpoint pointing at `169.254.169.254`, an RFC1918 address, or another internal service turns the media subsystem into an SSRF primitive. This is weaker than 9a's `webhook_url` case (an S3 endpoint is inherently infra config, not a fetch of arbitrary attacker URLs), which is why this is MEDIUM/forward, not HIGH — but MEMORY #56 (`media-gateway-stackit-objectstore`) already recorded exactly this class: "S3-compatible endpoint validation missing scheme assertion … Tofu preconditions must assert `!startswith("http://")`". The DB-config path re-introduces the same gap the IaC layer was told to close.
- **Transport downgrade:** `use_ssl: false` is (correctly, per AC5) an honored set value. MEMORY #56's second half warns of the operator temptation to flip `USE_SSL=false` while debugging, "silently downgrading transport for S3 credentials." Wired, `use_ssl:false` + real `access_key`/`secret_key` = credentials over plaintext HTTP.

**Remediation (consumer story, not fixable within 11a's no-consumer scope):** validate `endpoint` as hostname[:port] with no URL scheme (mirroring `runtime.exs`'s `minio.New` hostname-only contract and MEMORY #56); consider an SSRF/private-range check unless the target is an operator-pinned allowlist host; fence `use_ssl=true` for production. Record the SSRF sink as a MUST-VERIFY on the wiring checklist so "the value came from the config table, it must be fine" is never assumed.

### L-1 — LOW — Audit `changed_fields` is caller-input keys, not written columns; no known-key validation

`upsert(fields, actor)` computes `columns = build_columns(fields)` (drops unknown keys via `column_for/2 → nil`) but `write_audit(actor, fields)` records `%{changed_fields: Map.keys(fields)}` from the *original* input. Two consequences:

1. **Audit says something changed that didn't.** `upsert(%{unknown: 1})` writes nothing to a real column (only the always-appended `set_at`) yet the audit row claims `changed_fields: [:unknown]`. AC9 intends "the fields that changed" — this is the raw request, not the effect.
2. **Garbage/empty upsert still mutates + audits.** `upsert(%{})` and `upsert(%{unknown: 1})` both run `default_writer` (INSERT/UPDATE of `id, set_at`), creating the singleton row and bumping `set_at`, plus an audit entry. Sibling `Nebu.Media.Config.upsert/3` rejects unknown keys outright (`validate_known_key/1`); this module silently accepts and drops them.

Impact is low today (single trusted caller, no consumer, no secret leak — values are never in the audit). But it is an audit-integrity gap: the trail should reflect what was persisted. Derive `changed_fields` from the keys that produced a column (or reject unknown keys), and skip the DB write when `columns` is empty.

### L-2 — LOW — Silent env-var/default credential substitution on decrypt failure (accepted MINOR-2, cluster-wide via TTL)

`resolve_secret/5` treats a failed `SecretBox.decrypt/1` (returns `{:error, :decrypt_failed}` → `nil`) and an unavailable at-rest key (rescued `RuntimeError` → `nil`) as "ciphertext absent" and falls through to the env-var credential, then the compiled default. This is the deliberate MINOR-2(a)/(b) fix (log message-only, no secret material; read-path only — `upsert/2`'s `SecretBox.encrypt/1` still raises unguarded per AT12), and it is *directional-safe* (it never elevates an attacker; at worst the server authenticates to S3 with stale/absent credentials → availability failure).

The adversarial addition worth recording: because the GenServer's `:ttl_tick`/`:pg` refresh loop re-reads every 60s on every node, an operator rotating `NEBU_INTERNAL_SECRET` **without re-encrypting the stored keys** silently reverts the *entire cluster* to env-var (or `nil`/anonymous) credentials within a minute, with a `Logger.warning` as the only signal. That is an operational footgun, not an exploit. Acceptance is reasonable; recommend the consumer story emit an operator-visible alert (not merely a log) on decrypt failure so credential reversion during rotation is not invisible.

### L-3 — LOW — Masking reveals the whole secret for short values

`mask_secret/1` returns `"••••" <> String.slice(plaintext, -4..-1)`. For a normal 40-char S3 secret this leaks ~the last 4 chars (a deliberate recognizability UX, standard practice). For a secret of length ≤ 4, `String.slice/2` returns the entire string, so `get/0` echoes the full credential behind four bullets. Cap the revealed suffix (e.g. last-4 only when `byte_size(plaintext) ≥ 8`, else all-bullets).

### INFO-1 — Crash-report vector (MEMORY #84): module clean, forward hand-off to the caller

Encryption runs in the caller of `upsert/2` (`build_columns` → `SecretBox.encrypt`), decryption runs in the caller of `get/0`/`get_for_connection/0` (`resolved/0` → `SecretBox.decrypt`). The supervised `Nebu.Media.StorageConfig` GenServer's mailbox/state never contains a plaintext secret (its messages are `:refresh`/`:ttl_tick`/`{:invalidate_media_storage_config}`; its ETS holds ciphertext + env-raw only). So the always-running process is **not** an SASL-crash-dump leak for MEMORY #84 — no `Process.flag(:sensitive, true)` is needed on it. The vector re-opens only for a future caller (write-UI/controller) that holds plaintext in a supervised process; hand that obligation to the consumer story.

### INFO-2 — Audit-after-write persists on audit failure (accepted, 9a F-INFO-B parity)

`upsert/2` order is write → audit → refresh; `write_audit/2` only `Logger.error`s on `AuditWriter.log/6` failure, so the config write is not rolled back. Same accepted anti-forensics/AC-completeness surface as 9a. Exploitation requires inducing an audit-write failure; matches existing audit-bridge call-site convention. No block; consider Compliance-side alerting.

### INFO-3 — RLS UPDATE policy omits explicit `WITH CHECK`

`storage_config_update_singleton FOR UPDATE USING (id = 1)` has no `WITH CHECK`. An attempt to update `id` off the singleton is blocked three ways (column `CHECK (id = 1)`, the PK, and PG's implicit `WITH CHECK = USING`), so it is not exploitable — but it deviates from the `server_config`/9a precedent of spelling both clauses out. Cosmetic; add `WITH CHECK (id = 1)` for consistency and to stop relying on the implicit fallback.

## Verified CLEAN (angles independently checked)

- **9a HIGH not repeated — GRANT present & guarded.** `000024_media_storage_config.up.sql:44` = `GRANT SELECT, INSERT, UPDATE, DELETE ON media_storage_config TO nebu_app;`. `MigrationsGrantTest` gained a real 000024 describe block: the GRANT regex requires all four privileges in order on the right table/role (`~r/GRANT\s+SELECT\s*,\s*INSERT\s*,\s*UPDATE\s*,\s*DELETE\s+ON\s+media_storage_config\s+TO\s+nebu_app/i`), a `contains_create_table?` pre-check, a `has_serial_columns?` no-SERIAL guard (correct — the table is SMALLINT-PK/BIGINT, no sequence, so no companion sequence GRANT), and `000024_media_storage_config.down.sql` was added to the no-GRANT down-migration loop. The 9a fail-open-to-defaults production trap does not recur.
- **SecretBox is the sole crypto path.** `column_for/2` calls only `SecretBox.encrypt/1`; `decrypt_secret/1` calls only `SecretBox.decrypt/1`. No direct `Nebu.Media.Crypto` call, no second AES-256-GCM site. `SecretBox.at_rest_key/0` fails closed (`raise`) on an empty/missing internal secret (closes the `SHA-256("")` hole, MEMORY #66/#70), and `upsert/2` lets that raise propagate before any DB write (AT12).
- **No plaintext secret at rest in ETS (MINOR-1).** `do_refresh/0` caches `{:catalog, {row, env}}` where `row` is the raw DB row (ciphertext columns) and `env` the raw env map. `SecretBox.decrypt/1` is invoked only from `resolved/0` (both `get/0` and `get_for_connection/0`), on-demand per read, never during the GenServer's `:ttl_tick`/`:pg`/`init` refresh. The `:protected` (VM-globally readable) table therefore never holds a decrypted secret byte.
- **`get/0` masks on every return path.** Both branches (`:media_storage_config_source` seam and normal `resolved/0`) pipe through `mask_map/1`. `get_for_connection/0` is the only unmasked path and has no production caller (grep-confirmed).
- **No secret material in logs.** Every `Logger.warning/error` in the module carries only messages/reasons/exception messages (`inspect(reason)`, `Exception.message(e)`) — never the ciphertext, the plaintext, the `columns` map, or the `fields` map. `write_audit/2` records `Map.keys(fields)` (names) only; it never touches values or ciphertext.
- **No SQL injection.** `default_writer/2` builds its column list exclusively from `build_columns/1`'s output, whose keys come from the fixed, hardcoded `column_for/2` mapping (never caller strings). All values are bound parameters (`$1..$n`); `set_at` is server-generated (`System.system_time`); `id` is the literal `1`. INSERT/ON-CONFLICT placeholder indices are consistent (`$1`=id, cols start at `$2`, `update_set` re-uses the same indices). `default_loader/0` is a static `SELECT`.
- **Singleton enforcement.** `id SMALLINT PRIMARY KEY DEFAULT 1 CHECK (id = 1)` + `storage_config_insert_only WITH CHECK (id = 1)` make a second row impossible; `ON CONFLICT (id) DO UPDATE` keeps it a true upsert of the one row.
- **Per-field precedence.** `pick/3` uses `not is_nil(...)` (not `||`), so `use_ssl: false` from DB/env is honored as a set value, not treated as unset. `_FILE`-then-plain secret precedence (`resolve_env_secret/3`) mirrors `runtime.exs:86-95` (verified: `_FILE` path → `File.read!` |> `String.trim`, else plain var).
- **Supervision genuinely mirrors the sibling.** `Nebu.Media.StorageConfig.Supervisor` is a plain child `Supervisor` (ADR-019), `:transient` child via `raw_start_link/1` MFA (avoids the `start_link/1 → Supervisor.restart_child` re-entrancy deadlock), wired unconditionally into `Nebu.Application` alongside `Nebu.Media.Config.Supervisor`. AT13 kills the pid, awaits `{:DOWN, …, :killed}`, polls for a *new* pid under the registered name, and asserts the cache repopulates — exercising real OTP supervision, not a bare start. `max_restarts: 1000/5s` matches the accepted 9a `F-INFO-D` rationale (crash-resistant `init/1`, no attacker-triggerable crash loop).
- **Migration numbering / version count.** `priv/migrations/` ends cleanly at `000024` (no `000025` conflict); `release_test.exs` asserts `1..24`; `.down.sql` is `DROP TABLE` only (no GRANT) and is in the no-GRANT guard list.

## Memory Integration

No new recurring pattern beyond what MEMORY already holds. This story is a **positive confirmation** of three curated lessons: (a) MEMORY #86 / 9a F-1 (post-000001 table-creating migrations MUST carry a GRANT + a `MigrationsGrantTest` block) — honored, not repeated; (b) MEMORY #70 (shared at-rest AEAD helper: fresh-nonce, single trust boundary, fail-closed on empty key) — `SecretBox` reuse is exactly the "GOOD, one audited path" case; (c) MEMORY #84 (crash-report leak for a process holding attacker/secret bytes) — architecturally avoided by keeping crypto in caller processes so the supervised holder never holds plaintext.

One durable cross-reference worth reinforcing (already covered by MEMORY #44/#56): **an admin-configured storage endpoint is the same SSRF + transport-downgrade class as an admin-configured webhook/OIDC/SCIM URL** — the DB-config layer re-introduces the exact `endpoint` scheme/SSRF/`use_ssl` gap the IaC layer (MEMORY #56) was told to fence, and it must be validated at the *consumer* (S3-client construction) boundary, not assumed safe because "it came from the config table." Carry M-1 forward as a MUST-VERIFY on whichever story wires `get_for_connection/0`.
