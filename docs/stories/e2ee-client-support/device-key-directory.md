## Story

**As** a Matrix client during device verification and cross-signing, **I want** to claim one-time keys for another user's device and to learn which users' device lists changed between two sync tokens, **so that** I can establish encrypted sessions and keep my view of device keys current.

Scope (decided, see `## Decisions`; the story was too big for one pipeline run, the orchestrator split it): this story is `POST /_matrix/client/v3/keys/claim` (with rate limits, the restriction and the no-oracle rule), `GET /_matrix/client/v3/keys/changes`, the `/sync` fields `device_one_time_keys_count`, `device_unused_fallback_key_types` (per device) and `device_lists` (peers and own devices), the device-list change stream position those need, and the GDPR erasure of that stream. The hardening of `POST /keys/query` (restriction, `user_signing_keys` self only, cross-user signatures, signature verification) is the follow-up story `key-query-hardening` (REQ-2026-014).

Scope decision (claim): `POST /_matrix/client/v3/keys/claim` only serves the caller's own devices and devices of users who share at least one room with the caller where BOTH sides are `join` (the rule of `sendToDevice`). Any other target is treated like an unknown device: it is LEFT OUT of `one_time_keys` and nothing is recorded in `failures` (no existence leak). Claims consume a resource, so this is stricter than the Matrix spec's "any user" rule.

## Acceptance Criteria

```gherkin
Feature: Device-key directory (one-time key claim and device-list changes)

  Scenario: Concurrent claims consume a one-time key exactly once
    Given device "@bob:nebu.test" "BOBDEV" has exactly one one-time key "signed_curve25519:AAAA" and no fallback key
    When two different users with a shared room claim a "signed_curve25519" key for "@bob:nebu.test" "BOBDEV" at the same time
    Then exactly one claim receives "signed_curve25519:AAAA" and no other claim receives it, and the device has zero one-time keys left

  Scenario: Fallback key is used when one-time keys are exhausted and is not consumed
    Given device "@bob:nebu.test" "BOBDEV" has no one-time keys left and a fallback key "signed_curve25519:FFFF"
    When I claim a "signed_curve25519" key for "@bob:nebu.test" "BOBDEV"
    Then the response contains the fallback key "signed_curve25519:FFFF" and a second claim also returns "signed_curve25519:FFFF"

  Scenario: Unknown or unauthorized device is left out of the response
    Given "@dave:nebu.test" has no device "GHOSTDEV" and shares no room with me
    When I claim a "signed_curve25519" key for "@dave:nebu.test" "GHOSTDEV"
    Then the response contains no key for that device, "failures" is empty, and the answer is identical to the answer for a user I cannot claim from

  Scenario: Changed device lists are reported between two sync tokens
    Given I hold sync token "s100" and "@carol:nebu.test" shares a room with me
    When "@carol:nebu.test" adds or deletes a device after "s100" and I call GET /keys/changes with from "s100" and to the current token
    Then the response "changed" list contains "@carol:nebu.test"

  Scenario: Claims are rate limited per caller and target
    Given I have already claimed one-time keys for "@bob:nebu.test" "BOBDEV" up to the configured per-caller, per-target limit
    When I claim another one-time key for "@bob:nebu.test" "BOBDEV"
    Then the server rejects the claim with HTTP 429 and M_LIMIT_EXCEEDED and no one-time key is consumed
```

## Decisions

ATDD step (pinned by the tests in `server/test/nebu/matrix/device_key_directory_*`, `000060_device_list_changes_test.exs` and `user_deletion_device_key_directory_test.exs`; the oracle context of this story is `_bmad-output/nebu/epics/e2ee-client-support/step-results/device-key-directory/oracle-context.md`, Matrix CS v1.18). To be confirmed by the owner and the security review. All former open questions are resolved here.

**Owner and orchestrator decisions (pinned as given)**

- **D1 Scope split.** This story = `keys/claim`, `keys/changes`, the sync fields (`device_one_time_keys_count` always incl. `signed_curve25519`, per-device `device_unused_fallback_key_types`, `device_lists` for peers and own devices), the device-list stream position, the key-change stamps (identity key upload, device delete, device rename, cross-signing upload, membership join / leave), GDPR erasure of the stream. Follow-up `key-query-hardening` (REQ-2026-014, stub file in this directory, NOT part of this story): `POST /keys/query` restricted to the caller and users who share a joined room, `user_signing_keys` for the caller only (spec bug D1 of the oracle), visibility of cross-user signatures, cross-user master-key signatures in `/keys/signatures/upload`, cryptographic signature verification, `unsigned.device_display_name` pin test. The `user_signing_keys` change is a MUST-level spec fix and trivially independent: ONE pin test sits in its own file (`device_key_directory_d1_optional_test.exs`, tagged `:d1_optional`), the reference implements it in a separate hunk; **Taken: implemented in this story (green, protected.ex `Map.take`), so the follow-up does not repeat it; the file is not skipped.**
- **D2 `failures` is always `{}`; scenario 3 is rewritten.** The spec keys `failures` by SERVER NAME for unreachable remote servers only; Nebu has no federation, so it is always the empty object. An unknown user, an unknown device, a keyless device, a user without a shared room, an invite-only share, a remote user and a user whose algorithm has no key are all LEFT OUT of `one_time_keys` (no `failures` entry: a per-target `failures` keyed by user id would be read as server names and make rust-sdk back off). The old wording "the `failures` map reports the requested target" is superseded.
- **D3 The restriction (stricter than the spec).** A claim reaches the caller's own devices and the devices of users who share a room with the caller where BOTH sides are `join` (the rule and the SQL shape of `ToDeviceStore`), evaluated at REQUEST time (no cached membership). An invitation on either side opens no path (no consent). The spec lets any user claim; Nebu refuses because a claim consumes a one-time key (a stranger could drain a device). Risk: Element's DM pre-check queries invitees without a shared room and then creates the DM unencrypted (harmless, aligned with ADR-011).
- **D4 No existence oracle.** The same code path and the same statements for every target kind: unknown user, unknown device, keyless device, not shared, invite only, remote user (`@x:other.example`) answer byte-identical (status, body, headers) and run an EQUAL number of statements (one membership-joined consuming statement for the whole request, set based, no early return per target). Ids that are not syntactically valid (a user id without `@` / `:`, a device id above 255 bytes) are left out silently like any other unreachable target. Only the STRUCTURE of the body is validated: `one_time_keys` missing or not an object, an entry of it not an object, an algorithm that is not a string: `400 M_BAD_JSON`.
- **D5 Limits of a request.** At most **1000 targets** (user / device pairs) per request, `400 M_INVALID_PARAM` beyond (before any rate bucket is charged). The spec's `timeout` is accepted and ignored (a non-integer `timeout` is no error).
- **D6 Exactly once, in upload order.** A one-time key is handed out at most once: the consuming statement is `UPDATE device_one_time_keys SET claimed_at = ... WHERE ctid = (SELECT ... WHERE claimed_at IS NULL ORDER BY created_at, key_id LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING ...` per target (set based); a SELECT followed by an UPDATE hands a key twice. Of two concurrent claimers of the last key one gets it and the other gets the fallback key or nothing. Keys go out in upload order (`created_at`; the order inside ONE upload call is unspecified). The stored key object is returned VERBATIM (`key`, `signatures`, `fallback`, unknown members), the server adds and removes nothing. A consumed key is never handed out again, also not when the client uploads the same key id again (the insert is store-once and stays so).
- **D7 Fallback key.** When no one-time key of the requested algorithm is left, the device's fallback key of that algorithm is returned; it is NOT consumed (a second claim returns the identical key) but is marked `used` (its algorithm leaves `device_unused_fallback_key_types` of THAT device); uploading a new fallback key replaces it and sets `used` back to false (existing behaviour). No one-time key and no fallback key: the device is left out. A user entry without any obtained device is left out too (never `{user: {}}`). The server is algorithm agnostic: the requested string is matched against the stored algorithm.
- **D8 Rate limits (owner decision: token buckets, `Nebu.Web.Plugs.RateLimit.take_all/1`).** (i) per caller user 30 requests per minute, burst 10 (counts REQUESTS, not targets) and 600 targets per minute, burst 1000 (counts the syntactically valid targets of a request, never their state; security fix F1, cycle 4); `GET /keys/changes` has a per-user tier `keys_changes` (60 per minute, burst 20; finding F3); (ii) per (caller, target user, target device) 10 per hour, burst 5, charged for OTK and fallback claims alike AND for every target whatever its kind (unknown, unshared and keyless targets are charged too: a 429 that depends on the target's state would be an oracle). All buckets of a request are checked all-or-nothing BEFORE the consuming transaction; any bucket over its limit gives `429 M_LIMIT_EXCEEDED` with `retry_after_ms` (the existing envelope, `Retry-After` in seconds) for the WHOLE request and NOTHING is consumed (a refusal in the second stage keeps the first stage tokens spent: they do not depend on the state of a target). Node-local like every rate tier: N x the limit in a cluster (documented). The per-target bucket key is a SHA-256 digest of the caller-chosen ids (never a sub-binary of the request body) and the per-target buckets are charged in a second stage, only after the caller buckets paid; the targets budget and the idle sweep (one hour) bound the ETS growth.
- **D9 `GET /keys/changes`.** `from` and `to` are BOTH required sync `next_batch` tokens (the spec). `changed` and `left` are ALWAYS emitted as lists. `from` or `to` missing or empty: `400 M_MISSING_PARAM`; a MALFORMED token (outside the token alphabet, a bad position group, longer than 512 bytes): `400 M_INVALID_PARAM`; a well-formed token without a device-list position (issued before this story: "expired") is NOT an error: `200` with every user the caller currently shares a joined room with (plus the caller) in `changed` (conservative over-report, `left` empty). `to` is the end of the range: when it carries a position the answer covers `(from, to]`, a well-formed `to` without a position means "up to now". `changed` = users who share a joined room with the caller (both sides `join`), and the caller itself, whose device identity keys were added, removed or changed, whose cross-signing keys changed, whose device (with keys) was renamed, or who NEWLY share a joined room with the caller after `from`; `left` = users who share no joined room with the caller any more although a membership change after `from` happened in a room both were in. A user without any shared room NEVER appears in `changed` (the stream is read through the caller's own shared rooms). Rate limited per user by its own tier `keys_changes` (60 per minute, burst 20; D8, finding F3).
- **D10 The device-list stream.** New table `device_list_changes` (migration `000060_device_list_changes`, `user_id`, `room_id`, `kind` in `keys` / `join` / `leave`, `pos`, key `(user_id, room_id)`: the LATEST change per user and room, bounded by users and memberships; `room_id` is `''` for key changes). Positions come from `sync_global_pos_seq` (as `CrossSigningKeyStore.put_keys`) but are drawn at COMMIT (a deferred constraint trigger takes one global advisory lock and then `nextval`, so visible positions are commit ordered: a reader at position M never later sees a row at or below M; a transaction that stamped early and commits late is never skipped; pinned with a held transaction). Stamps: identity key upload when the stored `device_keys` object is new or differs (an identical re-upload is no change), delete of a device that had identity keys, rename of a device that has identity keys, cross-signing key upload (`put_keys`; a signature merge is no change), and membership join / leave (a trigger on `room_members`, every writer is covered). A keyless device row is no change when it appears or disappears; one-time and fallback key uploads are no change. State is in PostgreSQL only (cluster safe, ADR-020).
- **D11 The device-list position in the sync token.** `next_batch` is `<core>.<room account data pos>[.<to-device pos>][.d<device-list pos>]`: an optional LAST group `.d<digits>` (with a letter, so it can never be mistaken for the to-device position). Every response carries it; an initial or fallback answer carries a fresh position (drawn after the commit lock, above every visible stamp); an incremental answer carries `max(since position, bound)` where `bound` is the highest visible stream position (`SELECT max(pos)`, no lock) read BEFORE the two stream reads and passed to them as their upper limit (RE-PINNED by the owner in code-review cycle 1: the earlier rule, the highest REPORTED row, left the position of a quiet device at an old value, so every sync of it re-scanned all rows above it; the bound is safe because visible positions are commit ordered: a row stamped later always gets a position above the bound, and a change that commits after the read comes with the next sync); the position never goes backwards (`max(since, bound)`, also for a forged or too high presented position). A token without the group (issued before the change or by an old node) means "unknown": the answer lists every user the caller shares a joined room with once (conservative). Rolling deploy: an old node that receives a token with the new group does not recognise it and answers an initial-shaped sync (safe: nothing is lost, a full snapshot); old tokens keep working on new nodes. The position lives only in the token the client presents (stateless; a forged position can only hide the caller's OWN future lists: every row is read through the caller's own shared rooms, no cross-user leak), no per-device column, so there is nothing to advance under a foreign token.
- **D12 `/sync` fields.** `device_one_time_keys_count` is per DEVICE and ALWAYS contains `signed_curve25519` (0 when none; Synapse does the same, rust-sdk reads a missing entry as 0 and re-uploads). `device_unused_fallback_key_types` is ALWAYS present (`[]` when none) and PER DEVICE (oracle D2: it was aggregated per user, so a second device's used fallback key was masked by the first device's unused one and never rotated). A device-LESS request (an unbound raw IdP JWT) keeps the legacy per-user aggregates for both fields (oracle D3, documented, no client of Nebu uses it for keys). `device_lists` (`changed`, `left`; both always lists): on an INCREMENTAL sync `changed` lists peers (users sharing a joined room) whose device keys or cross-signing keys changed, users who newly share a joined room with the caller, and the caller itself when it added, deleted, re-keyed or renamed an own device with keys or uploaded cross-signing keys; a user who changed a device while apart and rejoins is in `changed` on the rejoin; `left` lists users who share no joined room with the caller any more. An INITIAL sync lists no peer (the own-user rules of `sync-token-per-device` D10 stay). A FALLBACK of a request that carried a `since` lists every user the caller shares a joined room with (the client cannot know it got an initial-shaped answer). The own user is never in `left`.
- **D13 GDPR erasure.** `device_list_changes` is in `UserDeletion.erased_tables/0` (the stream rows of the erased user: its key changes and its membership changes), the runbook and the sweep of 07-deployment name it. The claim keeps no state of its own besides the one-time and fallback keys (already erased with the device rows) and the node-local rate buckets (no personal content). The erasure deletes the stream rows last; the peers' `left` for an erased user is not emitted (documented residual).
- **D14 Logging (law: no sensitive data).** Key material (one-time keys, fallback keys, signatures), tokens, device ids of claims and claim bodies are never logged at any level; the request logger prints the route with the anchor only. A failing statement logs its kind only.
- **D15 Migration `000060_device_list_changes`** (000058 key backup, 000059 to-device; 000056 / 000057 live on another branch, so the release contiguity guard stays red on this branch: expected). Only a new table (no existing table is touched except for the new trigger on `room_members`, rolling deploy safe), grants to `nebu_app`, row level security enabled and forced with a policy per command, indexes for the position scan and the erasure, the deferred stamp trigger and the `room_members` trigger, a symmetric down.

**Pinned by this step (beyond the story text, please confirm)**

- **D16 Nebu is stricter than the spec in three places and says so:** who may be claimed (D3), the per-request cap and rate limits (D5, D8), and `/keys/changes` only reports users the caller shares a joined room with (the spec says users in encrypted rooms; Nebu has none, so "shared joined room" stands in).
- **D17 Rename stamps only a device that has identity keys** (the display name is only visible through `/keys/query` for devices with keys, in `unsigned`); a keyless rename and a keyless add / delete are not changes.
- **D18 A fallback of a `since` request lists all shared users** (D12), a pure initial sync none; both are pinned.
- **D19 `/keys/changes` `to` is honoured as an upper bound** when it carries a position; without one (an old token) the bound is "now".
- **D20 Residuals (documented in 11-risks):** `left` can over-report a user who shared a room with the caller only at another time (never under-reports a real loss in `/sync`, whose end token is the current position; a `/keys/changes` window with an old `to` that ends between that user's leave and the caller's own later leave reports the user one window later); an erased user's departure is not reported; a position drawn at commit makes membership and key writes wait for each other's commit (the lock is held only during the commit); node-local buckets (N x); the per-target bucket keys are SHA-256 digests of the caller-chosen ids and the claim targets budget (600 per minute, burst 1000) and the one-hour idle sweep bound the ETS growth (D8).

**Open questions for the owner (not blocking; the tests pin the recommended answer)**

- Resolved: the bucket memory growth is bounded by the claim targets budget (600 per minute, burst 1000 per caller), the 1000-target cap per request and the one-hour idle sweep (D8).
- Resolved: `/keys/changes` has its own per-user tier `keys_changes` (60 per minute, burst 20), see D8 and D9.
- Do we want the conservative "all shared users" answer for an old token, or a 400-free `changed: []`? Pinned: all shared users.
