## Story

**As** a Matrix client user verifying a device or requesting room keys, **I want** my client to send to-device messages to specific devices of another user and receive them via sync, **so that** device verification (SAS, QR), key requests and room-key forwarding can work without any room event.

Constraints (decided, to be confirmed in security review; lines marked SUPERSEDED were replaced by the `## Decisions` below, the tests pin the Decisions):

- Recipients are the sender's own other devices and users who share at least one room with the sender where BOTH sides are `join` (SUPERSEDED: the first draft said "share at least one room", the orchestrator refinement "join or invite", then the owner decision removed the invite reach: an invitation without consent opens no send path, and in-room verification does not use to-device messages). Targets outside that set are skipped silently (no existence oracle). Consequence for clients: verification and key requests work between your own devices and with a user you share a joined room with; a user you share no joined room with cannot be reached.
- Transaction IDs are idempotent per user, device, event type and txn id, persisted in the database (SUPERSEDED: "per access token and device": the token is irrelevant, a new token of the same device is the same transaction), like the existing send-event transaction handling.
- `*` expands to all devices of the target user at send time (the sending device is excluded for the sender's own user; an explicit device entry wins over `*`).
- Event type must match `^[a-zA-Z0-9._-]{1,255}$`. Content is opaque: the server inspects only type and size and never logs content.
- Limits: request body at most 64 KiB (`M_TOO_LARGE`), at most 50 recipient entries per request counting `*` as one (`M_TOO_LARGE`), at most 500 queued messages per device (SUPERSEDED: not `M_LIMIT_EXCEEDED` / 429: a full queue silently evicts its OLDEST message, the sender is never told), plus the aggregate budgets of Decisions 2 and 3 (user, sender share, fan-out), a sender rate limit of 60 per minute, burst 30, per user (SUPERSEDED: "consistent with send-event": send-event has no rate limit; the precedent is the account data write tier).
- Delivery in `/sync` as `to_device.events`, bounded per sync (100 messages / 1 MiB) with continuation. A batch is removed only when the client's next sync presents the `since` token that covers it; a retry with the older token re-delivers it.
- Queue rows are purged on device delete, logout and GDPR erasure (SUPERSEDED: "session revoke": revoking only the SESSIONS of a device keeps the device and its queue), and stale queues are purged by a TTL job (7 days, an Oban cron worker).
- Transport only. ADR-011 stays: Nebu continues to reject `m.room.encryption`. No federation.

## Acceptance Criteria

```gherkin
Feature: To-device messaging
  Scenario: Message to a specific device is delivered via sync
    Given Bob has device "BOBDEV1" and shares a room with Alice
    When Alice sends an event of type "m.key.verification.request" to device "BOBDEV1" via sendToDevice
    Then Bob's next sync returns the event in to_device.events with sender, type and content

  Scenario: Wildcard device target fans out to every device of the user
    Given Bob has two devices and shares a room with Alice
    When Alice sends a message to Bob with device "*"
    Then each of Bob's devices receives one copy in its next sync

  Scenario: Queued message is removed when the client's next sync presents the covering since token
    Given Bob's sync delivered a to-device message with next_batch "s5"
    When Bob's next sync presents since "s5"
    Then the message is no longer returned by sync and its queue row is deleted

  Scenario: Unknown or unreachable recipient is skipped silently
    Given Carol does not exist or shares no room with Alice
    When Alice sends a to-device message to Carol
    Then the request succeeds with 200 and no message is queued for Carol

  Scenario: Deleting a device drops its queued messages
    Given Bob's device "BOBDEV1" has undelivered to-device messages queued
    When Bob deletes device "BOBDEV1"
    Then the queued messages for "BOBDEV1" are deleted
```

## Decisions

ATDD step (pinned by the tests in `server/test/nebu/**/to_device_*`, `000059_to_device_messages_test.exs`, `user_deletion_to_device_test.exs`; the lessons of the sibling story `server-side-key-backup` and its three security reviews are applied from the start). To be confirmed by the owner and the security review.

**Orchestrator decisions (pinned as given)**

- **Queue full: evict the oldest.** A full queue evicts its OLDEST messages (per device 500 messages / 8 MiB, per user 2000 messages / 32 MiB); the sender is never told (the same `200 {}`, never a 429: a 429 would reveal the recipient's state and let one sender's flood block the others); the count is logged without content. This supersedes the story text "`M_LIMIT_EXCEEDED` / 429" for a full queue; 429 is only for the sender's own rate limit and for a transaction in flight.
- **Recipient restriction accepted, then TIGHTENED by the owner (test review m2; supersedes the orchestrator refinement "(a) join or invite").** Recipient = the sender's own device, or a user who shares a room with the sender where BOTH sides are `join`, evaluated at SEND time (not at delivery). An invitation (either side) opens NO send path: it needs no consent (any user could create a room, invite anyone and get a send path), and in-room verification (what Element and FluffyChat use for user verification) does not use to-device messages. Every other recipient (no shared joined room, only invited, unknown user or device, remote user, malformed id, deactivated user) is a silent identical `200 {}` (no oracle).
- **`*` to oneself excludes the sending device; an explicit device entry of the same user wins over `*`** (one copy per device, whatever the order of the keys in the body).
- **Limits kept:** body 64 KiB (`413 M_TOO_LARGE`), 50 recipient entries counting `*` as one (`413`, refused whole, never truncated), 7 days TTL. Sender rate limit **60 per minute, burst 30, per user** (own tier `to_device`; precedent: the account data write tier, there is no rate limit on room `send`; node-local buckets: N x the limit in a cluster).

**Pinned by this step (beyond the story text, please confirm)**

1. **Acknowledgement on the next token, persisted.** A sync response only delivers; the messages are deleted when a LATER sync presents the `since` token of that response (never on delivery). The to-device position travels in the token (`<core>.<room account data position>[.<to-device position>]`; a device without traffic keeps the two-part token the room account data tests rely on). State is in PostgreSQL only (a delivery stamp per message, `delivery_seq`, set by the first response that carries it): a retry with an older token delivers again, an initial sync / unknown / garbage / foreign (another device or user) token acknowledges nothing and delivers everything pending, a forged position can only acknowledge what was delivered, and a message that COMMITTED LATE (a lower queue position than a delivered one) is neither deleted nor missed (a pure "delete up to the position" would lose it; tested with a deferred trigger). `to_device: {"events": []}` is always emitted.
2. **Per-sender share and fair eviction (owner decision M1).** One sender may hold at most 100 queued messages per recipient DEVICE and at most **200 messages and 4 MiB per recipient USER** (over all its devices); beyond either the sender's OWN oldest are evicted first. When the USER-level cap (2000 messages / 32 MiB) trips, the eviction is FAIR: the oldest message of the sender with the LARGEST share goes first (a row's rank is its position counted from the newest of its sender, the highest ranks go first, older first on a tie), so a flooding co-member never evicts the older messages of a sender below its share. The device cap (500 / 8 MiB) still evicts the oldest overall. **Accepted residual:** many colluding senders (each below its share, together above the caps) can still evict a victim's older messages; bounded by the room co-membership requirement and the rate limit.
3. **Budgets with an aggregate for every per-item cap:** body 64 KiB; 50 entries; at most 100 targets per request AND 1 MiB of rows per request (content + 128 bytes per row; targets beyond are dropped silently, in a deterministic order; the first target is always kept); per device 500 / 8 MiB; per user 2000 / 32 MiB; per sender and device 100; per sender and recipient user 200 / 4 MiB; 1000 idempotency records per sending device (oldest forgotten); a sync response carries at most 100 messages and 1 MiB (the first message is always carried), the rest comes without waiting. Seams `:nebu, :to_device_<name>`, defaults in `ToDeviceStore.limits/0`.
4. **Rate limit before the body, authentication before both; a rate limit is not a concurrency limit.** `JsonBody` leaves the body unfetched (decoded segments); the route takes the user's rate token, then a send slot (4 per user, 6 per node since cycle 1 [was 32, superseded], monitor based `Nebu.Matrix.ToDeviceSendGate`, node-local, 429 before the body is read), then reads the body with the 64 KiB cap. A junk bearer or an exhausted bucket never makes the server read a body.
5. **No waiting locks.** The send takes the per-user `sync_global` advisory lock SHARED as a try-lock (the GDPR erasure takes it exclusively; a busy lock is a 429 for the sender and a silent skip for a recipient: no oracle for an erasure in progress), the transaction runs with a short `lock_timeout` (a held transaction record answers 429 within a second, no waiter holds a pooled connection); a send is a constant number of set-based statements however many recipients; the purge uses `FOR UPDATE SKIP LOCKED`.
6. **Idempotency persisted.** Scope (user, device, event type, txn id) in `to_device_txns` (unique key in the database), the token is irrelevant, another device / user / event type / the room `send` endpoint are independent; a refused request (400, 413, 429, 5xx) burns no txn id (the record is part of the same transaction); records are kept 24 hours.
7. **Wake-up of exactly the target device** (a test seam `:nebu, :atdd_to_device_before_join`, a 0-arity function run inside the sync between the pre-check and the `:pg` join, pins the missed wake-up window) (`{:to_device, device_id}` to the `user:<id>` `:pg` group, cluster wide; the other devices of the user keep waiting); a message the presented token does not cover makes the next sync return at once, one it covers does not (no busy loop); the check runs again after the poll joined its group (no missed wake-up).
8. **No timing oracle by work:** a request issues the SAME statements whatever the recipient (an unknown, unshared, deactivated or erased recipient only makes the arrays empty), pinned by counting the statements; answers are compared by status, body and headers.
9. **Content is opaque and never logged** (RequestLogger captures no body of the route and redacts sync response content, RouteNormalizer anchor `sendToDevice` replaces type and txn id, failing statements log their kind only: a trigger that quotes the row leaks nothing, nothing is half done after a failure, a refused request logs nothing of its body); the event TYPE is not content (sync responses log room event types as well).
10. **Lifecycle.** A device removal (`DELETE /devices`, `/delete_devices`, logout, logout-all, the admin device revoke `delete_user_device/2`, the OAuth logout) deletes the device's queue AND idempotency records (`DeviceKeyStore.delete_device`, one place); revoking only the SESSIONS of a device (the device and its keys stay) does not purge the queue; an admin DEACTIVATION keeps the queue (reversible) but nothing new is queued for an inactive user; messages a removed device SENT stay in the recipients' queues. A device re-created with the same id starts empty. **TTL:** 7 days decided by the delivery itself (an expired message is never delivered, not even before a sweep), housekeeping by the Oban cron worker `Nebu.Workers.ToDevicePurgeWorker` (existing limit-1 `oauth_cleanup` queue; leader enqueues, batched atomic SQL with `SKIP LOCKED`, one run purges any backlog, concurrent runs split the work, no node-local state).
11. **GDPR erasure.** `to_device_messages` and `to_device_txns` are in `UserDeletion.erased_tables/0` (no foreign key between them: no order); ONE more statement deletes the messages the erased user SENT (`sender`: authored content and the id, queued for other users); the sweep SQL of the runbook and 07-deployment does the same; a send of an erased user's in-flight bearer is `403 M_USER_DEACTIVATED`; a race with an erasure leaves no row.
12. **Migration `000059_to_device_messages`** (000058 = key backup; 000056 / 000057 are on another branch, so the `release_test` contiguity guard stays red on this branch: expected, merge that branch first). Tables, columns and indexes pinned by catalog tests: `to_device_messages` (recipient `user_id`, `device_id`, `sender`, `created_at`, a delivery stamp, a queue position), `to_device_txns`; a device is KNOWN when it has a `devices` row.
13. **Errors:** `400 M_NOT_JSON`, `400 M_BAD_JSON` (messages missing / wrong type, a non-object entry, a non-object body), `400 M_INVALID_PARAM` (event type outside `^[a-zA-Z0-9._-]{1,255}$`, txn id 0 or > 255 bytes), `413 M_TOO_LARGE`, `429 M_LIMIT_EXCEEDED`, `403 M_USER_DEACTIVATED`, `500 M_UNKNOWN` (generic). A malformed user id key is skipped silently (never a 400: no oracle); only `/_matrix/client/v3` is routed (405 `Allow: PUT`).
14. **Statement pins of the existing sync tests are ranges** (test review m3): `member_prev_content_http_test` initial sync 59..61 and `history_visibility_http_test` initial 50..52 / incremental 30..33 (old baseline = floor, the reference's measured count = ceiling, the SET LOCAL count stays exact); the real bound on to-device work is pinned by `to_device_concurrency_test.exs` (statements on the to-device tables).

**Cycle 1 (after the code review 0 MAJOR / 6 MINOR and Kassandra 1 HIGH / 4 MEDIUM / 2 LOW; orchestrator decisions, pinned by `to_device_sender_budget_test.exs`, `to_device_delivery_faults_test.exs` and the adapted older files)**

15. **Per-SENDER total budget over ALL recipients (HIGH #1):** 4000 messages and 16 MiB (seams `:to_device_max_per_sender_total`, `:to_device_max_bytes_per_sender_total`); beyond it the sender's OWN oldest rows go first, whichever recipient they are queued for; another sender is unaffected. Worst-case database footprint documented in 07-deployment and 11-risks (users sharing a room x 32 MiB per recipient, 16 MiB per sender). Plus the **byte-cost bucket** per sender, 4 MiB per minute, burst 8 MiB (seams `:to_device_rate_bytes_per_min`, `:to_device_rate_bytes_burst`), applied after the parse (`429 M_LIMIT_EXCEEDED` with `retry_after_ms`, the transaction is rolled back and its txn id not burnt), node-local (N x in a cluster, documented). **Deviation from the wording "bytes actually accepted":** the bucket is charged with the bytes the request ASKS to fan out (an explicit device: content + 128; a `*`: what it could reach, `max_targets` rows, never above the 1 MiB fan-out budget; a cost above the burst is charged as the burst), because an accepted-bytes cost would tell a delivered recipient from a skipped one by the 429 (an existence oracle). A delivered, an unknown, an unshared and an unknown-device target exhaust the bucket identically (pinned).
16. **DEVICE-level fair eviction and a byte share per sender and device (MEDIUM #2):** the device cap (500 / 8 MiB) uses the same fair rank ordering as the user cap (largest sender share first, oldest first on a tie) and every sender has a byte share of 1 MiB per recipient device (the count share of 100 stays; seam `:to_device_max_bytes_per_sender_device`): two colluding co-members cannot evict a victim sender's older messages from a victim device. The 11-risks residual is corrected ("two are enough" removed: only MANY senders beyond the shares).
17. **The erasure fence has its OWN advisory key (MEDIUM #3)** `to_device_erasure|<user>` (exclusive in `UserDeletion`, a shared try-lock in the send): a recipient's writer that holds `sync_global|<user>` no longer makes a message skip (pinned with a held `sync_global`: queued); an erasure in progress still skips silently. (Supersedes decision 5 for the key name; the try-lock rule stays.)
18. **A to-device delivery error never fails `/sync` (MEDIUM #4):** the answer is `200` with `to_device: {"events": []}`, the position is kept (nothing acked or lost), the room data is unaffected, the log names the kind only (was 503). The acknowledgement DELETE, the stamp UPDATE and the eviction subselects use `FOR UPDATE SKIP LOCKED`: a held row lock is skipped, never waited for (a send into a full queue with locked old rows is answered 200 at once, the queue overshoots and the next send catches up).
19. **Node send slots 32 -> 6 (MEDIUM #5; the old number 32 is superseded; per user 4 stays) and a `statement_timeout` of 2 s** per send and per delivery (`SET LOCAL`; over it: 429 for a send with nothing stored, an empty `to_device` for a sync). A running counter per queue (instead of re-aggregating the counts per send) is a documented follow-up in 11-risks.
20. **Device delete race (LOW #6):** the send takes `FOR KEY SHARE` on the target `devices` rows, `delete_device` / `delete_device!` lock the device row first: a send racing a device delete never leaves rows for a recreated device of the same id (pinned with a slow insert). LOW #7 (decode / re-encode of up to 1 MiB per sync, `Jason.Fragment`) is a follow-up note in 11-risks only, no test.
21. **Code review:** MINOR 1 the position of a response never covers a row it did not carry (the highest stamp among the rows the response carries, i.e. those it stamped itself and those already stamped; else the presented `since`) when its stamp UPDATE lost a race; the A/B trace (two overlapping syncs, a lost response, no message lost) is pinned with the test seam `:nebu, :atdd_to_device_before_stamp` (a 0-arity function run inside the delivery transaction between the read and the stamp), at the HTTP level (nothing is lost) AND at the store level (`ToDeviceStore.deliver/3`: the loser's position stays at its `since`, a pure redelivery claims the stamp of the rows it carries). Note from the ATDD run: in the nesting that the seam can build over HTTP (the loser persisted its token generation first) the loser's own token is already unusable (a second sync that presents the same `since` is a retry of the previous token generation and invalidates the token of the first one, so the client falls back to an initial sync and loses nothing); a loser that persisted LAST (a winner delayed between the token write and its read) has a usable token, which is the case the store-level test pins directly, and the 08-concepts sentence "covers exactly the batch a response carried" is superseded. MINOR 2 the advisory lock is taken only for the ids that passed the shared-room join (pinned with `pg_locks`). MINOR 3 facade `Nebu.Matrix.purge_expired_to_device/0`, used by the worker (static pin). MINOR 5 / 6 the moduledoc budgets and the wording "about 16 devices (15 when the content fills the body)" are pinned. MINOR 4 accepted. INFO: the sequence-reset operator note, the `ctid` purge, the shared `oauth_cleanup` Oban queue and the token without CAS are accepted notes (07-deployment / 11-risks).
22. **Old pinned numbers superseded on purpose:** node slots 32 -> 6; statement ceilings of the concurrency tests 14 -> 17; the 8 MiB device-budget default test (now nine senders, the fair device cap); the device flood expectation `[2, 4, 5, 11, 12]`; the delivery error answer 503 -> 200 with an empty `to_device`; the fence key `sync_global|` -> `to_device_erasure|`; concurrent same-token syncs: a losing response carries nothing; the pin "the /sync reads have NO statement timeout" of `sync_rejoin_range_scan_bound_http_test.exs` now exempts the one statement that sets the transaction-local timeout of the to-device delivery (the room reads stay without); `user_deletion_to_device_test.exs` pins the server name itself (order independence).

**Cycle 4 (the owner FIXES Kassandra's cycle 1 MEDIUM instead of accepting it; pinned by `to_device_two_phase_send_test.exs`, the cycle 4 docs pins in `to_device_docs_test.exs` and the adapted older pins)**

23. **A send is two transactions (cycle 4).** Phase 1 (one short transaction): timeouts, the shared try-locks (`to_device_erasure|<sender>`, the recipients' fences), the transaction record, the byte bucket (charged on the ASKED bytes before any recipient lookup), the target lookup with `FOR KEY SHARE` on the target `devices` rows IMMEDIATELY before the INSERT, the INSERT, the COMMIT: the key-share window contains no eviction, count or sum scan. Phase 2 (a second, separate transaction after the commit, best effort): the soft eviction (own-sender caps, fair device and user eviction) WITHOUT any lock on `devices` (it only deletes, so the erasure fence still holds: nothing is inserted for an erased or being-erased user, phase 1 stays under the shared try-locks). Reason: PostgreSQL grants new key-share lockers without queueing them behind a waiting `FOR UPDATE`, so overlapping sends of co-members could starve the victim's bounded `FOR UPDATE` (OAuth token rotation, `/oauth2/revoke`, `DELETE /devices`, the admin revoke: 300 ms `lock_timeout`). The 100 ms wait on the key share (429) and the order of `delete_device` (device row first) stay.
24. **Phase 2 is synchronous and best effort.** It runs in the request process after the commit and BEFORE the response (a quiescent state follows the answer; the existing cap tests stay valid), under its own `lock_timeout` and `statement_timeout`. A failure or timeout there NEVER fails the send: `200 {}`, the rows are queued, the transaction id is recorded (a retry is a no-op), the log names the error KIND only (never a row or a content), the excess stays until the next send evicts (the caps stay soft, as documented; with concurrent senders the caps are momentarily soft until the last second transaction has finished). The wake-up of the target devices happens right after phase 1, before the eviction. A retry of a recorded transaction runs no phase 2.
25. **11-risks (12) changes from an accepted residual to a CLOSED note** (key-share window only around the INSERT, eviction in a second transaction, residual: momentarily soft caps and a failed eviction leaves the excess until the next send); 07-deployment, 08-concepts and the CHANGELOG say so. The statement sequence of a send is still the same whatever the outcome of phase 1 (no timing oracle): phase 2 always runs for a fresh transaction.
26. **Old pins adapted or superseded by cycle 4:** see the list in the ATDD report, cycle 4 section (none was deleted).

**Open questions (owner / Kassandra)**

- Rate limit 60 / min, burst 30: a client that sends one `m.room_key_request` per missing session can exceed it in a burst (rooms are unencrypted here, so rare); alternatives: a higher burst, or a cost per target.
- Silent eviction of the oldest means a flooded device can lose an old verification message; per-sender shares (100 per device, 200 / 4 MiB per recipient user) and the fair user-level eviction bound one flooder; many colluding co-members, each below its share, remain an ACCEPTED residual.
- One request can wake up to 100 long polls of the victim's devices (each rebuilds its sync); bounded by the fan-out cap, the budgets, the rate limit and the requirement of a shared JOINED room. Accept, or gate the wake-ups? (accepted residual i4, also in 11-risks)
- The node-wide send slots (6) can be held by colluding accounts (4 per user): accepted (429, the client retries); buckets and slots are node-local (N x in a cluster).
- A crash of the send gate while holders are active (i3) is not tested beyond the restart test; accepted.
- Timing: the statement count is equal for delivered and skipped recipients (pinned); wall-clock differences (rows written, wake-ups sent) are not.
- **Accepted limits of the test suite (test review):** m9 the request is built with `Plug.Test` (always `application/json`, sized): no missing / non-JSON content type, no chunked or lying `Content-Length` and no Cowboy / Bandit listener in the path; m11 some tests couple to implementation names (the `content` column in the slow-commit trigger, the `user:<id>` `:pg` group name, `__opts__` of the worker, `to_device_shape?/1`, the wording regexes of the docs tests and the eviction log line); m12 `TD.statements/2` counts only the calling process's statements: an implementation that moves its work into another process escapes the count.
- `m.room.encryption` is still rejected (ADR-011): the queue only serves verification and key requests today. Dehydrated devices (not in v1.18) are out of scope; the `device_one_time_keys_count` / `device_lists` members of sync belong to story `device-key-directory`.
- No browser / Element end-to-end test in this step (the verification flow needs the whole stack: Dex, Element Web, two devices); the API level is covered through the full `Nebu.Web.Router` with real sessions and rooms. Release checkbox: Element Web <-> FluffyChat self-verification (SAS) and `/sync` long-poll latency with a real client.
- Crash reports: no test forces an unrescued crash inside the handler; the static scans forbid logging or inspecting content, conns and params in the to-device code.
