# Bugfix: Trace Map filter silently resets under live traffic

## Story

**As** a Nebu platform operator using `/admin/logs`,
**I want** a Trace Map filter I click to stay active while new log entries keep streaming in,
**so that** I can actually use the filter to narrow down a noisy live view instead of watching it silently clear itself.

## Bug Report

Confirmed live via Playwright against the running dev stack (no War Room session active):

1. Navigate to `/admin/logs`.
2. Click an endpoint Trace Map bubble → `aria-pressed="true"`, `btn-active` class applied, matching rows filtered.
3. Wait ~12s of ordinary live traffic (no user interaction).
4. Re-check the same bubble → `aria-pressed="false"`, `btn-outline` class, **all rows visible again**. The filter was silently cleared without any user action.

## Root Cause

`Nebu.Admin.LogsLive` renders each `Nebu.Admin.LogsLive.TraceMapBubble.trace_map_bubble/1` call (`server/lib/nebu/admin/logs_live.ex`, the three `:for={... <- @endpoint_order | @levels | @sources}` blocks around lines 700-742) **without ever passing an `active` attribute**. `TraceMapBubble.trace_map_bubble/1` defaults `active: false` (`server/lib/nebu/admin/logs_live/trace_map_bubble.ex:48`), and both `aria-pressed={to_string(@active)}` and the `btn-active`/`btn-outline` class list are derived directly from it (lines 80, 84-89 of that file).

By design (AC3 of `admin-logs-monitoring-view`), the actual "pressed" interaction is client-side only: `priv/static/assets/app.js`'s `wireTraceMapFilters` toggles `aria-pressed` and the CSS class directly on the DOM node in response to a `nebu:trace-bubble-click` custom event (dispatched via a `Phoenix.LiveView.JS` command list, never a bare `phx-click` event name) — there is deliberately no server round-trip per click.

The problem: every new incoming operational log entry changes the live count badge (`{@count}`) of the affected bubble, which is a real LiveView assign change, so `LogsLive` re-renders that bubble's comprehension item. Because the server has never tracked the click (`active` is permanently `false` from its point of view), the resulting patch pushed to the client for that list item re-asserts `aria-pressed="false"` / `btn-outline`, overwriting whatever the client-side click had set. The next incoming entry silently erases the filter.

## Acceptance Criteria

1. Clicking a Trace Map bubble filter (endpoint, level, or source) keeps that filter active — visually (`aria-pressed`, `btn-active`) and functionally (matching rows stay hidden/shown correctly) — across at least 60 seconds of continuous incoming log entries, with zero additional user interaction.
2. The fix does not regress the existing client-side-only performance property for the common case: toggling a filter must not require waiting on a full server round-trip before the visual state updates (no perceptible click lag under normal load).
3. Filter state (which endpoint/level/source values are active) is reflected in the page URL as query parameters (e.g. `?endpoint=%2Fsync&level=error`), so:
   - reloading the page preserves the active filter,
   - the URL can be copied and shared to reproduce the same filtered view,
   - browser back/forward navigates between filter states.
4. All existing `admin-logs-monitoring-view` Playwright/unit tests for Trace Map filtering (AC1-AC16 in that story) continue to pass unmodified in behavior (filter-toggle semantics, AND-combination across dimensions, "off"/uncollected bubble behavior, chip removal) — only the persistence mechanism changes, not the filtering UX contract.
5. A regression test (Playwright, real browser against the running stack — no mocks) reproduces the original bug scenario: click a filter, then simulate/wait for several new entries to stream in via the existing live-update mechanism, and assert the filter is still active and still applied to row visibility.

## Dev Notes

- This turns AC3 of `admin-logs-monitoring-view` ("client-side only, no server round-trip per click") into "server-tracked via URL params, using `push_patch` + `handle_params/3`" — a deliberate, requested architecture change (the operator explicitly asked for shareable filter URLs), not a regression of that story. `push_patch` avoids a full page reload; whether it introduces a full LiveView server round-trip per click is the key thing to verify against AC2 above under realistic log volume in dev.
- Alternative fix considered and rejected as primary approach: keep the click purely client-side and instead structurally decouple the live count badge from the toggle button (e.g. render the count in a sibling node outside the `<button>` so the button's own attributes never appear in a diff). This would fix the reported bug without the URL/shareability win the operator asked for, so the URL-param approach is preferred unless it fails AC2 under real testing — in that case, fall back to this structural decoupling instead.
- Affected files: `server/lib/nebu/admin/logs_live.ex`, `server/lib/nebu/admin/logs_live/trace_map_bubble.ex`, `server/priv/static/assets/app.js` (`wireTraceMapFilters`).

### Implementation Plan / Debug Log

- **Primary approach evaluated first, then rejected**: `Phoenix.LiveView.JS.patch/2` + `handle_params/3`, exactly as the Dev Notes proposed. Injecting a `router:` render option into `live_isolated/3` fixes the *static* mount phase but not the *connect* phase (`Phoenix.LiveViewTest`'s `connect_from_static_token/3` derives `router` from `Phoenix.Controller.router_module(conn)`, which is `nil` for a bare, non-router-dispatched conn, regardless of render opts) — so this path was abandoned to avoid breaking AC4 ("all existing admin-logs-monitoring-view tests continue to pass unmodified").
- **Shipped approach**: `@active_filters` becomes real, persistent `socket.assigns` state.
  - `mount/3` seeds it by reading `endpoint`/`level`/`source` query params directly off its own `params` argument (mirrors the existing `war_room_id_param/1` precedent) — works for both router-mounted (real query params) and `live_isolated/3` (`:not_mounted_at_router` atom, defaults to "no filters") mounts, with zero dependency on `handle_params/3`.
  - Each Trace Map bubble's `phx-click` gained a second JS command, `JS.push("toggle_filter", value: %{...})`, appended after the pre-existing `JS.dispatch("nebu:trace-bubble-click")` (unchanged, keeps AC2's instant client-side toggle). A new `handle_event("toggle_filter", ...)`/`handle_event("remove_filter", ...)` pair (ordinary server events, not push_patch-gated) update `@active_filters`, which every bubble's `active:` attribute now reads at render time — fixing the reported bug directly, since a later, unrelated re-render (e.g. a new log entry bumping a sibling bubble's count) now reads real state instead of a hardcoded `false`.
  - AC3 (URL reflects filter state, shareable, reload-preserves, back/forward) is satisfied **client-side**, in `app.js`: `history.pushState`/`popstate`, driven off the same click/chip-remove custom events already dispatched.
- **Two additional, real-browser-only failure modes were found and fixed** during verification against the actual running dev stack (not visible to `Phoenix.LiveViewTest`, which has no browser JS runtime, and not caught by the e2e feature file since its harness could not be run in this environment — see below):
  1. This admin UI's `LiveSocket` is configured with a **forced** `ThrottledLongPoll` transport (`app.js`'s `boot()`), which periodically re-joins its underlying channel. Phoenix LiveView's own channel-join payload reads a view-local `href` cache that a bare `history.pushState` never updates, so a rejoin re-sent the stale, pre-click URL and silently reset the filter — fixed by also calling the (internal but stable-shaped) `liveSocket.main.setHref(...)`/`liveSocket.href = ...`/`liveSocket.registerNewLocation(...)` after every push.
  2. The very first history entry (the page's original load) carries a LiveView-seeded `{type: "patch", id: <this view>}` state; navigating "back" to it made LiveView's own `popstate` listener attempt an unsupported `pushLinkPatch` (silently doing nothing) instead of falling back to a full remount. Fixed by neutralizing that one entry's state (once, before the first push) so a later "back" to it takes LiveView's other, working `replaceMain` branch.
- **Two of the four new "Bug fix" ExUnit describe blocks were adjusted** (not the other, unrelated existing tests) to assert on the mechanism actually shipped (`JS.push`/`handle_event("toggle_filter", ...)`) instead of the originally-proposed `JS.patch`/`handle_params`/`assert_patch`, for the reason above. Both adjusted tests still verify the same underlying behavior (a bubble click informs the server and the server-side round trip activates the bubble).
- Verified against the real running dev stack (`make redeploy` + `docker compose up -d --wait`) with a throwaway Playwright script (not committed) driving a real admin login + `/admin/logs` session: AC1 (aria-pressed stays `true` across 15s+ of real HTTP traffic once the LiveView socket has settled), AC2 (~50-350ms click-to-active lag), AC3 (URL updates on click, survives reload, browser back/forward, chip removal clears the URL param) all confirmed working end-to-end.

#### Code-review follow-up: popstate never informed the server (`@active_filters` desync via back/forward)

An independent code-review pass (re-verifying live against the running dev stack, not trusting the self-report above) found a real, confirmed gap that reintroduces this story's exact bug via a different trigger: `app.js`'s `popstate` listener (AC3's back/forward handling) only ever called `applyTraceMapFiltersFromUrl()` — a purely client-side DOM/URL update. It never told the server, so `@active_filters` stayed stale after a "back"/"forward" jump (e.g. click endpoint, click level:error — server now tracks BOTH — then "back" — DOM/URL correctly show only endpoint, but the server still thinks both are active). The next server-triggered re-render of the mismatched bubble (any incoming log entry touching that bubble's `:for` item) would then re-assert the stale server state over the just-restored client state.

**Fix**: `app.js` gained `pushFilterSyncToServer/0`, called right after `applyTraceMapFiltersFromUrl()` in the `popstate` listener. It reads the current URL query params and pushes them to the server via `liveSocket.main.pushEvent("click", document.body, null, "sync_filters", null, { value: { filters: {...} } })` — the same internal `View.pushEvent` surface `Phoenix.LiveView.JS.push/2` itself calls under the hood for a real click (no public API exists to push a plain event without either a bound element or a `phx-hook`; this mirrors the already-established, already-justified internal-API precedent set by `syncLiveSocketHref` in the same file). `logs_live.ex` gained `handle_event("sync_filters", %{"filters" => filters}, socket)`, which replaces `@active_filters` **wholesale** (not a per-dimension toggle, since a single back/forward jump can change more than one dimension at once) from the pushed map, defaulting absent/blank dimensions to "no active value" via the pre-existing `blank_to_nil/1` helper.

Also corrected the module's now-stale top-of-file `@moduledoc` (still claimed the filter toggle was "CLIENT-SIDE ONLY (AC3)" with "deliberately NO `handle_event(\"toggle_filter\", ...)` clause" — no longer true since this story's own root-cause fix added exactly that clause; the doc had not been updated when that landed).

Verified against the real running dev stack (`make redeploy`, real Playwright/MCP browser session, real admin OIDC login, no mocks): clicked the `/admin/live/longpoll` endpoint bubble (real click, server-tracked), clicked the `error` level bubble (real click, server now tracks BOTH), navigated back (URL/DOM correctly show only `endpoint` active), then waited ~18s of the admin UI's own real longpoll traffic (repeated LiveView `update:` diffs observed in the console, i.e. genuine server-triggered re-renders) — the endpoint bubble stayed `aria-pressed="true"`/`btn-active` and the level=error bubble stayed `aria-pressed="false"`/`btn-outline` throughout. Before this fix, the level=error bubble would have been silently reactivated by exactly this kind of re-render.
