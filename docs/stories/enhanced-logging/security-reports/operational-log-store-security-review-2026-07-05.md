## Security Review — operational-log-store (epic: enhanced-logging), cycle 1 (post code-review)

**Diff scope:** staged diff (`git diff --staged`). New persistent operational log store: `operational_logs` table (migration 000017), a generic app-wide Erlang `:logger` handler (`Nebu.Web.LogStore.Handler`), batching `Writer` GenServer, `PolicyCache`, `Retention` pruning, `RouteNormalizer`, and 5 new `server_config` policy keys. Wired into `RequestLogger`, `Sweeper`, `Application`, `Admin.DB`.
**Date:** 2026-07-05
**Reviewer:** Kassandra (nebu-agent-kassandra)
**Classification:** MEDIUM-only (no CRITICAL, no HIGH)
**Verdict:** APPROVED — no commit-blocking findings. 4 MEDIUM + 2 LOW advisories to address before epic end (several are latent/amplification surfaces the FOUNDATION story creates for the dependent stories `admin-logs-monitoring-view` / `admin-logs-retention-settings` / `war-room-mode`).

### Findings

| # | Severity | Location | Vulnerability | Remediation |
|---|----------|----------|---------------|-------------|
| 1 | MEDIUM | `log_store/retention.ex` (all clauses) + `log_store.ex:136` `should_persist?/1` | WARN/ERROR entries are **always persisted and NEVER pruned** — `Retention.prune_operational_logs/0` only handles `info`/`debug`. These entries can carry personal data (`user_id`, room IDs) in `message`/`metadata` and persist indefinitely. The story's claimed compensating control (retention pruning) does not cover the always-on tier → GDPR storage-limitation (Art. 5(1)(e)) gap. | Add an age cap (and/or max-count fail-safe) for warn/error, driven by a policy key; or explicitly document operational_logs as legitimate-interest with a bounded retention. |
| 2 | MEDIUM | `log_store/retention.ex`; `application.ex` (Writer child) | Unbounded table growth / disk-exhaustion DoS: same root cause as #1 — no TTL and no max-count for the always-persisted warn/error tier. A sustained error storm (IdP outage → repeated `Logger.warning`, etc.) grows `operational_logs` without bound. | Bound the warn/error tier (age + hard max-count safety cap), independent of admin config. |
| 3 | MEDIUM | `log_store/handler.ex` `log/2`, `parse_log_event/1`, `safe_metadata/1`, `render_msg/1` | The generic handler persists **every** log event verbatim with NO redaction of its own — including OTP/SASL crash reports (`{:report, ...}` → `inspect/1`) and arbitrary `Logger.metadata` (persist-everything-except-drop-list). Crash reports routinely embed function args / process state; a process crashing while holding or passed a token would leak it into `operational_logs` at ERROR level (always persisted, never pruned per #1). Previously such reports went only to ephemeral console/file. | Drop or truncate `:report`/crash-report events on the persistence path (still broadcast if desired); switch `safe_metadata` from a drop-list to an allowlist; truncate `message` length. |
| 4 | MEDIUM | pre-existing `payload_redactor.ex` `@always_content_keys` (leak) amplified by this story's persistence of `RequestLogger`'s DEBUG line | User-entered fields NOT in the fixed `@always_content_keys` list (`search_term`, `status_msg`, account_data values) are not redacted on the read path (`in_content?: false`) and leak into the DEBUG payload line. Root cause is pre-existing in `PayloadRedactor` (matrix-payload-debug-logging; recorded in Kassandra memory), but THIS story changes the risk profile transient→durable: with `log_collect_debug=true` these now persist in an admin-readable table. | Fix `PayloadRedactor` coverage (separate/pre-existing item) before enabling debug persistence in any deployment; note the dependency in the retention-settings/admin-view stories. |
| 5 | LOW | `log_store/handler.ex:139-147` `safe_broadcast/1` (AC10) | The handler broadcasts EVERY entry (including full DEBUG payloads) to PubSub topic `"operational_logs"` regardless of persistence policy. No subscriber exists today, but the later admin-logs-view / war-room live view MUST gate subscription behind admin auth and account for DEBUG-payload exposure even when debug persistence is off. | Watch-flag for the dependent UI story: authorize subscribers; consider not broadcasting redaction-sensitive payload lines. |
| 6 | LOW | `log_store/writer.ex` `write_async/1` (cast) + `flush_buffer/1` | The in-state buffer is bounded (flush at threshold 100), but the GenServer **mailbox** is not. Under a sustained log storm while `Nebu.Repo` is slow/down, the flush INSERT can block on pool checkout while `cast`s accumulate → memory pressure. | Consider overload protection (bounded mailbox / drop-oldest / sample under pressure); acceptable for MVP given low likelihood. |

### Detail

**Finding #1 & #2 — WARN/ERROR tier has no retention (GDPR + unbounded growth)** [MEDIUM]
`should_persist?/1` persists warning/error unconditionally (`should_persist?(level) when is_binary(level) -> true`). `Retention.prune_operational_logs/0` only issues `prune_ttl("info", …)`, `prune_ttl("debug", …)`, `prune_max_count("debug", …)`. There is no delete path for warn/error. Confirmed WARN/ERROR call sites embed identifiers, e.g. `event_dispatcher/server.ex:1666` `Logger.error("validate_token failed", user_id: user_id, …)`, `:4526` search_messages error with `user_id`, plus interpolated `room_id`/`user_id` in several `Logger.warning`/`Logger.debug` lines. Those identifiers now land in a durable, admin-readable table with no time bound and no erasure hook.

**GDPR erasure interaction (story's explicitly-deferred question).** Nebu's erasure model is crypto-shredding + deactivation, not hard-deletion of `user_id` references across all tables: `Nebu.Compliance.UserDeletion.delete_user_keys/3` NULLs private signing/encryption keys and sets `deletion_status='keys_deleted'`; `deactivate_user/2` sets `is_active=false` + destroys sessions. Neither touches `operational_logs`. So personal data (plaintext `user_id`/room IDs) in operational_logs survives an erasure request. This is tolerable for the pruneable info/debug tiers IF retention is bounded, but the always-on warn/error tier has NO bound — so the story's own compensating-control claim does not hold for the tier that is always collected. Assessment: real but MEDIUM (identifiers, not message content or credentials, in the common case; requires the durable table to be considered in a subject-access/erasure response). Recommend the retention-settings story cover warn/error and that operational_logs be enumerated in the GDPR erasure scope (or documented as legitimate-interest with a fixed maximum retention).

**Finding #3 — generic handler persists crash reports / metadata verbatim, no redaction** [MEDIUM]
By design (moduledoc "never a second unredacted leak path") the handler does no redaction and relies on upstream callers. That assumption holds ONLY for `RequestLogger`'s own payload line (which runs `PayloadRedactor`). It does NOT hold for the ~140 other `Logger.*` call sites, nor for OTP/SASL crash reports that the attached handler ALSO intercepts. `render_msg({:report, report})` inspects the whole report; `safe_metadata/1` keeps every metadata key except a bookkeeping drop-list. A GenServer crashing with a token in `:last_message`/`:state`/exit args would have that value inspected into `message` and persisted at ERROR level (always, forever). Point-1 caller survey result: no CURRENT call site passes raw chat content or raw credentials into the persisted path — `Nebu.Repo.QueryTelemetry` is verified sanitized (logs only `source`/`duration_ms`/`ok|error|unknown`, never `:query`/`:params`/the exception); credential-adjacent logs record one-way hashes / JTIs / DB error reasons, not secrets. The residual risk is the crash-report / future-caller vector, hence MEDIUM not HIGH.

**Finding #4 — pre-existing redactor gap amplified to durable storage** [MEDIUM]
`@always_content_keys = body formatted_body filename topic name displayname reason` is a fixed list; `search_term`/`status_msg`/account_data values are not covered on the default read path. Pre-existing PayloadRedactor limitation (already in Kassandra memory), not introduced here, but this story turns the sink from transient to durable when `log_collect_debug` is enabled.

### Points verified CLEAN

- **Point 3 — RLS allowlist (AC3).** Migration 000017 re-creates `config_update_mutable` FOR UPDATE with the 5 new keys added to the `USING (key IN (...))` allowlist, matching the established key-scoped pattern (contrast the cautionary migration 000045). With `WITH CHECK` omitted, PostgreSQL reuses `USING` as the row-check, so an UPDATE can neither target nor rename a row to a non-allowlisted key. No new caller-facing write path is introduced; the keys are writable only via the existing admin-authenticated `upsert_server_config/1`. No privilege-escalation vector. `.down.sql` correctly restores the 000016 allowlist.
- **Point 4 — SQL injection.** All three dynamic-SQL sites are parameterized: `Writer.insert_batch/1` builds `$N` placeholders from a fixed `@columns` list and entry index, values bound; `LogStore.build_where/1` filters keys against `@allowed_filter_keys` (column names never from caller data) and binds values; `Retention` binds `level`/`days`/`max_count` as params (`($2 || ' days')::interval`, `LIMIT $2`). No string interpolation of caller-controlled values into SQL anywhere in the diff.
- **Point 5 (buffer).** The Writer in-state buffer is bounded (flush at threshold 100, resets to `[]` on every flush including failures); no unbounded buffer growth. The PolicyCache correctly removes the `Nebu.Repo` re-entrancy/deadlock on the synchronous handler path (`:persistent_term` read, refreshed by a 2s GenServer + write-through hook in `upsert_server_config/1`). Residual mailbox-growth concern is Finding #6 (LOW).
- **Point 1 core.** `QueryTelemetry` does not log bind parameters, SQL text, user search terms, or the raw exception — clean.

### Summary

CRITICAL: 0 — block commit
HIGH: 0 — block commit
MEDIUM: 4 — advisory, address before epic end (findings #1–#4; #1/#2 share a root cause — add a warn/error retention bound)
LOW: 2 — advisory (findings #5, #6)

**Verdict:** APPROVED (no CRITICAL/HIGH). The two deferred questions resolve as: (1) redaction integrity into the new store is INTACT for all current callers (QueryTelemetry sanitized; no current call site persists raw chat content or credentials), with a MEDIUM residual on crash-report / arbitrary-metadata persistence (#3) and the pre-existing redactor-coverage gap now made durable (#4); (2) the GDPR-erasure interaction IS a gap for the always-on WARN/ERROR tier, which has no retention bound and is not reached by the crypto-shredding erasure flow — MEDIUM, best fixed by bounding warn/error retention in the retention-settings story and enumerating operational_logs in the erasure scope.
