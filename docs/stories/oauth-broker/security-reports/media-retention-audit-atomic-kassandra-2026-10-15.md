# Kassandra short review: media-retention-audit-atomic (2026-10-15)

Verdict: CLEAN (0 CRITICAL / HIGH, 1 MEDIUM fixed, 2 LOW, 5 INFO). Scope: value + `media_config_updated` row of `deleted_days` / `infected_days` / `released_delete_after_days` in ONE transaction in `Nebu.Media.Config.upsert/3`; a shortening needs the audit (refused otherwise), a lengthening / disabling is applied unaudited when the audit table is not writable.
- No way to force a unaudited shortening: the first attempt always audits; the single retry without audit runs a guard that re-reads the old value UNDER the lock; any other error is not retried; the two-step bypass (unaudited lengthening, then a shortening) is refused at step two; the test seams are not reachable in production.
- MEDIUM-1 (fixed): `released_delete_after_days = 0` was treated as the shortest retention (so 0 -> 5 a "lengthening"), but the only reader (`MediaReleasedAutoDeleteWorker.validated_window/0`) treats 0 as invalid = no deletion (off, like nil): 0 -> N switches auto-deletion ON. The guard now treats 0 like nil for this key (0 -> N is a shortening, audit mandatory; N -> 0 is a disabling); story D2b and 07-deployment corrected, tests.
- INFO-1 (fixed): an empty `sub` made the audit unwritable for that admin (actor ""): the controller falls back to `system:media_config`.
- LOW-1 (follow-up `du`): `deleted_days` / `infected_days` of `media_config` are NOT read by `MediaCleanupWorker` (it reads `:nebu, :media_cleanup`): the atomic audit protects two values that have no effect today; the docs / admin form describe an effect they do not have.
- LOW-2: an unaudited lengthening / disabling (`released_delete_after_days` -> nil switches data minimisation off) is an owner decision (D2), compensated only by a value-free ERROR line: an alert / telemetry counter for "applied without audit" would make it visible.
- Lock / DoS: one key per transaction, fixed order advisory lock -> row lock -> upsert -> audit, no deadlock, a retry is a second sequential transaction; RLS: the UPDATE policy lists the three keys, `pg_advisory_xact_lock` is executable. Logs: key and direction only. Cache: refresh + `:pg` broadcast only after the commit.
