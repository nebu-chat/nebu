| M-1 | MEDIUM | server.ex do_invite! -> invite_target_membership! -> write_invitation!, join_banned? | Event-order ban erasure through the new invite event (a new instance of the `ex` class, outside its documented scope): the ban check reads the latest membership outside the room process; the invite event is written later with ts = now. A ban landing in that window (ban_user rejects the pending row, writes the ban event) is followed by the re-arm upsert and a NEWER `invite` event: join_banned? reads `invite`, a pending row exists => the banned user can join. Before this story the invite path wrote a row only, so the ban stayed latest. Not exploitable today (no ban route, ban_user has no lib callers). The planned `ex` fix (atomic ban call) does NOT close it: invite still decides and writes outside the room process. | Extend `ex` to cover the invite writer and make it a gate for the ban route: serialise invite (membership/ban check + row + event) as ONE room-process call, or make the join ban decision read an authoritative ban record; test with a ban interleaving between the membership read and the event write. |
| M-2 | MEDIUM | validate_invite_list (cap 50), emit_invites, POST /createRoom | Invite spam / harassment amplification without a rate limit (`ey`, amplified 50x): unlimited rooms, each inviting 50 active local users with attacker-chosen name/topic/initial_state and is_direct; invitation rows per invitee unbounded; no invite blocking (m.invite_permission_config), no ignore list (fa b). Each invitation adds a :pg subscription + wake-up source to the victim's incremental /sync (L-3). Invisible in Element today (ev), becomes visible exactly when ev ships. | Make `ey` (per-user tier for /createRoom charged per invitee, /invite, /join) a release-gate item together with ev; per-inviter cap on pending invitations, per-invitee cap per inviter; M_INVITE_BLOCKED / ignore list with ev. |

| L-3 | LOW | do_incremental_sync {:new_event} branch | Pending-only rooms stay subscribed: every event there wakes the invitee's long-poll with an empty response (no confidentiality issue); with M-2 an attacker posting in N inviting rooms makes the victim re-sync in a tight loop with N :pg join/leave operations per sync. | In {:new_event, ev}, if the event's room is in pending_only_room_ids keep waiting (re-enter receive with the remaining timeout). |
