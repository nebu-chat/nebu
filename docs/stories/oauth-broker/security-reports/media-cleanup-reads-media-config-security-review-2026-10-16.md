Verdict: CLEAN (0 CRITICAL / HIGH / MEDIUM, 3 LOW (L-1 fixed, L-2 fixed, L-3 fixed), 4 INFO). Scope: `Nebu.Media.Config.retention_days/0` (strict direct read), the fail-safe branch of `MediaCleanupWorker.perform/1`, the catalogue default `infected_days` 90 -> 7, the removed `config :nebu, :media_cleanup`, docs. ## Checks
1. **Early deletion by a mis-read value: not possible.** `retention_days/0` runs its own fresh SELECT (not `get/0`, which falls back to defaults and whose refresh replaces a good cache by the defaults when one read fails). One statement reads both keys (`key` is the primary key: no duplicates, no partial read). RLS cannot hide a row (`media_config_read_all USING (true)`, `GRANT SELECT` to the runtime role). The parser accepts only `\A[0-9]{1,6}\z` (no sign, whitespace, trailing newline, Unicode digits, exponent, fraction) in 0..3650; everything else is `:invalid`; raise / throw / exit / a loader that is not a map / no Repo / a SQL error is `:unavailable`. On any error both fresh phases are skipped, the job returns `:ok` (no retry storm); the completion sweep only finishes rows that are already `:hard_deleted`. The window is bound as `Integer.to_string(days)` into `($1 || ' days')::interval` (days, never seconds; 3650 is far from interval overflow). The loader seam is set by no production config.
2. **`0` = delete at the next run** is the documented meaning (ADR-033, admin gate with fresh sign-in, atomic audit for shortenings). Residual: a UI trap next to `released_delete_after_days` (0 / blank = off): L-2.
3. **Silent change on upgrade:** values saved earlier (no effect so far) become effective at the next run: documented with a pre-upgrade SELECT (L-3). The infected default 90 -> 7 keeps the EFFECTIVE retention (the worker used 7); 90 would be a conscious increase (owner decision `eh`, not a finding).
4. **Audit / logs:** `media_hard_deleted` carries `retention_days` (the integer used); the INFO line logs the two day counts, the ERROR line only `reason=:unavailable | :invalid` and the keys, never a stored value (Law: No Sensitive Data in Logs).
5. **Multi-node / races:** a cron job run twice is harmless (`invalid_transition`); the window is read once per run: a lengthening during a run takes effect at the next run (INFO-3), a shortening during a run uses the longer window (safe).

## Findings
- **L-1 LOW (FIXED):** the writer (`upsert/3`) accepted any integer >= 0 for `deleted_days` / `infected_days` while the reader refuses > 3650: a future writer storing "keep forever" would silently stop ALL cleanup. Fixed: `validate_value/2` accepts exactly 0..3650 for the two keys (unit test; the sentinel values of the atomic-audit tests moved below 3650).
- **L-2 LOW (FIXED):** `deleted_days` / `infected_days` = 0 hard-deletes everything at the next run, irreversibly; no hint on the form, the neighbour field means "off". Fixed: a hint under both fields ("0 = at the next daily run, cannot be undone"); UX review in `step-results/media-cleanup-reads-media-config/`.
- **L-3 LOW (FIXED):** a never-effective saved value (for example `0` from a test) goes live at the first run after the upgrade. The pre-upgrade SELECT was docs only: now also an acknowledge item of the manual group E and "run the SELECT BEFORE deploying" in 07-deployment. (An optional first-run WARN was not added.)
- INFO-1 default 7 vs 90 = owner decision `eh`. INFO-2 the fail-safe delays GDPR erasure / infected removal when the value is damaged, only a daily ERROR line shows it (an alert / metric is optional; the ERROR now names the keys). INFO-3 window read once per run. INFO-4 the `:media_config_loader` seam is shared with `get/0` and never set in production.

Classification: CLEAN. Counts: CRITICAL 0, HIGH 0, MEDIUM 0, LOW 3 (all fixed), INFO 4.
