### Detail

**Finding #1 — Tier-1 display name ciphertext survives, decryptable with the server key** [HIGH]
`UserProvisioner.Postgres.provision_user/4` writes `display_name_encrypted, display_name_nonce` from `Signature.encrypt_operational_pii(display_name, server_key)`. `server_key` is `Application.get_env(:signature, :pii_encryption_key)` (`config/runtime.exs:449`), one key for the whole instance. Only `email_*` is encrypted to the user's `enc_pub` (`encrypt_sensitive_pii/2`). The erasure NULLs `user_keys.private_key` and leaves every `users` column except `deletion_status`, `keys_deleted_at` and `anonymized_at` untouched. So after a "successful" erasure, `SELECT display_name_encrypted, display_name_nonce FROM users WHERE user_id = '@alice:x'` plus the server key gives the plaintext name. Anyone with DB read access and the runtime config can do this: an operator, a backup consumer, a compromised node, or the server itself on the next login (`decrypt_and_return/1`). The project's own policy (08-concepts "Three PII Tiers": Operational PII -> "Overwrite with 'Deleted User'") requires the overwrite. The story applied it only to `profiles` and then documented `users` as "crypto-shredded". For a GDPR Art. 17 story whose acceptance criterion is "every row of personal data ... really gone", this is a blocking gap in the core claim, not an edge case. The fix is one SET clause, and the columns are nullable (000001).

**Finding #2 — Erasure is not terminal: re-authentication revives the account and reverts the anonymisation** [HIGH]
Exploit / failure scenario (standard user credentials, no attacker sophistication): employee Alice requests erasure of her chat data but stays employed, so her IdP account is live. The operator runs `delete_user_keys`. The next morning Element obtains a fresh IdP token (or Alice signs in again through SSO / the OAuth broker).
1. OidcPlug verifies the IdP JWT. Its `jti` is new, so the denylist does not hit. `do_provision/2` runs `TokenValidator.validate/4`: the row exists, `is_active` is true and `signing_key_id` is set, so `decrypt_and_return/1` succeeds (server key, #1). Then `upsert_profile(@alice, "Alice Example", nil)` sets `profiles.displayname` back to the real name for every room member.
2. `/sync`: `persist_sync_position` hits the D5 guard and returns `:skipped`. The next request falls back to an initial sync again, and that repeats for every long-poll. The cost is a full initial sync per request, rate-limited only per IP.
3. Device registration, `/keys/upload`, receipts and room account data re-create rows under the erased user. Global account data and cross-signing return 500 (D10), so the client is broken but not stopped.
4. Operator re-erasure answers `:conflict`. The only remover is the sweep, which does not cover sessions (#3).
The ATDD report even pins "a session created AFTER the erasure gets 404 for `m.direct`", so post-erasure sessions are treated as valid. The pre-existing behaviour (no deactivation on erasure) becomes a HIGH here for two reasons. This story introduces the anonymisation that login silently reverts. And its docs and Gherkin scenario 3 claim the erased user's tokens are rejected, which holds only for the Nebu-minted tokens the teardown happened to find. The fix (#2 (a)-(e)) is small and also makes the D5/D10 guards and limitation (f) belt-and-braces instead of the only line.

**Finding #3 — Post-commit teardown has no retry, and the sweep excludes its tables** [MEDIUM]
`end_sessions_after_erasure/1` wraps each step in `guarded/2`, which rescues, logs the struct name and continues. A single failed step leaves live session rows. `matrix_sessions.oidc_refresh_token` is an IdP refresh-token ciphertext under the server's AES key, a live credential to the IdP. The erasure itself reports success. Nothing re-runs the teardown, and the sweep note says these tables need no sweep. Conditions: a transient DB error or a node restart in the window after the commit. Not attacker-triggerable directly, hence MEDIUM. With #2 unfixed, the surviving tokens are also fully usable.

**Finding #4 — Unguarded in-flight writers** [LOW]
D10 covers only the two `sync_global` writers. The other erased tables have writers without a `deletion_status` predicate. The dev report states this as limitation (f). It is acceptable once #2 bounds the window to one request.

**Finding #5 — Crypto-shredding vs storage residue** [LOW]
Pre-existing (Story 5.7). Recorded because the new docs repeat the "irrecoverable" claim. The heap residue clears at VACUUM. The WAL, the backups and the replicas do not clear until their retention expires.

**Finding #6 — Avatar media object retained** [LOW]
See the table. The inventory reason does not fit avatars.

**Finding #7 — Sweep as an operator tool** [LOW]
Verified safe in scope: every statement keys on `user_id IN (SELECT user_id FROM users WHERE deletion_status = 'keys_deleted')`, active, deactivated and `deletion_in_progress` users are untouched (the sweep test pins all three), and a second run is a no-op (`anonymized_at` is updated only when NULL). The residuals are listed in the table.

### Verification of the focus areas

1. **(a) Inventory completeness.** I independently checked the tables of 000001 / 000041 / 000045 and the writers. The 13 erased tables, the teardown tables and the retained list match the schema. The schema guard (pg_catalog, FK + column-name patterns) is a sound recurrence control. Its blind spot is COLUMNS of an already classified table. `users` is "retained" as a whole, which is exactly how the Tier-1 ciphertext columns (#1) slipped through. Suggest a per-column allow-list for `users`. Also note `users.last_seen_at` (refreshed by `upsert_user` on every login) and `users.deactivation_reason` (admin free text that may describe the person): both are retained without a stated reason (INFO-1). ETS: the OidcPlug provisioning cache holds the user id only. The session ETS entry is evicted by `destroy_session/1`. No new cache holds content.
2. **(b) Migration 000055 / RLS.** The policy is `expires_at < now() - 24h OR EXISTS (SELECT 1 FROM users u WHERE u.user_id = oauth_codes.user_id AND u.deletion_status IS NOT NULL)`. The subquery is correlated to the ROW's `user_id` (not a parameter), so a DELETE can remove only codes whose own user is erased or being erased. `deletion_in_progress` is visible only inside the erasure's own uncommitted transaction (READ COMMITTED), so no other session can widen it. `users` has no RLS, so the subquery is not silently filtered. FORCE RLS stays on, as do the INSERT (`used_at IS NULL`), UPDATE (plus the `oauth_codes_guard` trigger) and SELECT policies, and there are no grant changes. An active user's unexpired code stays undeletable (the MAJOR-3 test). Reuse detection loses only the erased user's codes, so there is nothing to protect. Rollback: the down step restores 000041 exactly. The documented hazard (the old policy makes the erasure DELETE silently 0 rows) is correct and stated in the release note.
3. **(c) Races / locks.**
   - The D5 `INSERT ... SELECT ... WHERE EXISTS (... FOR SHARE)` waits on the erasure's `users` row lock (FOR NO KEY UPDATE conflicts with FOR SHARE). After the commit it re-evaluates the qual on the new row version and inserts nothing. It holds no other lock first (it is the first statement of the persist transaction, and the erasure never touches `sync_tokens`), so there is no cycle.
   - D10: the writer's `pg_advisory_xact_lock` is a separate statement, so the INSERT snapshot is taken after the lock is granted and sees the committed status. A writer that got the lock first commits before the erasure's DELETEs read, and its rows are deleted. A first-upload writer that INSERTs a new `cross_signing_keys` row is caught by the DELETE's fresh snapshot after the advisory wait.
   - Lock order: `users` -> `user_keys` -> `uia_sessions` -> `cross_signing_keys` -> advisory matches `replace_with_approval/7` (uia -> cross_signing row -> advisory). Neither writer locks `users` (a plain read; FK checks take FOR KEY SHARE, compatible with NO KEY UPDATE) or `user_keys`. Deadlock-free as analysed in the dev report. I found no other `sync_global|` lock holder (grep: only `put/3`, `put_keys/2`, the erasure).
   - DoS: the advisory key is per user and only the erasure (operator) takes it in a long transaction. A user can only contend their own row. No attacker-controlled lock amplification beyond INFO-2.
   - Concurrent erasures: `mark_in_progress` is atomic. The loser now returns `:conflict` via `unwrap_transaction/1` with no success audit (D14). Correct: `{:ok, {:error, _}}` only arises for a business error before any write, or for a failed statement whose aborted transaction Postgrex turns into `{:error, :rollback}`.
   - Resurrection via re-login: #2.
4. **(d) Sweep.** See #7. No injection, correct scope, idempotent, one transaction. Safe on a live DB apart from lock duration on large `read_receipts` / OTK tables (each DELETE is keyed by `user_id`; run off-peak).
5. **(e) Log law.**
   - The new D12 warning interpolates only `inspect(reason)` of `end_all_user_devices/1`, which returns only `:ok | {:error, :unavailable}` (rescue/catch to `:unavailable`; per-device failures are logged inside with `describe/1` and the device id). No token, name or IP.
   - D10 refusals reach the existing `error_kind/1` lines (atom only). The D5 skip logs nothing.
   - The attempted audit carries `inspect(error_reason)`, in practice `:rollback` (Postgrex aborted-commit) or a `check_user` DB error struct. Neither carries parameters (`Repo` `log: false`).
   - The pre-existing `Logger.error("delete_user_keys failed", target_user_id: ..., reason: inspect(reason))` and the `message: "deletion failed: #{inspect(reason)}"` error term carry the pseudonymous user id and an atom. Acceptable.
   - Note that OidcPlug's pre-existing "email/preferred_username claim absent for #{user_id}" warning would fire for a revived erased user (#2). It is harmless, but it is one more trace of post-erasure activity.
6. **(f) Audit integrity.** The success audit is written only after `{:ok, now_ms}`. The attempted audit is written in a separate transaction on a DB failure. There is no audit for `:conflict` or `:user_not_found` (spec AC3). The audit rows are untouched by every erasure statement and by the sweep (`audit_log` is not in `@erased_tables`, and the guard keeps it on the retained list). The append-only property remains application-enforced (accepted risk 13.14). Nothing new deletes or updates `audit_log`.
7. **(g) Crypto-shredding.** Email: valid only modulo storage residue (#5). Display name / avatar ciphertext: NOT shredded (#1). No code path copies `user_keys.private_key` into a cache or ETS. `Signature` holds private keys only transiently during provisioning.
8. **(h) Response differences.**
   - `GET /profile/{erased}` returns 200 `Deleted User`, while an unknown user gives 404. That reveals "this user existed and was erased" (INFO-3; Synapse-equivalent behaviour, and user ids are visible in retained events anyway).
   - The erased user's own dead tokens give 401 `M_UNKNOWN_TOKEN`. A peer reading the erased user's account data gets 403. Both are unchanged and give no cross-user oracle.
   - The D10 500 is returned only to the erased user themselves.

### Informational (no severity)

**INFO-1 — `users.last_seen_at` and `users.deactivation_reason` are retained without a stated reason.** `last_seen_at` is a behavioural timestamp (it keeps moving if #2 is not fixed). `deactivation_reason` is admin free text. Consider NULLing both in step 5, or listing them with a reason.

**INFO-2 — `FOR SHARE` on every initial sync.** Each one writes the tuple's xmax (a dirty page, WAL), and concurrent holders create MultiXacts. This is documented in the release note. One user can only churn their own row. Watch `pg_stat_user_tables` / `mxid_age` on busy instances.

**INFO-3 — `Deleted User` 200 vs 404** discloses the erased state. This is standard. Mention it in the runbook if the controller considers erasure itself confidential.

**INFO-4 — `:skipped` for a user without a `users` row** (previously an FK error) means a perpetual initial-sync fallback for such a principal. OidcPlug provisions the row on first sight, so this happens only after a provisioning DB error. It is fail-safe.

**INFO-5 — Verified positive:** all new SQL is parameterised (`$1`). The only interpolation is the compile-time `@erased_tables` identifier list. `erased_tables/0` drives both the DELETEs and the guard, so they cannot drift. The rollback of earlier steps on a failed DELETE is proven by the trigger test.

### Summary

CRITICAL: 0 — block commit
HIGH: 2 — block commit (#1 Tier-1 display-name ciphertext survives, server-key decryptable; #2 erasure not terminal: re-authentication revives the account and reverts the profile anonymisation)
MEDIUM: 1 — advisory, address before epic end (#3 teardown without retry/sweep coverage, IdP RT ciphertext can survive)
LOW: 4 — advisory (#4 unguarded in-flight writers, #5 crypto-shredding vs backups/WAL, #6 avatar media retained, #7 sweep operational gaps)

**Verdict:** NOT APPROVED. #1 and #2 must be fixed in this story. Both are small, local changes to step 5, the auth gates and the profile upsert, plus the sweep and docs. #3 should be fixed with them or recorded as a follow-up before the epic gate.

**(3) The new 403 mapping.** `403 M_USER_DEACTIVATED` for `:user_erased` is reachable only by the erased user's OWN still-cached bearer: the target is the authenticated user for account data and cross-signing. That is identical to "the target has no such cross-signing key", which an erased user indeed no longer has (deleted rows), so a third party gets no "erased" oracle beyond the pre-existing `/profile` `Deleted User` (INFO-3). Info-level log with the kind only: OK.

**(4) `step=<name>` audit / log, `safe_reason/1`.**
- Step names are compile-time atoms (`@erased_steps` built from the constant table list, plus fixed step atoms).
- `safe_reason/1` keeps only the SQLSTATE atom (`%{postgres: %{code: atom}}`) or a bare atom, and everything else becomes `:unknown_error`. No message, detail, constraint key values, statement or parameters can pass.
- The new `Logger.error` carries the step and the reduced reason, with no user id. The audit `error` field is `inspect` of the reduced reason. `error_detail` is `"step=" <> atom`.
- The dispatcher's pre-existing `Logger.error(... reason: inspect(reason))` and the raised `message` now receive only the reduced reason.
- Throw semantics: DBConnection's `transaction/3` rolls back on any `catch kind` (throw included) and re-raises it. The outer `catch :throw` converts it, and the tests prove the rollback for every step. The success audit is unreachable on a throw. The `:conflict` path is unchanged (no throw, `unwrap_transaction/1`).
- Log law satisfied.

**(5) `oauth_codes_not_erased` fail-closed: correct.** It runs after the `oauth_codes` DELETE inside the same transaction, the count is the user's own rows, and a count > 0 rolls back everything (status included) with an attempted audit. With 000055 present the count is 0, because the policy branch sees the transaction's own `deletion_in_progress`.

A refused merge stores nothing, and an error raises a static message (no values). The previous `:ok = ...` MatchError, which crashed with the statement in the error, is gone. Verified safe.
