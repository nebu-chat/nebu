# Story: `POST /createRoom` honours `preset` / `visibility`, `power_level_content_override` and `topic`, and `POST /join` enforces the join rule (follow-ups `ec`, `ef`, `ea`)

As a Matrix user (Element Web creating a private room, a DM, a public room or a Space) I want a room I create as private to be joinable only by
the people I invite, a user I ban to stay out, a public room to be really public, the permissions Element asks for (Spaces: only admins post,
private Spaces: only moderators invite) to be applied, and the topic I typed to be set. As an operator I want to know what the old behaviour
allowed, which existing rooms are affected and whether anybody joined a private room without an invitation.

Follows story `create-room-input-validation` (closed `ed`, `ee`, `eg`, `ei`; spec order, `emit_state_event_at/6`, `Server.validate_create_room_request/1`,
D6 errcodes). Not in this story: `eb` (`invite` / `invite_3pid` / DM `is_direct`, the next story), `em` (alias directory), `ep` (65536-byte event limit), `en`.

### The security finding (`ec`): every room that is not `restricted` is open-join, and bans are not enforced

| Claim / question | Verified state today |
|---|---|
| What join rule is effective without an `m.room.join_rules` event? | Two different answers. Display paths use `invite` (the Synapse / client convention for an absent rule; the v10 auth rules have no default) (`join_rule/1` `server.ex` ~l.2926, `Nebu.Matrix.RoomSummary` l.26, `JoinRules.join_rule/1`). The JOIN path does not care: `join_room/2` (~l.1142) calls `enforce_restricted_join!/2` (~l.1215), and `Nebu.Matrix.Room.JoinRules.check_join_allowed/3` returns `:ok` for every rule except `restricted` ("public / invite / default / knock / unknown — unchanged", moduledoc table). `Nebu.Matrix.Room.Server.handle_call({:join, ...})` (~l.318) only checks "already member" and `max_members`. |
| Can anybody join a private room by id? | **YES.** Any authenticated local user who knows a room id can `POST /_matrix/client/v3/join/{roomId}` and becomes a member: every private room, every DM, every private Space, every Admin-created room, every personal self-room, AND rooms with an EXPLICIT `{"join_rule": "invite"}` event. Probe on the dev server: `JoinRules.check_join_allowed([%{type: "m.room.join_rules", state_key: "", content: ~s({"join_rule":"invite"})}], "@mallory:x", has_invite?: false)` -> `:ok`; with no join_rules event -> `:ok`. They exist only when a client puts them into `initial_state`. |

(bundle 1.12.15, `createRoom` helper + `CreateRoomDialog.roomCreateOptions`) | **Private room:** `preset: "private_chat"`, `visibility: "private"`, `initial_state` = `m.room.guest_access {"guest_access": "can_join"}` (default `guestAccess: true`), `m.room.history_visibility {"history_visibility": "invited"}`, `m.room.encryption` (skipped by Nebu, ADR-011); NO join_rules entry (Element relies on the preset for `invite`); `name`, `topic` (if typed). **Public room:** `preset: "public_chat"`, `visibility: "public"`, `room_alias_name`, no guest_access / history_visibility / join_rules entry (relies on the preset), `name`, `topic`. **DM:** `preset: "trusted_private_chat"`, `invite: [user]`, `is_direct: true` (`eb`). **Space:** `preset` public_chat / private_chat, `power_level_content_override: {"events_default": 100, "invite": 0 (public) / 50 (private)}`, `visibility: "public"` only if the server advertises `org.matrix.msc3827.stable` (Nebu does not, so `private`), `initial_state` history_visibility `world_readable` / `invited`. **Video room / group calls:** `power_level_content_override: {"events": {...}}`. **Knock rooms:** `initial_state` join_rules `knock`, `visibility` per the dialog. ## Spec (Matrix CS API v1.18, local copy `skills/nebu-agent-oracle/matrix-spec/v1.18/`, `client-server-api/api.json` `/createRoom`, `index.html`)

- createRoom: "The server MUST apply the normal state resolution rules when creating the new room, including checking power levels for each event." Order: 1 `m.room.create`, 2 creator join, 3 default
  `m.room.power_levels` "Overridden by the `power_level_content_override` parameter" (v1-11: the creator, not other members, may send state events), 4 `m.room.canonical_alias` (`room_alias_name`),
  5 preset events (`m.room.join_rules`, `m.room.history_visibility`, `m.room.guest_access`), 6 `initial_state` in list order, 7 `name` / `topic`, 8 invites.
- Presets: `private_chat` = join_rules `invite`, history_visibility `shared`, guest_access `can_join`; `trusted_private_chat` = the same + "All invitees are given the same power level as the room creator"
  (and, v12+, invitees SHOULD be appended to `additional_creators`; Nebu is v10); `public_chat` = `public`, `shared`, `forbidden`. `preset` enum `private_chat` / `public_chat` / `trusted_private_chat`;
  "If unspecified, the server should use the `visibility` to determine which preset to use": `public` -> `public_chat`, `private` -> `private_chat`.
- `visibility`: "The room's visibility in the server's published room directory. Defaults to `private`." enum `public` / `private`.
- `initial_state`: "Takes precedence over events set by `preset`, but gets overridden by `name` and `topic` keys."
- `power_level_content_override`: "The power level content to override in the default power level event. This object is applied on top of the generated `m.room.power_levels` event content prior to it
  being sent to the room. Defaults to overriding nothing." (No deep-merge rule; Synapse applies it as a shallow top-level update.)
- `topic`: "an `m.room.topic` event with a `text/plain` mimetype will be sent ... This overwrites any `m.room.topic` event in `initial_state`." `m.room.topic` content: `topic` (string, required),
  `m.topic` (v1.15, `{"m.text": [{"body", "mimetype" (default text/plain)}]}`, `topic` SHOULD duplicate the text/plain representation); absent / `null` / `""` topic = no topic. No length limit in the spec.
- 400 reasons (open list): `M_BAD_JSON` / `M_NOT_JSON`, `M_ROOM_IN_USE`, **`M_INVALID_ROOM_STATE`** ("the initial state implied by the parameters to the request is invalid: for example, the user's
  `power_level` is set below that necessary to set the room name"), `M_UNSUPPORTED_ROOM_VERSION`.
- Room v10 auth rules (`rooms/v10`): power-level values MUST be integers (no strings, no floats) in the range [-(2^53)+1, 2^53-1]; `events` / `notifications` are objects of integers, `users` keys are user ids. Join auth order: sender != state_key -> reject; banned -> reject; `invite` / `knock` -> allow only if the current membership is `invite` or `join`; `restricted` / `knock_restricted` -> `invite` / `join` or an authorising allow condition; `public` -> allow; OTHERWISE reject (so `private`, unknown and malformed rules reject even an invited user; strictly, an ABSENT join_rules event rejects too: treating it as `invite` is Synapse / Nebu policy, not spec text). Invite auth: a target that is joined or banned -> reject (a banned user never holds a pending invite). The 403 errcode of a refused join is not specified; `M_FORBIDDEN` is used. `POST /_matrix/client/v3/rooms/{roomId}/join` is a spec endpoint Nebu does not route.
  `restricted` / `knock_restricted` -> invite or an allow condition; a `ban` membership always refuses the join; an unknown rule refuses.

## Decisions

- **D1 (join authorization, the security fix).** `join_room/2` decides, in this order, BEFORE `Room.Server.join/2`:
  1. Already a member -> idempotent 200 exactly as today (no rule or ban check; an invite-only room must not 403 its own members' re-join, Element does that).
  2. Latest `m.room.member` of the user is `ban` -> `403 M_FORBIDDEN` with the fixed text **"You are banned from this room"**, whatever the rule (also for `public` and `restricted` and with a pending invite).
  3. The effective join rule = `join_rule` of the latest `m.room.join_rules` (state_key `""`):
     - NO `m.room.join_rules` event at all -> treated as `invite` (**Nebu / Synapse policy, not spec text**: strict v10 would reject every join, even an invited one; this keeps legacy rooms joinable by invitation, D10);
     - `public` -> allowed;
     - `invite`, `knock` -> allowed only with a pending invite (`pending_invite?/2`), else `403 M_FORBIDDEN` with the fixed text **"You are not invited to this room"** (the SAME text for every rule refusal: absent, `invite`, `knock`, `private`, unknown, malformed, `restricted` / `knock_restricted` without a grant);
     - `restricted` and `knock_restricted` -> the existing restricted decision (pending invite OR member of a valid `allow[]` room);
     - `private` (reserved by the spec), every unknown value, and a MALFORMED event (content without a string `join_rule`, an empty / non-string value, undecodable content) -> `403 M_FORBIDDEN` ALWAYS, even with a
       pending invite (strict v10 "otherwise reject"; such a room can be repaired by a member with PL >= 50 setting a valid rule).
  The 403 body is `{"errcode": "M_FORBIDDEN", "error": <fixed text>}` for both refusals (ban text / rule text above) and reveals no state: no room id, user id, rule or membership value in either text. `Nebu.Matrix.Http.map_error/1` today maps EVERY `permission_denied` to `"You are not a member of this room"` and ignores the message, so the two texts need an **opt-in override** (decision of the test review): `map_error` honours the message (and the errcode) of a `permission_denied` `Nebu.Matrix.Error` only when the error carries an explicit `errcode` (like `invalid_argument` since the previous story); every existing `permission_denied` stays unchanged. The join refusals raise with `errcode: "M_FORBIDDEN"` and the two texts. The tests pin: ban text != rule text, all rule refusals identical, exact strings; an unknown / not running room stays `404 M_NOT_FOUND` (unchanged).
  **Invite of a banned user** (v10 invite auth): `invite_user/2` answers `403 M_FORBIDDEN` when the target's latest membership is `ban` (no invitation row is written), so a ban can only be lifted by `/unban`. The target's latest membership is read through `rooms_db_module().get_member_membership/2`; a FAILING read is `500` (fail closed, like the join path).
  **Later route:** `POST /rooms/{roomId}/join` is a spec endpoint Nebu does not route; when it is added it MUST go through the same D1 decision (recorded in the scope doc, AC15).
  The decision stays in the PURE module `Nebu.Matrix.Room.JoinRules` (extend `check_join_allowed/3`: `:banned?` option; new table; moduledoc updated), `join_room/2` resolves the impure inputs.
  **Fail closed:** a failing read of the join rule state or of the latest membership is `500` (no join, value-free log with `db_error_class/1`), NOT "no state = invite" (an honest error instead of a misleading 403;
  today `restricted_join_state/1` swallows errors into `[]`, which was harmless only because `[]` meant open). A missing pending-invite read keeps today's semantics (`false` = no invite: fail closed).
  The direct `Room.Server.join/2` callers keep bypassing (creator join, upgrade creator join, auto-join = admin policy); `admin_add_room_member/3` keeps working through its invite, but for a BANNED target it now
  answers an error (D1.2; the Admin UI has no unban: follow-up `et`). No audit row for a refused join (unchanged: the restricted refusal writes none either).
- **D2 (presets, spec step 5).** `preset` absent / `null` -> derived from `visibility` (`"public"` -> `public_chat`, absent / `null` / `"private"` -> `private_chat`). Events (sender = creator, state_key `""`):
  `private_chat` and `trusted_private_chat` -> `m.room.join_rules {"join_rule": "invite"}`, `m.room.history_visibility {"history_visibility": "shared"}`, `m.room.guest_access {"guest_access": "can_join"}`;
  `public_chat` -> `{"join_rule": "public"}`, `{"history_visibility": "shared"}`, `{"guest_access": "forbidden"}`. A preset event whose `(type, "")` is also set by an `initial_state` entry that will be APPLIED
  (not a skipped type) is NOT written (**Synapse parity, not spec text**; the match is on state_key `""` ONLY: an `initial_state` `m.room.join_rules` entry with a non-empty state_key does not suppress the preset event; the resulting state is the same, the timeline has one event less). The `trusted_private_chat` "invitees get the creator's power level" rule is SPEC-NORMATIVE; it needs `invite`
  and is delivered by `eb` (noted in its follow-up row); until then `trusted_private_chat` writes the same events as `private_chat`. Every preset event is fatal on failure (500, orphan cleanup): it defines who can join. `guest_access` is written although Nebu has no guests (spec; cosmetic, `es`).
- **D3 (one strictly increasing timestamp chain for steps 4-7).** The `last_ts` of the previous story is threaded: explicit alias (step 4) -> preset events (step 5, each `emit_state_event_at(..., last_ts + 1)`) ->
  `initial_state` (step 6, unchanged) -> `m.room.name` (step 7, now written through `emit_state_event_at/6` with `last_ts + 1` instead of `now_ms()`) -> `m.room.topic` (step 7, after the name) -> the derived
  canonical alias (Nebu feature, after the name as today, `last_ts + 1`). So `initial_state` beats the preset and `name` / `topic` beat `initial_state` deterministically, without sleeps, also with 64 entries in one
  millisecond. `m.room.create`, the creator join and the power levels (steps 1-3) keep their timestamps (different `(type, state_key)` slots). The name write stays NON-fatal (as today), so does the topic (D5).
- **D4 (`preset` / `visibility` validation, in `validate_create_room_request/1`).** `preset`: absent / `null` ok; a non-string -> `400 M_BAD_JSON`; a string other than the three presets -> `400 M_INVALID_PARAM`.
  `visibility`: absent / `null` ok; a non-string -> `400 M_BAD_JSON`; a string other than `public` / `private` -> `400 M_INVALID_PARAM`. Convention of the previous story: wrong type = `M_BAD_JSON`, wrong value =
  `M_INVALID_PARAM` (Synapse uses `M_BAD_JSON` for both; the spec leaves the code open). Fixed messages, no client value.
- **D5 (`topic`, step 7).** Top-level `topic`: absent -> no event; `""` -> an event `{"topic": ""}` is WRITTEN (spec: "If this is included ... overwrites any `m.room.topic` event in `initial_state`"; Synapse does the same; an empty topic = unset, so it clears an `initial_state` topic; NO `m.topic` block for `""`); a PRESENT `null` (decided in the ROUTER, see D11: the core cannot tell `null` from absent), a non-string or a string with NUL -> `400 M_BAD_JSON` (unlike `name`, which keeps the previous story's `null` = absent); more than
  **1024 Unicode code points** -> `400 M_INVALID_PARAM` (**Nebu policy**, not spec: generous for a channel description, cf. Discord / Teams / Mattermost 1024; keeps `/sync`, summaries and the Admin Space form bounded; 1024 accepted).
  Content written: `{"topic": t, "m.topic": {"m.text": [{"body": t, "mimetype": "text/plain"}]}}` (spec: "with a `text/plain` mimetype"). The same content rule on EVERY writer of `m.room.topic`
  (top level, `initial_state` entry, `PUT .../state/m.room.topic`, hence also the Admin Space form via `Nebu.Matrix.set_space_state/5`): `topic` absent / `null` / `""` valid; non-string `400 M_BAD_JSON`; cap `400 M_INVALID_PARAM`;
  `m.topic` absent / `null` or an object whose `m.text` is absent or a list of objects with a string `body` (at most **4096** code points each: markup allowance, **Nebu policy**; an empty `m.text` list is valid; `m.topic` may differ from `topic`, it is not cross-checked) and an optional string `mimetype`,
  else `400 M_BAD_JSON` / `M_INVALID_PARAM` (the cap is otherwise bypassable: `RoomSummary` shows the `m.topic` text/plain body first). Reuse the name helpers (`name_too_long?/1` generalised to a cap argument,
  `validate_name_string/2` pattern). The top-level topic write is non-fatal like the name (value-free warning). Order in `validate_create_room_request/1`: right after the name checks (top level, then `initial_state` entries).
- **D6 (`visibility` stores the directory flag).** There is no room directory (`publicRooms` unrouted, `ad`). `visibility: "public"` writes `rooms.visibility = 'public'` through the existing audited
  `set_room_visibility/3` with the creator as actor (one `room_visibility_changed` row), so the Admin rooms list shows a room Element created as public as "Public" and a future `publicRooms` (`ad`) has its
  publication flag; the publication POLICY (may every user publish? Synapse `room_list_publication_rules`) is decided by `ad` (noted in its row). `private` / absent writes nothing (column default `'private'`).
  Non-fatal like the Admin path today (the flag has no behavioural effect; a failed write leaves the conservative `'private'`; value-free warning). `Nebu.Matrix.create_room/2` passes its `:visibility` option as
  the request's `visibility` (so an Admin "Public" room gets `public_chat` = join rule `public`, matching its label) and DROPS its own post-create `set_room_visibility` call (no double write / audit row);
  its pre-create allowlist check (`{:error, :invalid_visibility}`) stays. `create_space/2` passes nothing (private Space -> `private_chat`).
- **D7 (`power_level_content_override`, spec step 3: shallow merge, validated, no creator lock-out during creation).**
  - Merge: `Map.merge(default_levels_with_creator_100, override)`, top-level keys REPLACE (Synapse parity; an override `users` map replaces the default `users` map, so a client that wants to keep the creator
    lists it, as Element's file-tree code does; Element's Space override has no `users` key and keeps the creator at 100). The merged content is written once at step 3 through the existing
    `Room.Server.set_power_levels/3` (one `m.room.power_levels` event, `rooms.power_levels_json`). Absent / `null` -> today's content exactly.
  - Validation (before the room exists, `400 M_BAD_JSON` with a fixed message, first failure wins): the override is an object (the override itself `null` = absent); a PRESENT key with a JSON `null` value (`{"ban": null}`, `{"users": null}`, a `null` inside `events` / `users` / `notifications`) -> `400 M_BAD_JSON`; `ban`, `kick`, `invite`, `redact`, `state_default`, `events_default`, `users_default`
    if present are integers (JSON integers only: no float, string, boolean; room v10 rule) within the canonical-JSON range ±(2^53 - 1); `events` an object of non-empty string keys (at most 255 bytes) to such integers;
    `users` an object whose keys are valid user ids (`Nebu.Matrix.UserId.valid?/1`; a non-local but well-formed id is accepted, harmless without federation) to such integers; `notifications` an object of
    such integers. Other top-level keys are kept as sent (forward compatibility), bounded by the existing depth (32) / NUL rules (the size bound is the 1 MB body cap like every state content: `ep`, noted in its row).
  - **Creator lock-out = `400 M_INVALID_ROOM_STATE` (the spec's own example).** With the merged levels the creator's level (`users[creator]`, else `users_default`) must reach the required level
    (`events[type]` when it is an integer, else `state_default`) of EVERY state event the server writes on the creator's behalf after step 3: the explicit canonical alias, the preset events of D2, every applied
    `initial_state` entry (skipped types do not count; an `m.space.parent` entry counts although its guard may still skip it), `m.room.name`, `m.room.topic`, the derived canonical alias (with a name and no
    `room_alias_name`). Checked in the pure validation, so a refused request creates nothing. Because a preset always writes at least one state event unless `initial_state` replaces all three, an override that
    takes away the creator's state power is refused in practice; an override that only restricts LATER actions (e.g. `"kick": 101`, `"invite": 100` for another user, `users_default: 100`, a demoted creator
    with per-type `events` exceptions) is applied as is (spec). This check uses spec semantics (the `events` map) although the runtime check `PowerLevels.can?/3` ignores `events` (`eq`); documented.
  - Consequences documented, not prevented (spec-compliant): `users_default` >= 50 makes every joiner able to change state (incl. the join rule); since power levels cannot be changed after creation (`eq`), a
    restrictive override is permanent; the Admin and Space paths never send an override (unchanged content), Element's Space override (`events_default: 100`, `invite: 0 / 50`) is now enforced by `can?/3`
    (only PL 100 posts messages in a Space; in a private Space only PL >= 50 invites), Element's video-room `events` entries are stored, not enforced (`eq`).
- **D8 (`initial_state` `m.room.power_levels` stays skipped).** The spec has no merge for it (premise above); honouring it means a REPLACEMENT at step 6 through the GenServer-authoritative path with a threaded
  timestamp and the D7 lock-out simulation over the rest of the plan; no known client needs it (Element uses the override). It stays in `@initial_state_forbidden_types` (skipped with a warning, the room is created)
  and the docs label it a **documented spec deviation** (keep the warning: room id + type only); follow-up `er`. With both an override and a skipped `initial_state` power-levels entry, the override's merge is what the room gets.
- **D9 (`rooms.topic` is not written).** The column is dead (no reader, no writer); writing it only at create time would make it a second, unmaintained copy (the PUT path would not sync it). Every topic reader uses the
  event. No migration, no column change.
- **D10 (existing rooms: no backfill; two read-only operator queries).** No event is written into existing rooms. Effect of D1 on them: a room without an `m.room.join_rules` event (all rooms created before this
  story unless their `initial_state` set one) is now invite-only. That is the intended state for every private room, DM, private Space and personal room. Rooms that were meant to be public (Element "public room"
  creates, Admin "Public" rooms, public Spaces created without an `initial_state` join rule) lose open join until a member with PL >= 50 (the creator has 100) sets Access: Public (Element: Room settings ->
  Security & Privacy, a `PUT .../state/m.room.join_rules`, allowed) or invites the users. A guessed backfill would have to infer intent (`rooms.visibility` is an Admin label, Element public rooms left no marker); the
  `invite` policy for an absent rule (D1) is the fail-closed choice that still lets invitations work. The docs give two queries (verified against a throwaway database inside a rolled-back transaction, like L-3 of the previous story): **Q1** rooms without any
  `m.room.join_rules` event, with `rooms.visibility`, `room_type`, `creator_user_id`, member count and whether an `m.room.history_visibility` event exists (Element private rooms have one, Element public rooms do
  not) for the operator to review; **Q2** incident review: `m.room.member` `join` events whose `state_key` is not the room creator, in rooms that are not `is_auto_join`, with no `room_invitations` row for
  `(room_id, invitee_id = state_key)` = joins that could only have happened through the old open join (legitimate for public rooms, suspicious for private rooms / DMs). Q2's limits are stated (one invitation
  row per (room, user), Admin force-adds have a row, joins before invitations were tracked cannot be told apart).
- **D11 (where the checks live, order).** Router: passes `params["preset"]`, `params["visibility"]`, `params["topic"]`, `params["power_level_content_override"]` RAW (any JSON type) in
  `Core.CreateRoomRequest` (new keys `preset: nil`, `visibility: nil`, `power_level_content_override: nil`; `topic` exists; **`null` vs absent:** in the request struct both are `nil`, so the ROUTER answers a PRESENT `"topic": null` (`Map.has_key?(params, "topic") and is_nil(params["topic"])`) with `400 M_BAD_JSON` before the core is called (covered by the HTTP test only); the core treats `nil` as absent (unit test documents it); `lib/pb/core.pb.ex` hand-edit comment extended, `proto/core.proto` comment-level parity).
  Core: `validate_create_room_request/1` order (first failure wins): name -> **topic** -> creation_content -> room_version -> room_alias_name -> initial_state aliases -> **preset / visibility** ->
  **power_level_content_override shape** -> **creator lock-out** -> alias-taken pre-check (stays the only DB read, last). Example for a test: an invalid `preset` together with a taken alias answers `M_INVALID_PARAM`.
