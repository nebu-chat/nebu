### Detail

**Finding F-1 — The ingress for two unvalidated URL fields widened from infra-only to admin-UI-writable; the invariant that justified LOW last time is gone** [LOW]

This is the directed question, and the answer is: the risk **class** is unchanged, the **justification** is materially weaker, and it still lands at LOW — but on one leg instead of three.

The predecessor story's F-1 (2026-10-01) carried at LOW on three independently-verified legs, recorded as MEMORY pattern #93:

1. **No DB/admin write path exists, structurally.** `column_for/2` ended in a `defp column_for(_unknown_key, _value), do: nil` catch-all that silently dropped these keys, and `validate_storage_params/1` built a closed key set that never routed params to them.
2. **Env-sourced config is trusted by design.** `build_resolved/2` resolves `endpoint` from `NEBU_MINIO_ENDPOINT` with zero validation; the module's deliberate split is *DB-sourced (admin-writable) values are SSRF-validated, env-sourced (operator) values are not*. An actor who can set process env already owns the node.
3. **There is no sink.** Zero consumers, so no request to redirect.

**This diff deletes legs 1 and 2 outright.** Leg 1 is gone by construction: `column_for(:iam_endpoint, value), do: {"iam_endpoint", value}` is exactly the clause whose absence was the structural guarantee, and `put_env_backed_field/5` is exactly the param route that did not exist. Leg 2 inverts: the values are no longer env-only, they are DB-sourced — which puts them on the side of the module's own trust split that is *supposed to be validated*. Only leg 3 survives.

I verified leg 3 rather than inheriting it, and I confirm the correction carried from the 4th code-review pass is right:

- `config_overrides/1` (`storage_config.ex:1054-1065`) builds the ExAws option list from exactly six candidate keys — `access_key`, `secret_key`, `host`/`port` (split from `endpoint`), `scheme` (from `use_ssl`), `region`. It never reads `iam_endpoint`/`sts_endpoint`. `candidate_from_params/1` now *carries* the two keys into the candidate map, and `test_connection/1` → `resolve_candidate_secrets/1` → `default_test_connection/1` passes that map along — but the two keys fall off the end, inert. **"Test Connection dials the new URLs on demand" is false.** There is no live outbound-request surface.
- `grep -rn "StorageConfig" server/lib` outside the module itself: only `media.ex:494` (`.s3_key_prefix_template`) and the admin controller. `Nebu.Media.Storage` still never calls `get_for_connection/0`. No consumer anywhere.

So why still LOW and not MEDIUM? Three things hold it down, and I want them on the record so the next reviewer does not have to re-derive them:

- **Same trust boundary, weaker primitive.** The actor is an authenticated instance-admin (`require_admin` → `current_user["admin"] == true`). That actor can already rewrite `endpoint`, `bucket`, `access_key` and `secret_key` through the *same form* — i.e. point all future media at a store they control. Against that, writing an unreachable URL into two columns nothing reads is not an escalation.
- **No sink.** Severity tracks exploitability, and there is no request to redirect. Per the skill's definitions this is "best-practice deviation without direct exploit path" = LOW, not "requires chaining with other issues" = MEDIUM. A future code change is not a chain with an existing issue, and I will not inflate on that basis.
- **The DB value cannot reach a request path by accident**, because no request path reads it.

What I will not do is repeat last time's framing that this is merely a watch-flag. It is now the **only** unvalidated admin-writable endpoint-shaped field on this table — the exact shape of MEMORY pattern #237 ("in-tree shared SSRF guard bypassed on ONE admin-supplied-endpoint surface while sibling surfaces use it"), which was raised against `endpoint` itself at the 2026-07-20 epic gate and fixed there. The fix regresses the fix's *principle* on two new columns. And it is pattern #51's asymmetry in its purest form: on one rendered page, `webhook_url` is `SSRF.check/1`-guarded at save and `checked_target/1`-guarded at send, `endpoint` is `checked_target/1`-guarded at both controller and persist, and these two are guarded nowhere.

**On the `invalid_endpoint_scheme?/1` asymmetry — confirmed correct, and confirmed *not* to be the gap.** The guard rejects a `http://`/`https://` prefix because `endpoint`'s contract is a bare `host[:port]`; `iam_endpoint`/`sts_endpoint` are full URLs, so applying it would reject every legitimate value. That reasoning is sound and the asymmetry creates no gap by itself. But — naming precisely which layer is incompatible, per MEMORY pattern #93 — the incompatible layer is *only* `invalid_endpoint_scheme?/1` and `validate_candidate_endpoint/1`'s scheme pre-check. `Nebu.Media.SSRF.checked_target/1` itself **requires** an `http`/`https` scheme and takes full URLs; it would validate `https://host:4443/iam` perfectly. So "the guard can't be applied here" is true of the wrapper and false of the guard. The absence of a scheme assertion is the other half: `endpoint`'s transport is decided server-side from the `use_ssl` boolean, so the cloud-init `NEBU_MINIO_USE_SSL: "true"` fence covers it; for a URL-valued field the scheme travels inside the value and the fence buys nothing (MEMORY pattern #56). Nothing anywhere enforces `https://` on these two.

**Finding F-2 — Widening the `SELECT` couples the whole storage-config read path to migration 000037, and the failure mode is silent reversion plus an orphan-gate bypass** [LOW]

`@sql_load_media_storage_config` is a static column list. Adding `iam_endpoint, sts_endpoint` to it means that if either column is absent, the query fails with `column … does not exist`, `default_loader/0` logs `Logger.warning` and returns `nil`, `safe_load/0` passes that `nil` through, and `build_resolved(nil, env)` resolves **every** field from the env-var fallback and compiled defaults — including `resolve_secret/5`, which falls back to `NEBU_MINIO_ACCESS_KEY_FILE`/`NEBU_MINIO_SECRET_KEY`. The module's own `MINOR-2(a)` comment at line 807 states the principle this violates: *"a corrupted ciphertext or a rotated/wrong at-rest key must not silently fall back to the env-var credential — that is a security-relevant substitution the admin has no other way to notice."* The same substitution is reachable here by a different route.

The second consequence is new and was not recorded against the pre-existing LOW: `persisted_target/0` returns `:fresh` on `nil`, so `handle_storage_save/3` takes the `:fresh` branch — which **skips both the orphan-risk gate and `changed_storage_keys/1`**, persisting the undiffed submitted form map and naming every submitted field in the audit `changed_fields`. An admin saving during the skew window silently re-points the storage target with no "existing files will become unreachable" warning. `persisted_iam_sts/0` inherits the same conflation (`N3-M3` in cycle 3) and now gates a *write* decision, not just a gate decision.

How reachable is this? Mostly not, and I want the bound stated honestly: `server/Dockerfile:42`'s entrypoint is `./bin/nebu eval 'Nebu.Release.migrate()' && exec ./bin/nebu start`, so a forward deploy always migrates before serving, and a rollback to *old* code against a *new* schema is harmless (the old SELECT is a subset). The realistic trigger is an operator running `000037_…down.sql` against a live new release, or a partially-restored DB. That narrowness is why this is LOW and not MEDIUM. The reason it is a finding at all is that the blast radius is disproportionate to the cause: two cosmetic columns can revert the credential source for the entire media store, and the only signal is one `Logger.warning`.

### Directed questions — answered

**1. Can an unauthenticated or lower-privileged actor reach `put_env_backed_field/5`? No. Verified end-to-end.**
`put_env_backed_field/5` is a private function reachable only from `validate_storage_params/1`, reachable only from `save_storage/2`. `Nebu.Admin.Router:203` registers `post "/media/settings/storage"` inside `scope "/admin"` with `pipe_through :browser`, and `MediaSettingsController:113` declares a **module** plug `plug Nebu.Admin.Auth, :require_admin`, which Phoenix runs before every action in the controller. `require_admin/2` (`auth.ex:119-130`) matches `%{"admin" => true}` on `conn.assigns[:current_user]` and otherwise `redirect |> halt()`. `fetch_current_user/2` (`auth.ex:153-163`) sources that map **exclusively** from `get_session(conn, "current_user")` — never from params, query string, or headers — so there is no param-shadowing or header-injection route to a forged admin assign. The `:browser` pipeline additionally runs `protect_from_forgery`, and the storage form emits `<input type="hidden" name="_csrf_token" value={Plug.CSRFProtection.get_csrf_token()} />`, so no cross-site forced write of these fields is possible. The `maybe_skip_csrf/2` escape hatch is gated on `Application.get_env(:nebu_http, :admin_csrf_bypass, false)`, which is never set outside the test env, and affects CSRF only — never the auth gate. Regression tests exist at both levels (`media_settings_controller_test.exs:1530`, `:1551` assert 302 + `refute_received` on the writer seam). **No auth bypass; no privilege change versus `endpoint`/`bucket`.**

**2. Does `persisted_iam_sts/0` leak anything the masking was designed to prevent? No.**
`safe_load/0` returns the raw DB row, which *does* contain `access_key_encrypted`/`secret_key_encrypted` (SecretBox ciphertext). `persisted_iam_sts/0` extracts exactly two keys by name via `Map.get/2` and discards the row — it never returns, logs, or `inspect`s it. There is no `Logger` call in the function and no error branch that could carry row contents: the `nil` case is a literal two-key map, and the only logging in the chain is `safe_load/0`'s `inspect(e)` of an *exception* (pre-existing; `default_loader/0`'s own rescue logs a `Postgrex.Error` whose payload is the static SQL text, no bound values, no secrets). The two returned fields are correctly **not** routed through `mask_map/1` — `mask_map/1` is a targeted two-field rewrite of `access_key`/`secret_key` only, and these are public service URLs, not secrets. Confirmed intentional and consistent with both this story's AC2 and the predecessor's. **Nothing about this accessor reintroduces a secrets-adjacent leak.** One non-security note: it calls `safe_load/0` directly, bypassing the ETS cache, so each storage save issues one extra `SELECT` — identical to `persisted_target/0`'s long-standing behavior, admin-authenticated, not a DoS lever.

**3. Migration 000037 hygiene — GRANT reasoning holds; RLS reasoning holds.**
`ADD COLUMN IF NOT EXISTS` / `DROP COLUMN IF EXISTS` guards present on both files, matching the repo convention (000002/000004/000012/000019/000021). The no-new-GRANT reasoning is **correct**: MEMORY pattern #88's fail-open class (`new-table migration ships with no GRANT … TO nebu_app`; dev `ALTER DEFAULT PRIVILEGES` masks it, prod fails open with the read path silently serving compile-time defaults) applies specifically to `CREATE TABLE`. In PostgreSQL a table-level `GRANT SELECT, INSERT, UPDATE, DELETE ON <table>` is not a column snapshot — it covers all columns, present and future. I verified `000024_media_storage_config.up.sql` issues exactly that grant for `nebu_app`, and this migration is a pure `ALTER TABLE` on that table, creating no new table and no sequence. So there is nothing for `MigrationsGrantTest`'s hand-maintained enumeration to miss here. RLS is likewise unaffected: `media_storage_config` has `ENABLE` + `FORCE ROW LEVEL SECURITY` and three policies — `storage_config_read_all` (SELECT `USING (true)`), `storage_config_insert_only` (INSERT `WITH CHECK (id = 1)`), `storage_config_update_singleton` (UPDATE `USING (id = 1)`) — all **row**-scoped on the singleton `id = 1`, none column-scoped, so added columns inherit the existing policy set with no `ALTER POLICY` needed. (The missing explicit `WITH CHECK` on `storage_config_update_singleton` is pre-existing, safe via PostgreSQL's implicit `WITH CHECK = USING` fallback, and untouched by this diff — same disposition as the 9a `media_config` F-3.) `release_test.exs` version list bumped to include 37, with the GRANT rationale recorded inline. Down-migration drops both columns and no index/constraint/policy references either. **Clean.**

**4. Audit trail — confirmed consistent, and the premise is stricter than assumed.**
`write_audit/2` (`storage_config.ex:603-622`) passes `%{changed_fields: Map.keys(fields)}` — **field names only, never values**, for every field including the secrets. So the question of whether plaintext iam/sts URLs in the audit log are acceptable is moot: no value of any field, secret or not, ever reaches the audit log. `:iam_endpoint`/`:sts_endpoint` appear in `changed_fields` exactly as `:endpoint`/`:bucket`/`:region` do — fully consistent, no special-casing, nothing leaked. The audit action is the pre-existing `media_storage_config_updated`, already present in `AuditWriter.@known_actions` (`audit_writer.ex:138`) — **no new action, so the known audit-allowlist merge gotcha does not apply here.** The cycle-2/cycle-3 `has_db_override?` work also tightened audit *accuracy*: a blanked env-sourced field no longer emits a false `changed_fields` entry for a write that did not happen.

**5. Template placeholder `7mf5k.upcloudobjects.com` — not live infrastructure.**
`grep -rn "7mf5k"` across the repo returns only: this template's two `placeholder=` attributes, test fixtures in the two touched test files, and the predecessor story's `bug-context.md:15`, which sources it explicitly from UpCloud's provider-schema documentation (`iam_url = "https://7mf5k.upcloudobjects.com:4443/iam"`). It appears in **no** `deploy/tofu/**` file, no `.tfvars`, no compose file, and no environment config — i.e. nowhere that would indicate a Nebu or innoq tenant. It is a `placeholder` attribute, so it is a greyed hint that is never submitted and never persisted. **Not a leak.** One cosmetic recommendation only (matching code-review MINOR-7): UpCloud object-storage hostnames are tenant-scoped in *shape*, so a hash-looking label in a UI hint reads like a real account identifier to anyone who does not know its provenance. Prefer an obviously-synthetic example such as `https://objects.example.com:4443/iam`.

### Observations (non-findings)

- **O-1 — The 5-branch `put_env_backed_field/5` logic itself is sound; I traced all five branches independently.** `is_nil(raw)` (absent param) → no-op, correct and now consistent with `maybe_put_field/3`. `submitted == baseline` → omit, with both sides normalized through `blank_to_nil/1`, which is what makes a whitespace-padded or `""`-valued env var converge instead of re-writing forever. `submitted == nil and has_db_override?` → explicit `nil`, which reaches `column_for/2` → `build_columns/1` → `default_writer/2` as a genuine `SET iam_endpoint = $n` with a `nil` parameter (verified through to the SQL; `build_columns/1` drops only keys for which `column_for/2` returns `nil`, i.e. unknown atoms — never a `nil` *value*). `submitted == nil` without an override → omit. Otherwise persist. The `has_db_override?` argument is correctly sourced from `persisted_iam_sts/0`'s **raw** row, never the merged view, and is normalized through `blank_to_nil/1` at the call site (cycle 3's N3-M1 fix, present at `:399`/`:405`). No branch can write a value the submitter did not supply, and no branch writes to any key other than the one passed. **No logic flaw with a security dimension.**
- **O-2 — No injection surface in the widened write path.** `column_for/2`'s two new clauses map to hardcoded string literals `"iam_endpoint"`/`"sts_endpoint"`; `default_writer/2` interpolates column *names* into SQL but sources them exclusively from that fixed mapping, with every value bound as `$n`. Admin-supplied strings reach only the parameter positions. Confirmed unchanged from the pre-existing, already-reviewed shape.
- **O-3 — XSS: clean, with defense in depth.** Both new values reach the browser only as HEEx attribute interpolations (`value={@storage_config.iam_endpoint}`), which Phoenix escapes via `Phoenix.HTML.Safe`. `storage_config_from_params/1` echoes the *raw submitted* value back on a blocked/invalid re-render through the same escaped path. Neither value is ever rendered as element content or into a `<script>`/URL context. The admin CSP (`router.ex:86-92`) is `script-src 'self'` with no `unsafe-inline`, so even a hypothetical escape would not execute.
- **O-4 — Non-binary param → 500, pre-existing class, two new instances.** A scripted admin POST with `iam_endpoint[]=x` yields a list, and `blank_to_nil/1` has clauses only for `nil` and `is_binary/1` → `FunctionClauseError`. This is exactly code-review MINOR-6/cycle-3's carried item. Assessed: admin-authenticated only; `String.trim(params["endpoint"] || "")` already raises identically for `endpoint`/`bucket`/`region`, so this is parity not regression; the raise happens before any DB write so no partial state results; and `debug_errors` is set nowhere in `server/config/`, so Phoenix's default `false` applies and the 500 carries no stack trace. **No information disclosure, no DoS lever.** Adding a `defp blank_to_nil(_), do: nil` catch-all would close the whole class in one line.
- **O-5 — Carried forward, still open: the predecessor's F-2 (`""` vs `nil` divergence).** `runtime.exs`'s `normalize_optional_env` maps `"" -> nil`; `StorageConfig.maybe_put_env/2` still stores `""` verbatim, so `get/0` can return `iam_endpoint: ""` while `Application.get_env(:nebu_http, :media_iam_endpoint)` is `nil`. This diff does **not** resolve it, but it does neutralize it on the new write path (`put_env_backed_field/5` normalizes both sides through `blank_to_nil/1`) and the new `runtime.exs` comment explicitly warns future consumers off the app-env keys. Remediation unchanged from 2026-10-01: normalize per-key in `build_resolved/2`, never in the shared `maybe_put_env/2`.
- **O-6 — A `""` written to either column by a non-controller caller would be permanently unclearable from the UI.** `upsert/2` is public and `column_for(:iam_endpoint, "")` passes `""` through verbatim; `pick/3` then treats `""` as present and shadows the env var, while `blank_to_nil("")` makes both `baseline` and `has_db_override?` read as "unset", so rule 1 omits every subsequent save. Unreachable through the admin UI today (the controller can only ever write `nil` or a trimmed non-empty string). Convergence nit, **no security dimension** — recorded so it is not rediscovered as a mystery.
- **O-7 — Pre-existing, non-security, flagged because I verified it while tracing the write path:** a no-change resubmit of the storage form (target unchanged, no optional fields) makes `changed_storage_keys/1` filter `changes` down to `%{}`, and `default_writer/2` then emits `INSERT INTO media_storage_config (id) VALUES ($1) ON CONFLICT (id) DO UPDATE SET ` with an empty `SET` clause → SQL syntax error → `{:error, …}` → "Failed to save storage settings". Introduced by story 11b's cycle-2 `changed_storage_keys/1` addition, not by this diff; no injection, no auth bypass, no partial write. Worth a guard (`if changes == %{}, do: :ok`) at the team's convenience.
- **O-8 — Explicitly recorded so it is not re-raised: "Test Connection dials the new URLs on demand" is FALSE.** `config_overrides/1` reads six keys and none of them is `iam_endpoint`/`sts_endpoint`. There is no live request path. The real residual is the absence of validation (F-1), nothing more. Cycle 3 already dismissed this as a layer false-positive; I re-verified it independently and concur.
