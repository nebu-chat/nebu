### Detail

**Finding F-1 — New URL fields carry no scheme or SSRF guard, and the stack's transport fence does not reach them** [LOW]

`endpoint` in this module is defended at two points: `upsert/1` → `validate_endpoint_field/1` → `validate_candidate_endpoint/1` (DB-write path) and `test_connection/1` (pre-request path). That guard does two separate jobs — reject a scheme prefix (because `endpoint`'s contract is a bare `host[:port]`), and run `SSRF.checked_target/1` (loopback / RFC1918 / link-local / CGNAT / `169.254.169.254` rejection). `iam_endpoint`/`sts_endpoint` get neither.

Today that is *harmless*, and I verified it rather than assuming it:
- `grep -rn "media_iam_endpoint\|media_sts_endpoint" server/lib server/test server/config` → only the two `runtime.exs` writer lines. `grep -rn "iam_endpoint\|sts_endpoint" server/lib server/test | grep -v storage_config` → zero hits. **Nothing reads either value.** No outbound request is constructed from them anywhere.
- `Nebu.Media.Storage` does not call `get_for_connection/0` at all; it uses the `config :ex_aws` application env, which this diff leaves byte-identical. So the new keys do not even reach the ExAws option set.

The reason this is still worth a finding rather than silence is the *shape*, which is MEMORY pattern #86 ("value plumbed in but not yet reflected → pre-register the sink, never wave through as CLEAN"). The bug-context explicitly names the likely follow-up: a runtime STS `AssumeRole` exchange against `sts_url`. That is a **credential-bearing** outbound call. When it is written, the value flows into an HTTP request with:
- no scheme enforcement — an `http://` STS URL would carry the credential exchange in cleartext, and
- no private-IP guard,

while the sibling field `endpoint` sitting in the same returned map *does* carry both. That asymmetry inside one config struct is the trap: a developer who has read "endpoint is SSRF-validated" will reasonably assume the struct is.

The transport point is the concrete, non-obvious half and is a direct recurrence of MEMORY pattern #56 one layer up. `cloud-init.tftpl:500` pins `NEBU_MINIO_USE_SSL: "true"` as a non-overridable template constant — exactly the fence pattern #56 prescribes. But that constant governs only `endpoint`, whose scheme is decided *server-side* from the `use_ssl` boolean (`runtime.exs:143`, `config_overrides/1`). For `iam_endpoint`/`sts_endpoint` the scheme is part of the string, so `USE_SSL=true` buys them nothing. The upcloud provider supplies `https://` today, so the shipped path is fine — the gap is that nothing *enforces* it.

**Finding F-2 — `""` means two different things to the two readers of the same env var** [LOW]

`runtime.exs:126-136` added `normalize_optional_env` (`nil -> nil`, `"" -> nil`, `value -> value`) in response to code-review MINOR-2. `StorageConfig`'s `maybe_put_env/2` (line 1060) has no such normalization — it stores any non-`nil` `System.get_env` result, so `NEBU_MINIO_IAM_ENDPOINT=""` yields `Application.get_env(:nebu_http, :media_iam_endpoint) == nil` **and** `StorageConfig.get().iam_endpoint == ""` simultaneously.

The cloud-init `%{ if s3_iam_endpoint != "" ~}` guard closes the UpCloud-stack route to this (verified at `cloud-init.tftpl:491-496`, byte-identical idiom to the `oidc_issuer != ""` guards above it), so it is not reachable from the shipped deployment. It remains reachable by hand (a `docker-compose` env entry, a Helm value, an operator export). The security weight is entirely latent and entirely about the future consumer: `if is_nil(cfg.iam_endpoint)` and `if is_nil(Application.get_env(...))` take opposite branches on the same misconfiguration — the classic shape behind "the control silently did not apply." Deliberately scoped to the two new keys in the remediation: changing the shared `maybe_put_env/2` would alter behavior for `NEBU_MINIO_ENDPOINT`/`BUCKET`/`ACCESS_KEY`/`SECRET_KEY` too, which is a broader change than this bugfix should make.

### Directed question — does the "no `validate_candidate_endpoint/1`" reasoning hold?

**Yes, the conclusion holds. The stated reason is incomplete and partly wrong; the real reason is stronger.** I did not take code-review INFO-3 on trust.

INFO-3 says the guard is "correctly NOT applied … (it would reject every UpCloud `https://` URL)." That is true of the *wrapper* only, and it quietly implies no SSRF validation is available — which is false:

- `Nebu.Media.SSRF.checked_target/1` (`ssrf.ex:50-60`) takes a **full URL** and *requires* an `http`/`https` scheme (`uri.scheme not in ["http","https"] -> {:error, :bad_scheme}`). It would validate `https://7mf5k.upcloudobjects.com:4443/iam` perfectly. It is `validate_candidate_endpoint/1`'s own `String.starts_with?(downcased, "https://") -> {:error, :invalid_endpoint}` pre-check — present solely because `endpoint`'s contract is bare `host[:port]` — that is incompatible. So "the SSRF check can't be applied here" is not the case; only "that particular wrapper can't."

The argument that actually carries the conclusion is the **trust boundary**, and all three legs verified:

1. **No DB/admin write path exists, structurally.** `column_for/2` (line 559) ends in `defp column_for(_unknown_key, _value), do: nil`, and `build_columns/1` drops every `nil` — so even a hand-crafted `upsert(%{iam_endpoint: "http://169.254.169.254/"})` is silently discarded before the DB write. Upstream, `media_settings_controller.ex`'s `validate_storage_params/1` (lines 295-320) builds a **closed** key set (`endpoint`/`bucket`/`use_ssl` + five `maybe_put_field` keys) — no params route to these fields. `changed_storage_keys/1` filters the *submitted* map, so the two extra keys now present in `StorageConfig.get()` cannot leak into `changes` either. There is no admin, API, or request-borne writer.
2. **The module already treats env-sourced config as trusted, by design.** `build_resolved/2:696` resolves `endpoint` from `NEBU_MINIO_ENDPOINT` with **no** validation call — the guard lives only on the DB-write and test-connection paths. The deliberate existing contract is: *DB-sourced (admin-writable) values are SSRF-validated; env-sourced (operator) values are not.* The two new fields are env-only, so they land entirely on the already-trusted side of a boundary that predates this diff. Setting process env is operator/root-equivalent — an actor there already owns the node and does not need an SSRF primitive.
3. **There is no sink.** Zero consumers (verified above), so there is no request to redirect even in principle.

Net: no SSRF finding against this diff, and I'd have reached the same verdict independently. F-1 records the residual as a watch-flag precisely because leg 3 is the one that expires.

### Observations (non-findings)

- **O-1 — Terraform / cloud-init injection surface: none.** `${s3_iam_endpoint}` lands in a double-quoted YAML scalar inside a `write_files` docker-compose block. The value's provenance is the UpCloud provider API response for a resource the operator owns (`upcloud_managed_object_storage.nebu_media[0].endpoint[].iam_url`) — not attacker-reachable, and the same provenance/quoting as the pre-existing `${s3_endpoint}` line directly above it. The `%{ if ... ~}` directives sit at column 0 with trailing `~}` (newline-stripping), matching the four existing `oidc_* != ""` guards; both template variables are always-defined strings (`var.enable_media_gateway ? ... : ""` ternaries at `server.tf:19-32`), so the `!= ""` comparison can never hit an undefined variable. `deploy/tofu/examples/stackit/cloud-init.tftpl` is a separate file — no cross-example `templatefile` breakage from the new required vars.
- **O-2 — Dead STS plumbing next to long-lived static keys: a false-assurance risk, and the genuinely security-valuable follow-up.** `main.tf:72-77` provisions `upcloud_managed_object_storage_user_access_key` with `status = "Active"` and no expiry — **long-lived static S3 credentials**, which is the stack's actual credential-hygiene posture. This diff adds STS plumbing that nothing uses, plus an output whose description reads "Use as `NEBU_MINIO_STS_ENDPOINT` when configuring external S3 clients." An operator reading that output can reasonably conclude short-lived STS-issued credentials are now in play. They are not; the credential lifetime is unchanged. STS is exactly the mechanism that would *fix* the long-lived-key exposure, so the follow-up story the bug-context flags has real security value beyond the functional need — recommend it be framed that way, and that the two output `description`s say "provisioned for future use; not currently consumed by the server" until a consumer lands.
- **O-3 — Secret handling clean.** No credential enters the new paths: `NEBU_MINIO_ACCESS_KEY_FILE`/`SECRET_KEY_FILE` remain Docker-secret file references, untouched. The new values are public service URLs, correctly **not** marked `sensitive` in `outputs.tf` (consistent with `media_s3_endpoint`), and they already exist in Terraform state via the parent resource — no new state or log exposure. `mask_map/1` (line 824) is a targeted two-field rewrite (`access_key`/`secret_key`) and is unaffected by the wider map. No `Logger`/`inspect` of the resolved config exists (`storage_config.ex:886,894` log only an error `reason`). AC1's "never masked" is correct: these are not secrets.
- **O-4 — `test-iac-validate` extension is a net security gain, supply-chain posture unchanged.** `deploy/tofu/examples/upcloud/.terraform.lock.hcl` is git-tracked (not ignored) and pins `upcloudltd/upcloud 5.39.1` with 13 `h1:` + 13 `zh:` hashes, so the added `tofu init -backend=false` is hash-verified and introduces no new unpinned provider fetch. The target previously validated `aws`/`stackit`/`k8s` only — this closes a real gap where the upcloud example could drift unvalidated.
- **O-5 — PRE-EXISTING, not introduced here: `upcloud_managed_object_storage_bucket.nebu_media` (`main.tf:60-64`) has no `lifecycle { prevent_destroy = true }`.** This is MEMORY pattern #55 verbatim, the same gap flagged as MEDIUM-1 against the Stackit bucket on 2026-05-26, now confirmed present in the UpCloud example too — an `enable_media_gateway` flip-to-false, a `tofu destroy`, or state surgery deletes the bucket and all customer media. Explicitly **not** a finding against this diff (the diff only reads `.endpoint[]` off the adjacent service resource and adds outputs); recorded because I had the file open and the data-loss surface is customer media. Recommend folding into the same follow-up as O-2, since both touch `main.tf`'s object-storage block. Companion long-lived-key rotation gap noted in O-2.

### Summary

CRITICAL: 0
HIGH: 0
MEDIUM: 0
LOW: 2 — F-1 (scheme/SSRF guard + transport fence do not extend to the two new URL fields; watch-flag, becomes MUST-FIX the moment a consumer is wired) and F-2 (`""`/`nil` divergence between the two readers of the same env var). Both are advisory hardening with no present exploit path.

**Verdict:** APPROVED — no commit-blocking findings. Classification: **CLEAN**.

**Carried forward as a SEC-Gate MUST-VERIFY for the anticipated STS follow-up story:** before `sts_endpoint`/`iam_endpoint` is read by any outbound-request code, that story must (a) assert `https://` on both values, (b) run `Nebu.Media.SSRF.checked_target/1` on both, (c) reconcile the `""`→`nil` divergence between `runtime.exs` and `StorageConfig`, and (d) confirm the STS-issued credentials actually replace — not merely supplement — the long-lived `upcloud_managed_object_storage_user_access_key`.
