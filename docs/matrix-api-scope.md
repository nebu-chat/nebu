# Matrix API Scope

This document provides a full inventory of Matrix Client-Server API endpoints and their
implementation status in Nebu. Derived from `server/lib/nebu/web/router/protected.ex` and
`server/lib/nebu/web/router.ex` route registrations, cross-referenced with the Matrix
Client-Server API specification.

**Legend:**
- ✅ Implemented - real handler with database-backed logic
- 🔶 Stub - returns a hardcoded or minimal valid response; no persistent storage
- ❌ Intentionally excluded - will not be implemented (by design)
- ⏳ Planned - requires ADR decision before implementation
- 🔲 Not implemented - no route registered; known gap, tracked as a potential follow-up
- Rule for every 🔲 row and every route not listed (story oauth-room-summary-unrecognized): since this story an unrouted Matrix endpoint answers `404 M_UNRECOGNIZED` and an unsupported method `405 M_UNRECOGNIZED` + `Allow`, without an auth check; `POST /register` answers `403 M_FORBIDDEN` (registration not enabled, RU10a); HEAD on GET routes answers 405 (deviation from the RFC 9110 SHOULD). Exception (RU11a): the unimplemented `GET /rooms/{roomId}/state[/{eventType}[/{stateKey}]]` keeps `404 M_NOT_FOUND` (clients read it as "state absent").

## Sync

| Method | Endpoint | Status | Notes |
|---|---|---|---|
| GET | `/_matrix/client/v3/sync` | ✅ | Long-poll (max 25s cap, was 30s); initial sync parallel room fetch (Task.async_stream, max_concurrency: 5); top-level global `account_data.events` delivered from durable PostgreSQL store — full on initial sync, changed-only on incremental: per device by the position `account_data_pos` of the device's since-token row (story sync-token-per-device; device-less clients keep the consume-once `changed` flag of account-data-durability); `rooms.join.<id>.account_data.events` delivered from `user_room_account_data` using the `stream_pos` carried in `since`/`next_batch` (`<core>.<pos>`), per device, account-data-only rooms included (room-account-data-and-read-markers). **Partitioned by membership (story sync-membership-partition, follow-ups `ev` + `ez`, both closed).** One partition function classifies every room of the user (latest membership with a fixed tie order, see below) as join / invite / leave / none, and a room id is in at most ONE section: `rooms.join` = joined rooms only (decided by the membership row; a latest `ban` event demotes it to `rooms.leave`, so even the half state of `ex` is never in `rooms.join`, not even as an account-data-only room), delivered as before. `rooms.invite` (`rooms.invite.<id>.invite_state.events`) = stripped state events with exactly the keys `type`, `state_key`, `sender`, `content`: `m.room.create` (required since v1.16, synthesized for a legacy room without one), name, avatar, topic, canonical alias, join rules and encryption as they are now, the inviter's member event, and the invitee's OWN invite member event with its real sender and `is_direct` (Element's `getDMInviter` and the DM marking need it); an invitation without an invite event (a row-only invitation: room upgrade, legacy) gets a synthesized own member event from the invitation row; invitations from users in the invitee's `m.ignored_user_list` are suppressed (the sender of the invite event counts; sync side only, an unreadable list suppresses nothing). Initial sync = joined rooms + every pending invitation, never `rooms.leave` (no `include_leave` support). Incremental sync: an invitation is delivered when it is new against the device's cursor of the room (by position and class, story sync-stream-position) and then not repeated (a row-only invitation is delivered once as well; it never ends a long-poll on its own); a message in an invited room neither arrives nor wakes the poll. `rooms.leave` (`rooms.leave.<id>`: left, kicked, banned, removed by an Admin, declined) is delivered ONCE, incremental sync only: the timeline holds the events after the since token strictly before the leave event (the newest 20, `limited` with a `prev_batch` when more), then the leave event itself, and nothing at or after it (an event in the same millisecond as the leave is excluded; the window ends at the leave event or at the end of the membership row, `room_members.left_at`, when that is earlier, so a removal whose leave event write failed does not open a window over the time the user was already out of the room); for a declined or banned invitation it is the leave event alone; `state` and `account_data` are empty by design (Nebu choice: the current state would carry changes made after the leave; when a leave window is `limited` the state changes in the gap before the window are not delivered); a non-limited timeline has no `prev_batch` key; afterwards the room is in no section and its events do not wake a long-poll. A taken-back invitation (a leave event at least as new as the invitation whose row reject failed) is a leave, never an invitation, and is not joinable. The tie rule: two member events of the user in the same millisecond are ordered most restrictive first (`ban`, `leave`, `invite`, `knock`, `join`: the most restrictive is the latest), in the sync, the join decision and the ban check. A forgotten room stays out until the user re-joins or is re-invited. `full_state` (`full_state=true` with `since`) is honoured (returns at once, every joined room with its full state, new invitations and leaves as usual, never a non-joined room in `rooms.join`). `use_state_after` (v1.16) is not supported: `/versions` stays below v1.16 and no `state_after` is sent (pinned). KNOWN DEVIATION (`fg` (a)): `filter` (including `include_leave`, `lazy_load_members`, timeline `limit`) is ignored: a user's left rooms are never listed on request. The partition is read again after the joined rooms were fetched: a room whose membership ended during the fetch is rebuilt as a leave of the same response, never delivered in `rooms.join` after the removal (a membership that keeps changing during the fetch is a `503`, no token). A since token that is neither the device's current nor its previous one is an initial-sync fallback (no leaves), never a delivery of everything. A failing membership, head or cursor read answers `503 M_UNAVAILABLE` with `errcode` and `error` and saves no token (M_UNAVAILABLE is not a spec errcode, kept for consistency with the other unavailable answers). Residuals (what the guarantee does not cover): `cq` (the timestamp-ordered reads that remain; `fc`, the timestamp anchor, is closed by story sync-stream-position), `ex` (a ban whose member removal failed), `fg`. **The since token is per device (story sync-token-per-device, follow-up `fd` closed):** the key is the user plus the AUTHENTICATED device (never a request parameter), so two clients of one user no longer overwrite each other's token; device-less requests (an unbound raw IdP JWT) keep the per-user token and flags (`cj`); a token stored before the update falls back to one initial-shaped answer; global account data and the own cross-signing change are delivered per device by stored positions (nothing is consumed, the writer gets the echo too); a fallback answer to a request that carried a `since` lists the own user in `device_lists.changed`; a global account data PUT is a wake-up for the user's waiting `/sync` on every node and pending global account data answers a long-poll at once. **Wake-ups are cluster-wide (story sync-wakeups-cluster-wide, follow-up `fe` closed):** every sender of a message the long-poll waits for (a new event, a join, a leave, an invitation, a changed account-data room) reads its recipients with `:pg.get_members/1`, so a sync task on any node is woken at once and rebuilds from the database; a joined room with new events whose room process is not resolvable on the waking node (the Horde registry replicates by CRDT) is retried for at most one second per build (one deadline per build, shared by its rooms: a room met after another one used up the second is started on its first miss without polling) and then started once on demand (each start attempt costs Horde `start_child`, the init reads and up to 500 ms of registry wait; the whole sync runs in a per-request sync Task with a budget of the long-poll timeout + 10 s, so two rooms whose start times out in all six builds of a 25 s request, 37 s, exceed it and the request fails and is retried: an accepted rare residual); a dead room (archived, e.g. an upgraded room, or missing) is dropped at once and never delays or pins a sync. Only a room that still cannot be resolved (a transient failure) is not delivered and does not move the anchor, so the next sync delivers its events (in that rare case other rooms' events since the old anchor, a `limited` window included, are sent again; an unresolvable room is never an error). A non-archived room whose process can never start keeps the anchor pinned (follow-up `bp`). Known gap `be`: the tombstone of an upgraded room reaches only members whose sync read the old room before it was frozen. **No per-response cap on `rooms.invite` (story rate-limits-join-invite-create-room, D10):** every pending invitation is listed (a capped, hidden invitation would only reappear with the next initial sync: a silent loss); the list is bounded at the source by the per-invitee cap of pending invitations (100, `NEBU_INVITE_MAX_PENDING_PER_INVITEE`) and the per-pair cap (10). **Byte budget (review cycle 1, Kassandra M-2):** the stripped state of an invitation is attacker-written, so one response drops an OPTIONAL stripped event (topic, avatar, canonical alias, encryption, join rules, name) whose content is above 64 KiB and, while the `rooms.invite` total exceeds 8 MiB, the largest optional events (topic first); an invitation and the member events are never dropped and an `m.room.create` above 64 KiB is reduced to its spec keys. The optional stripped state is bounded; create and member content stays unbounded until `ep` (the write-time event size limit, the next story). **Predecessor keys on state events (story member-event-prev-content, follow-up `ff` closed; `unsigned-replaces-state` before it):** every STATE event of `rooms.join` (state and timeline) and of the `rooms.leave` timeline that has a predecessor at its `(room_id, type, state_key)` slot carries, next to `unsigned.age`, the three keys `unsigned.replaces_state` (the predecessor's `event_id`), `unsigned.prev_content` (its content, a JSON object, `{}` when it was empty) and `unsigned.prev_sender` (its sender), always TOGETHER; an event without a predecessor (the first event of its slot, `m.room.create`) and every non-state event carries none of the three (absent, never `null`). One batched lookup per room for the joined sections and ONE batched lookup for all leave entries of the response (no N+1); the order of a slot is the partition's tie order for member slots (`ban`, `leave`, `invite`, `knock`, `join`: the most restrictive is the latest) and `(origin_server_ts, event_id)` for every other type, a Nebu rule instead of the spec's stream order. It is what lets Element mark an accepted direct-chat invitation as a DM (the invitee's join carries `prev_content` = the invite with `is_direct`, `prev_sender` = the inviter) and write "rejected the invitation" instead of "left". `rooms.invite` stripped events are unchanged (exactly four keys, never an `unsigned`). **Member state (story membership-state-model, follow-ups `fb`, `fl` (c)):** the initial `/sync` state lists every member slot (join, invite, ban, knock, leave) from the member events: one slot per user, the latest member event in the tie order, real event id, stored content (the `reason`) and `unsigned` (age, predecessor keys); the incremental `/sync` state keeps the joined slice of the room process: member changes reach clients in the timeline, except in a `limited: true` delta (follow-up `fc`; the synthesized joined slot re-sent in a delta can overwrite the real latest join content, `gg`); a member slot that is in the timeline is not repeated in `state`: state = current member state minus the timeline slots (a client replaying the timeline ends in the same final state; no prior `join` is served for a user banned inside the window); member slots other than `join` are capped at 10 000 per room in the `/sync` state, `/members` and `/initialSync`: Nebu bound; one slice read per joined room of an initial `/sync` (`SET LOCAL` + the slice in one transaction); a read that meets the 2 s statement timeout, loses its pool connection or finds the node-wide limit of 3 concurrent slice reads full degrades only that room (security cycle 2): member state of this room is joined-only until the client's next initial or `full_state` sync, or a `/members` call (lazy loading); ## Key Directory (E2EE-ready, not E2EE)

A PostgreSQL-backed **key directory** that persists and reads back opaque client key
material so Matrix clients (Element Web / Element X) complete device registration and
cross-signing bootstrap cleanly. This is an **E2EE-readiness** facility, **orthogonal to
encryption**: all stored material is opaque, the server never decrypts and never holds a
private part, and persisting these keys does **not** enable room encryption —
`m.room.encryption` is still rejected (`403 M_FORBIDDEN`) per
[ADR-011](architecture/adr/ADR-011-managed-e2ee-key-escrow.md).

| Method | Endpoint | Status | Behavior |
|---|---|---|---|
| POST | `/_matrix/client/v3/keys/upload` | ✅ | Persists device + one-time + fallback public keys (`Nebu.Matrix.DeviceKeyStore`, migration 000009). A raw IdP JWT can never bind to or write the keys of a device that has an OAuth session (`403 M_FORBIDDEN`, the G1 text; OAuth sessions authenticate with Nebu opaque tokens only). |
| POST | `/_matrix/client/r0/keys/upload` | ✅ | Same as v3 (legacy compatibility) |
| POST | `/_matrix/client/v3/keys/query` | ✅ | Echoes stored `device_keys` (DeviceKeyStore) **and** stored `master_keys` / `self_signing_keys` / `user_signing_keys` (CrossSigningKeyStore); empty maps for users without keys |
| POST | `/_matrix/client/v3/keys/device_signing/upload` | ✅ | Persists opaque master/self/user cross-signing keys per user (`Nebu.Matrix.CrossSigningKeyStore`, migration 000010); `200 {}`. MUST-guard: a cross-signing key ID colliding with an existing device ID → `400 M_INVALID_PARAM` before any write. Idempotent re-upload of identical keys is allowed without UIA; overwriting different keys without `auth` → `403 M_FORBIDDEN` (cross-signing-readback story). "Unchanged" (story oauth-account-management, A14 step 3, spec-correct): the request carries `master_key`, it equals the stored one and every additionally SUPPLIED self-/user-signing key equals the stored one (keys not supplied are not compared; earlier all three keys were compared, so a master-only re-upload was answered `403`, now `200` also for legacy callers); a request without `master_key` while a master is stored is a replacement. Replacement by an OAuth caller (`auth_api = oauth`): `m.oauth` UIA (`401` with exactly `flows: [{"stages": ["m.oauth"]}]`, `params["m.oauth"].url` = `<issuer>/account?action=org.matrix.cross_signing_reset`, `session`; no `errcode`); the user approves the request on the account page, the client retries with `auth: {session}` (type absent, `m.oauth` or `org.matrix.cross_signing_reset`) and the keys are replaced (single use, 600 s after approval, bound to the user, the requesting device and ALL supplied keys, consume + key write in ONE transaction, a failed write => `500 M_UNKNOWN` and the approval stays consumable). An approved PARTIAL replacement keeps the stored keys that were not supplied (review cycle 1); an OAuth replacement that supplies no key at all answers `400 M_MISSING_PARAM` "No cross-signing keys supplied"; at most one pending request per device and five per user. Story oauth-authorize-freshness (FR16, gate ak(1)-(3)): the supplied keys are NORMALIZED first, for every caller: an explicit JSON `null` key is an absent key, a key that is not a JSON object is `400 M_BAD_JSON` "Invalid cross-signing key"; a body that supplies no key (`{}` or all `null`) while a master is stored is `400 M_MISSING_PARAM` for EVERY caller, before any approval (a Nebu choice, the legacy caller used to get `403`); the "unchanged" rule compares the supplied (normalized) keys only; the approved replacement reads its merge base `FOR UPDATE` inside the transaction, after consuming the approval (a failing locked read is `500` and the approval is not consumed). While OAuth is not live an OAuth caller gets the legacy `403`. KNOWN DEVIATION (unchanged, out of scope): a LEGACY caller replacing keys still gets `403 M_FORBIDDEN "Cannot replace existing cross-signing keys"` instead of the UIA challenge the spec requires. `m.oauth` appears only here, never in the flows of `DELETE /devices`, `/delete_devices` or the legacy UIA fallback |
| POST | `/_matrix/client/v3/keys/signatures/upload` | ✅ | Validate-then-persist: merges supplied signatures into the stored device/cross-signing key objects (caller-identity guard); `200 {"failures": {}}` on success, per-(user,key) `M_INVALID_SIGNATURE` under `failures` on mismatch. Merged signatures are visible on the next `keys/query` |

After a successful `device_signing/upload`, the uploading user's own ID is surfaced in
`device_lists.changed` of the next incremental `/sync` of every device of the user, the uploader's
included, once per device (`cross_signing_keys.changed_pos` against the device's
`sync_tokens.cross_signing_pos`, story sync-token-per-device; a device-less client keeps the
consume-once `cross_signing_changed` flag on the `cross_signing_keys` table). Both stores follow ADR-018 (inline parameterised SQL
via `Nebu.Repo`, no Ecto schema). `CrossSigningKeyStore` mirrors `DeviceKeyStore`.

## OAuth coexistence notes (story oauth-legacy-coexistence)

`/account/deactivate`, `/account/password`, `/account/3pid*` and `/register` are deliberately absent for BOTH APIs (OAuth-aware clients MUST NOT use them; deactivation is admin or account page, `GET /capabilities` reports `m.change_password` and `m.3pid_changes` as `false`). Since story oauth-room-summary-unrecognized an unrouted Matrix endpoint answers `404 M_UNRECOGNIZED` and an unsupported method `405 M_UNRECOGNIZED` + `Allow`, without an auth check; `POST /register` answers `403 M_FORBIDDEN` (registration not enabled, RU10a); HEAD on GET routes answers 405 (deviation from the RFC 9110 SHOULD). `account_management_uri` and `account_management_actions_supported` are advertised since story 6 (the account page `/account` is live under the same predicate as the metadata; OAuth sessions delete devices there, gate item (w) is closed). Legacy `POST /_matrix/client/v3/logout` is per device since the bugfix legacy-logout-per-device (gate item r closed).
